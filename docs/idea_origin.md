# GitHubに整理した調査メモを「耳で聞ける形」にして読み上げる

## 概要・きっかけ

Claude Code で調査した内容を GitHub のリポジトリ（Markdown）に整理している。読む余裕がないとき（移動中・家事中など）に、それを読み上げて耳で聞きたい。

ただし、文書をそのまま読み上げると、記号（`#`・`|`・`*`・URL等）、表、サンプルコード、mermaid の図などが音声では理解できない。そのため、**読み上げる前に「聞くための原稿」へ要約・意訳する工程**が要る。

処理は大きく2段に分かれる。

1. **原稿化**: Markdown → 聞いて分かる文章（コードは「何をするコードか」の説明に、表は文章に、図は構造の説明に置き換える。URL・記号は読まない）
2. **音声化**: 原稿 → 音声（TTS）

決まっていること（2026-10-17）:

- 原稿は **Claude Code が事前に作る**。その手順は Claude Code の **スキル** にする
- 聞く端末は **Android のスマートフォン** を前提とする。検証のために PC で先に試してもよい

未決の点: 音声化の手段、音声をリアルタイムで作るか事前に音声ファイルを用意するか。

## 評価

- **良い点**
  - 調査した内容を、読む時間のない場面でも復習できる。耳で聞くことで、整理した内容の抜けや分かりにくさにも気づける
  - 「聞くための原稿」は、それ自体が要約として読み返しにも使える
  - 1 の原稿化さえできれば、2 の音声化は既存の無料の TTS で済む可能性が高い（Claude の見立て。各ツールの現在の仕様は着手時に確認する。「実現性」の節を参照）
- **懸念点**
  - **原稿化の質**: 要約・意訳は機械的な置換では難しく、LLM が要る。要約で大事な情報（数値・条件・注意書き）が落ちる、もっともらしい誤りが混ざる、といったおそれがある
  - **原文との食い違い**: 原文の Markdown を更新したのに原稿が古いまま、という状態が起きやすい。原稿がどの版の原文から作られたか（コミット）を記録する等の仕組みが要る
  - **外部サービスへの送信**: 非公開のリポジトリの内容を、無料の外部サービス（クラウドの LLM・TTS）に渡すと、その内容が外部に出る。リポジトリに作業環境や個人に関わる記述が含まれる場合は特に注意が要る
  - **音声ファイルの置き場所**: 事前に音声を作る場合、音声ファイルを Git にコミットするとリポジトリが重くなる。置き場所を別に考える必要がある
  - **再生する端末**: Android のスマートフォンで聞くため、PC でしか再生できない方式は用途に合わない。PC での検証で問題がなくても、Android で同じように聞けるかは別に確かめる必要がある

## 肉付け（想定機能）

- **聞くための原稿の書き方のルール**（原稿化のスキルの中身になる）
  - 見出しは「次は〇〇について」のような話し言葉の区切りにする
  - コードブロックは中身を読まず、「〇〇を△△するコード（言語・要点）」と説明する
  - 表は「〇〇は△△、□□は××」のように文章にする。大きな表は要点だけにする
  - mermaid 等の図は、何と何がどうつながるかを文章で説明する
  - URL・ファイルパス・コマンドは読まず、「参考資料が○件ある」「〇〇のコマンドを実行する」程度にする
  - 冒頭に「この話のポイント（3点程度）」、末尾に「まとめ」を置く
  - 原文のどのファイル・どのコミットから作ったかを記録する（音声では読まない）
- **原稿の置き場所**: 原文の隣（例: `xxx.md` に対して `xxx.listen.md`）か、別フォルダか
- **更新の検知**: 原文が更新されたら原稿を作り直す（手動の依頼か、自動化か）
- **再生**: 再生速度の調整、続きからの再生、複数ファイルの連続再生

## 実現性

- 原稿化: Claude Code はリポジトリを直接読めるため、「このフォルダの Markdown から聞くための原稿を作って」と頼む形なら、仕組みを作らなくてもすぐ試せる。ルールベースの自作（コードブロックや記号を除く）は簡単だが、要約・意訳はできない
- 音声化: ブラウザ・OS・スマートフォンに標準の読み上げ機能があり、VOICEVOX のようなローカルで動く無料の TTS もある（既知の情報による。各ツールの現在の仕様・利用規約は着手時に確認する）
- 難所は、(1)原稿の質と正確さ、(2)原文と原稿の同期、(3)スマートフォンで聞ける形にすること。技術的な難易度は、既存ツールの組み合わせなら低い

## 実現方針（案）

分岐点1・4は決定、分岐点3は原稿の部分のみ決定（2026-10-17）。分岐点2と分岐点3の音声の部分は未決。決めたら `docs/qa_log.md` に記録する。

- **分岐点1: 原稿化に Claude Code をどこまで関与させるか**
  - 選択肢A: Claude Code が原稿を作る（既に Claude Code で扱っているリポジトリなら、その内容は既に読ませているため、新たに外部へ出る範囲が増えない。Claude Code でまだ扱っていないリポジトリを対象に加える場合は、その内容が新たに外部へ出る）
  - 選択肢B: 他の無料ツール（Web の生成 AI、音声で要約する機能を持つサービス等）に原文を渡して原稿化する（手軽だが、非公開の内容がその外部サービスに渡る）
  - 選択肢C: 自作のスクリプトでルールに従って変換する（記号・コードを除くだけで、要約・意訳はしない）
  - 選択肢D: C で機械的に前処理し、要約・意訳だけ A に頼む（組み合わせ）
  - **決定: 選択肢A。原稿化の手順（書き方のルール・原稿の置き場所・原文のコミットの記録）を Claude Code のスキルにする**
  - スキルについて着手時に決めること（Claude の補足）:
    - 置き場所: 複数のリポジトリの調査メモを対象にするなら、ユーザーレベル（`~/.claude/skills/`）が合う。特定のリポジトリだけなら、そのリポジトリの `.claude/skills/` でもよい
    - 呼び方: 意図しないときに原稿が作られないよう、手動で呼ぶ形（スラッシュコマンド）にするか
    - 対象の指定: 1ファイルずつか、フォルダ単位か。原文が原稿より新しいファイルだけを作り直す機能を持たせるか
  - 自動化（GitHub Actions 等から Claude を呼ぶ）は、API の従量課金が別にかかる可能性があるため、手動でスキルを呼ぶ運用で足りない場合に検討する（Claude の見立て）
- **分岐点2: 音声化の手段**（未決。分岐点4の決定により、Android で聞けることが条件になる）
  - 選択肢A: Android のブラウザ・OS の標準の読み上げ機能（GitHub に push した原稿を Android で開いて読み上げる）
  - 選択肢B: ローカルで動く無料の TTS（VOICEVOX 等）で PC 上で音声ファイルを作り、Android に移す
  - 選択肢C: クラウドの TTS（声は自然だが、原稿の内容が外部に渡る。無料枠の範囲・利用規約の確認が要る）
  - 自作の TTS エンジンは目的に対して重いため、候補にしない（Claude の判断）
  - Android の標準の読み上げ機能には、選んだ部分を読み上げる機能や、ブラウザでページを読み上げる機能があるとされる（既知の情報による〈要確認〉。今の機能名・使い方・日本語の声の質は着手時に確かめる）
- **分岐点3: 音声をリアルタイムで作るか、事前に用意するか**
  - 選択肢A: リアルタイム（原稿を開いて、その場で端末の TTS に読ませる）。原稿さえ最新なら音声も最新。音声ファイルの置き場所が要らない
  - 選択肢B: 事前に音声ファイル（mp3 等）を作る。オフラインで聞け、ポッドキャストのように扱える。原文を更新するたびに作り直しが要り、置き場所（Git の外）と Android への移し方を決める必要がある
  - 選択肢C: 原稿は事前に作り、音声はリアルタイム（中間）
  - **決定（原稿の部分）: 原稿は事前に作る**（分岐点1の決定による）。音声をリアルタイムで作るか（選択肢C）、事前に音声ファイルも作るか（選択肢B）は未決
  - Claude の見立て: まず C で試し、声の自然さが気になる場合やオフラインで聞きたい場合に B を足す
- **分岐点4: どこで聞くか（再生する端末）**
  - **決定: Android のスマートフォンを前提とする。検証のために PC で先に試してもよい**
  - PC で試すときは、原稿の分かりやすさ（書き方のルール）の検証が主になる。読み上げの声・操作性は Android で改めて確かめる（Claude の補足）
- **MVP の案（Claude の案）**: 原稿化のスキルの最小版（書き方のルールだけ）で1ファイル分の原稿を作り、まず PC で読み上げて原稿の聞きやすさを確かめる。次に、原稿を GitHub に push して Android の標準の読み上げで聞く。聞きにくかった点をスキルの書き方のルールに反映する
- **セキュリティ**: 外部サービス（分岐点1の B、分岐点2の C）を使う場合は、渡す内容に機微情報・作業環境の情報・個人に関わる記述が含まれないかを先に確認する。新しいツール（TTS ソフト・ブラウザ拡張・アプリ）の導入はユーザー自身が行い、出所の確かなものに限る
- **著作権**: 自分でまとめた文章を自分で聞く個人利用が前提。原文に第三者の文章の引用が含まれる場合、その音声を公開・配布しない
- 仕組みづくり（スキルの作成、原稿の書き方のルールの確定、自動化）は、アイデアを溜める `brainstorming` では行わず、このアイデアファイルを出発点とする実現用の新しいプロジェクトで進める

## 関連するアイデア

- `brainstorming` のアイデア `kindle-image-tts-reader`（Kindle の画像ページを OCR＋TTS で朗読）: 音声化（TTS）の部分の検討を共有できる
- `brainstorming` のアイデア `fast-playback-clarity-enhancer`（倍速再生時の聞き取りやすさ改善）: 原稿を倍速で聞く場合に関係する

## 類似の既存事例（既知の情報のみ。Web 検索はしていない）

- ブラウザや OS に標準の読み上げ機能（ページ全体の読み上げ、選択した部分の読み上げ）がある。ただし Markdown の記号やコードもそのまま読むか、読み飛ばすかの扱いはツール次第
- 文書を渡すと、内容を対話形式の音声に要約してくれる生成 AI のサービスがある（具体的なサービスと現在の仕様・無料の範囲は着手時に確認する）
- **差別化点・示唆**: 「読み上げ」そのものは既存の機能で足りる。価値があるのは、技術メモ（コード・表・図を含む）を **聞いて分かる文章に直すルール** と、それを原文の更新に追いつかせる運用の部分
