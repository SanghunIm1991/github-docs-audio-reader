## 0. 学習目標と完了の条件

学習目標は4つです。

1つ目。強化学習で学習させた方策を、numpy だけで計算する ROS2 のノードにできる。

2つ目。学習のときと同じ観測を、ROS2 のトピックの値から作れる。学習した範囲の外では、NN を使わないようにできる。

3つ目。launch の引数と条件で、起動する制御器を切り替えられる。

4つ目。PI 制御と NN を、同じ一式、同じ目標の並びで記録し、フェーズ6-3 の指標で比べられる。

完了の条件は、4節で PI 制御と NN の記録を取り、5節の比較表から、フェーズ7-4 と同じ傾向、つまり NN は PI 制御に届かず、定常偏差が残ることが、ROS2 のノードの形でも見えることを説明できることです。

## 1. 全体像

フェーズ5-4 では、target_generator が目標速度を送り、pi_controller がペダルを決め、gz_plant が Gazebo の車両を動かして速度を返す、という形でループを閉じました。pi_controller は、スラッシュ target_velocity と、スラッシュ plant スラッシュ velocity を受けて、スラッシュ plant スラッシュ pedal を送るだけなので、同じトピックを受けて送るノードなら、何でも代わりに置けます。このページでは、そこに、フェーズ7-4 で学習させた NN の方策を置きます。

NN の方策は、フェーズ7-4 の2-1節のとおり、掛け算と足し算と、ReLU と tanh を重ねるだけの関数です。重みは .npz にあるので、ノードは numpy だけで計算できます。PyTorch も SB3 も要らないので、ノードは、強化学習の仮想環境ではなく、ふだんの ROS2 の Python で動きます。学習の道具と、学習したものを使う側を分けられることも、.npz に書き出した理由の1つです。

ただし、学習のときと、条件をそろえる必要があります。NN は、フェーズ7-3 の学習用のワールド、つまり車輪の関節に減衰を入れたものと、ブレーキの遅いプラント、つまり tau_brake が1.0秒のプラントで学習しました。また、観測は、目標、速度、偏差、前回のペダル、次の変わり目までの時間の5つでした。このページでは、フェーズ5-4 の一式を写して、ワールドとプラントのパラメータを、学習のときに合わせ、観測を、トピックの値から作ります。目標を切り替える時計も、学習のときと同じ、シミュレーションの時間にそろえます。2-4節の話です。走らせる目標の並びは、フェーズ7-4 の確かめ用のシナリオの1つ、つまり種20 にして、フェーズ7-4 の結果と見比べられるようにします。

## 2. NN の重みでペダルを計算するノード

### 2-1. 仕様

仕様は7つです。

1つ目。ノード名と実行ファイル名は nn_controller で、パッケージは learn_py です。

2つ目。受けるのは、スラッシュ target_velocity と、スラッシュ plant スラッシュ velocity で、どちらも std_msgs の msg の Float64 です。

3つ目。送るのは、スラッシュ plant スラッシュ pedal で、std_msgs の msg の Float64、マイナス1 から1 の値を、period 秒ごとに送ります。名前と型は、pi_controller と同じにします。

4つ目。観測は、フェーズ7-3 の4節の環境の _observation と同じ5つです。目標と速度は10 で割り、偏差は error_scale で割り、前回のペダル、そして次の変わり目までの時間を change_interval で割ったものです。プラスマイナス5 に収めます。次の変わり目までの時間は、目標が変わった時刻を覚え、学習と同じく、change_interval 秒ごとに変わる前提で数えます。

5つ目。目標が0 以下の間、つまり target_generator の最初の切り替えまでは、NN を使わず、ペダル0 を送ります。学習では、目標は毎秒3 から15メートルの範囲だけだったので、0 は、NN にとって学習した範囲の外です。

6つ目。パラメータは4つです。weights は重みのファイルのパス、period は既定0.1秒で学習と同じ、change_interval は既定10秒、error_scale は既定1 で、フェーズ7-3 の環境の既定と同じです。どれも起動するときに決め、実行中の変更は受け付けません。

7つ目。ログは、1秒に1回、目標、速度、ペダルを出します。

### 2-2. 方策のクラスを learn_py に写す

フェーズ7-4 の4-2節の npz_policy.py、つまり NpzPolicy は、ROS2 を使わないクラスなので、そのまま learn_py に写して、ノードから import します。フェーズ5-1 の vehicle_model.py を、plant_node.py から使ったのと同じ形です。

cp で、ホームの rl_practice の npz_policy.py を、ホームの ros2_ws の src の learn_py の中の learn_py のフォルダに写します。

期待する結果は、何も表示されないことです。cp は、成功しても何も表示しません。

### 2-3. ノード、nn_controller_node.py

ファイルは、ホームの ros2_ws の src の learn_py の learn_py の nn_controller_node.py です。

80行ほどのコードで、ブロックは6つです。import、Node を受け継いだクラス NNControllerNode の __init__、on_target、on_velocity、on_timer、そして関数 main です。import では、os、numpy、rclpy、rclpy の executors の ExternalShutdownException、rclpy の Node、std_msgs の Float64、そして learn_py の npz_policy から NpzPolicy を読み込みます。クラスのコメントには、フェーズ7-4 で学習させた NN の方策、つまり .npz で、目標速度と現在速度からペダルの指令を計算して plant の pedal へ送るノードで、観測の作り方は、フェーズ7-3 の環境の gz_pedal_env.py の _observation と同じにする、とあります。on_velocity は、届いた現在速度を覚えるだけです。main は、これまでのノードと同じく、ノードを作って spin で回し、Ctrl+C で後片付けをして終わります。

要の行は1か所で、on_timer の最初の、速度がまだ1つも届いていなければ、何もせずに戻る行です。最初の速度が届くまで、ノードはペダルを送りません。

nn_controller_node.py の解説です。骨組みは、フェーズ5-2 の pi_node.py と同じで、受けた値を覚え、タイマーでまとめて計算して送ります。違うのは、計算に、PIController の代わりに NpzPolicy を使うことと、観測を作る部分です。

解説は5つです。

1つ目は __init__ です。パラメータを宣言し、weights のファイルから NpzPolicy を作ります。os.path.expanduser は、パスの先頭のチルダを、ホームのフォルダに直します。YAML や引数に、チルダで始まるパスを書いても読めるようにするためです。ファイルが無いと、ここで FileNotFoundError になって止まります。読み込めたら、そのパスをログに出します。

2つ目は on_target です。目標が前と違えば、その時刻を change_time に覚えます。時刻は、ノードの時計、つまり get_clock の now で測ります。launch で use_sim_time を真にするので、シミュレーション時刻になります。フェーズ5-4 の5節の話です。

3つ目は on_timer です。フェーズ7-3 の環境の _observation と同じ並びで観測を作り、方策でペダルを計算して送ります。次の変わり目までの時間は、change_interval から、目標が変わってからの経過時間を引いたものを、change_interval で割った値で、0 より小さくはしません。学習では、目標はちょうど10秒ごとに変わったので、この前提が成り立ちます。目標が0 以下の間は、ペダル0 を送り、前回のペダルも0 にしておきます。

4つ目は、前回のペダルです。観測の1つなので、送ったペダルを self.pedal に覚えておき、次の計算に使います。

5つ目。実行中の変更、つまり ros2 param set を受け付ける on_params は、書いていません。重みや観測の作り方を途中で変えると、学習のときと条件がずれるためです。変える場合は、ノードを起動し直します。

学習した範囲の外では NN を使わない、ということについて、補足の囲みがあります。3つの点です。

1つ目は、一般的なことです。NN の方策は、学習で経験した範囲の観測では、それなりの行動を出します。範囲の外の観測、このページなら、目標0 や、学習に無かった速さでは、どんな行動を出すかの保証がありません。実際のロボットで NN を使うときは、入力が学習の範囲にあるかを確かめ、外れたら、決まった安全な動作に移す仕組みを、NN の外に置くことが多いです。安全な動作は、たとえば、止める、人に知らせる、別の制御器に切り替える、などです。

2つ目は、このサンプルの扱いです。目標が0 以下の間はペダル0 にする、という最も簡単な形だけにしました。速度が学習の範囲を外れた場合の扱いは、書いていません。

3つ目は、実務の目安です。NN の出力をそのまま使わず、範囲の確認や、出力の変化の速さの制限を、NN の外で行います。

### 2-4. target_generator の時計を選べるようにする

フェーズ5-4 の5節では、target_generator に use_sim_time を渡さず、現実の時間、つまり単調増加する時計で目標を切り替えました。このページでは、これを変えます。

NN の観測の1つの、次の変わり目までの時間は、nn_controller が、シミュレーション時刻で、目標がちょうど change_interval、つまり10秒ごとに変わる前提で数えます。2-3節の on_timer の話です。目標の切り替えが現実の時間のままだと、Gazebo が現実より遅く動くとき、シミュレーションの時間で見た1段が、10秒より短くなります。たとえば、Gazebo が現実の80パーセントの速さで動くと、1段は約8秒になり、次の変わり目までの時間は、0.2 より小さくならないうちに1 へ戻ります。学習では、段の終わりに必ず0 まで下がっていた値なので、NN にとっては、学習と違う状況になります。指標を測る段も短くなります。

そこで、フェーズ6-1 の4-1節の target_node.py を、パラメータ use_sim_time で時計を選ぶように書き換えます。フェーズ5-4 の5節の末尾の課題3 と、同じ考え方です。use_sim_time は、どのノードにも初めからあるパラメータで、既定は偽です。偽のときは、今までどおり単調増加する時計で測るので、フェーズ5-3 から6-3 の launch で起動したときの振る舞いは、変わりません。

書き換えるのは、ファイル target_node.py の、次の4か所です。

1か所目は、クラスのコメントです。3行目として、経過時間は、use_sim_time が真ならシミュレーション時刻で、偽なら単調増加する時計で測る、という1行を足します。

4か所目は、on_params のコメントと、拒否するパラメータの名前です。コメントを、階段と周期と終わる時刻と時計は、起動時にだけ決められるので、実行中の変更は拒否する、とし、拒否する名前の並び、つまり step_times、step_values、period、end_time に、use_sim_time を足します。

target_node.py の変更点の解説は、4つです。

1つ目は、self.get_clock です。ノードの時計で、use_sim_time が真なら、ブリッジが中継するスラッシュ clock に従う、シミュレーション時刻になります。フェーズ5-4 の5節の話です。スラッシュ clock がまだ届いていない間は0 を返し、この時計で動くタイマー、つまり on_timer も呼ばれません。そのため、Gazebo より先に起動しても、self.start は0 になり、経過時間は、Gazebo の時刻とほぼ同じになります。

4つ目。時計を選ぶだけなので、target_generator の登録、つまり entry_points は、変えなくてかまいません。

1つ目は、一般的なことです。シミュレーションの中のロボットに、人や外の仕組みが指令を送る場面を試すなら、指令は現実の時間で来ます。一方、シミュレーションの中で決まった試験の手順、つまりシナリオを再現するなら、手順もシミュレーションの時計で進めないと、PC の速さによって、手順の中身が変わってしまいます。

読み方です。表の読み方は、フェーズ6-3 の2-2節と同じです。rise[s] は立ち上がり時間で、変化の90パーセントに届かなければハイフンです。settle[s] は整定時間で、段の終わりまでに、プラスマイナス2パーセントの帯に収まらなければハイフンです。error は定常偏差で、目標から、段の最後の1秒の速度の平均を引いたものです。sat[s] は、ペダルがプラスマイナス1 に張り付いた時間です。サンプル数は、どちらも、50ヘルツで100秒分の約5000 になります。目標をシミュレーション時刻で切り替えるので、PC の速さによらず、ほぼこの数になります。2-4節の話です。目標を現実の時間で切り替えると、Gazebo が現実より遅く動く分だけ、少なくなります。作成時に、そうして記録したときは、4771 と4924 だった、とあります。行き過ぎ量、定常偏差、RMS の値は、次の5-2節の比較表で読みます。

読み方は5つです。

1つ目は、減速の段で、PI 制御は大きく行き過ぎる、ということです。ブレーキの遅いプラント、つまり tau_brake が1.0秒のプラントなので、PI 制御は、減速の段で約40パーセント行き過ぎます。つまり、目標より下まで落ちます。その後は、積分の項で目標に戻り、段の最後の偏差は、毎秒0.1メートル以内に収まります。この PI 制御は、フェーズ7-4 と同じく、手で決めた既定のゲイン、つまり kp 0.5、ki 0.1 で、任意のフェーズ7-2 で調整したゲインではありません。フェーズ7-4 の5-2節の、比べた PI 制御は、手で決めた既定のゲインだ、という項目の話です。

2つ目は、NN は、減速の段の行き過ぎが小さい代わりに、目標まで落としきらない、ということです。NN の減速の段の行き過ぎ量は、0 から17パーセントと小さいです。一方、定常偏差は、毎秒マイナス0.58 からマイナス1.65メートルで、段の最後になっても、目標より速いままです。定常偏差は、目標から速度を引いたものなので、負は、速度が目標より大きいことを表します。行き過ぎを重く減点されて学んだ、つまり重み20 なので、減速ではブレーキを控えめにしている、という読み方もできるが、作成時には確かめていない推測だ、とあります。次の項目のとおり、行き過ぎの減点は加速の段にもかかるのに、NN は加速の段では行き過ぎているので、重みだけでは説明しきれない、とあります。

3つ目は、加速の段では、NN が行き過ぎる、ということです。PI 制御は、加速の段では、ほとんど行き過ぎません。アクセル全開に張り付いて上げ、手前で緩めます。NN は、加速の段で10 から30パーセント行き過ぎ、3.2 から7.2 の段では、段の最後まで、目標より速いまま残ります。最初の段、つまり0.0 から7.0 は、学習では、止まった状態から始める最初の10秒に当たり、行き過ぎを数えない段でした。フェーズ7-1 の4節の vehicle_env.py の解説の、direction の話です。最初の段には、上げる、下げる、の向きが無いので0 になります。フェーズ7-3 の環境も、同じ数え方です。学習で減点されなかった振る舞いが、そのまま出ている可能性がある、とあります。

4つ目は、RMS は、PI 制御が少しよい、ということです。比較表の最後の行のとおりです。どちらも、最初の段、つまり目標0 から7.0 への加速を含むので、フェーズ7-4 の5-2節の RMS、つまり最初の10秒を含まないものより大きいです。また、フェーズ7-4 の値は、5つのシナリオ、つまり種20 から24 の平均で、このページは、種20 の1回だけなので、そのまま比べる値ではありません。

5つ目は、フェーズ7-4 と同じ傾向が、ROS2 のノードの形でも見える、ということです。NN は PI 制御に届かず、定常偏差が残ります。フェーズ7-4 の5-2節の話です。強化学習の環境の中で比べた結果と、ROS2 のトピックでつないだ一式で比べた結果が、同じ向きになりました。学習した方策を、学習の道具の外に持ち出しても、少なくともこの1つのシナリオの1回の記録では、学習の環境と同じ傾向で働きました。記録を取り直すと、値は少し変わります。冒頭の注記の話です。

強化学習の環境と、ROS2 の一式の違いについて、補足の囲みがあります。フェーズ7-4 の環境と、このページの一式は、同じワールド、同じプラント、同じ観測を使いますが、次の4つの点が違います。そのため、同じ種20 のシナリオでも、指標の値は、ぴったりは一致しません。

1つ目は、時間の進め方です。フェーズ7-4 の環境は、Gazebo を一時停止して0.02秒ずつ進め、計算が終わるのを待ちました。このページは、Gazebo が現実の時間で動き続け、ノードは0.1秒ごとのタイマーで計算します。計算の遅れや、トピックが届く時機の分、ペダルが変わる時機が、わずかにずれます。

2つ目は、アクチュエータの計算の刻みです。フェーズ7-3 の環境は0.02秒ごと、gz_plant は、period の既定の0.01秒ごとに計算します。

3つ目は、目標の値です。YAML には、小数第2位で丸めた値を書きました。

4つ目は、目標の切り替えの時機です。どちらも、目標を、シミュレーションの時間で10秒ごとに切り替えます。このページは2-4節の話です。ただし、このページの target_generator は、0.1秒ごとのタイマーで時刻を確かめるので、目標が実際に変わるのは、10秒の区切りから、最大で0.1秒ほど遅れることがあります。

## 6. 本フェーズのまとめ

4つあります。

1つ目。学習した方策を、.npz の重みと numpy だけで計算する ROS2 のノード、つまり nn_controller にしました。PyTorch や SB3 を、ふだんの ROS2 の Python に入れずに済みます。

2つ目。観測は、学習のときと同じ並び、同じ割り算で、トピックの値から作りました。次の変わり目までの時間は、目標が変わった時刻から数えました。目標の切り替えも、use_sim_time でシミュレーション時刻にして、学習のときと同じく、シミュレーションの時間で10秒ごとに段が変わるようにしました。学習した範囲の外、つまり目標0 では、NN を使わず、ペダル0 にしました。

3つ目。launch の引数と、IfCondition と EqualsSubstitution で、PI 制御と NN を切り替えました。トピックの名前と型をそろえておけば、制御器を入れ替えるだけで、同じ一式、同じ記録と解析の手順で比べられます。

4つ目。ROS2 の一式でも、フェーズ7-4 と同じく、NN は PI 制御に届かず、定常偏差が残りました。NN は、減速の段の行き過ぎは小さいですが、目標まで落としきりません。
