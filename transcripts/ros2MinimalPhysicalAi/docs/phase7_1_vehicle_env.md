# フェーズ7-1: 車両の環境を作る、ペダルを選ぶ環境（聞くための原稿）

これは、ros2MinimalPhysicalAi という教材の、フェーズ7-1 の手順書の話です。学習計画のフェーズ7 の7-1、元のアイデアのステップ6 に当たります。フェーズ5-1 の車両のプラントを、Gymnasium の環境として包みます。方策、つまりエージェントは、0.1秒ごとに、マイナス1 から1 のペダルの指令を直接選び、環境は、追従の良し悪しを報酬として返します。目標速度は、10秒ごとに、ランダムな幅で上がったり下がったりします。このページでは、環境を作って SB3 の check_env で点検し、PI 制御を方策として当てはめたものや、ペダルを一定にした方策、でたらめな方策で動かして、報酬の性質を確かめます。そして、SB3 の学習の流れにつながることを確かめるところまでを扱います。次のフェーズ7-3 では、同じ形の環境を、フェーズ5-4 の Gazebo の物理で作り、フェーズ7-4 で、その環境で NN の方策を学習させます。

想定する環境は、WSL2 と Ubuntu 24.04 と ROS2 Jazzy です。このページは ROS2 を使わず、ワークスペースのコードだけを借ります。前提は、フェーズ7-0 です。フェーズ6-3 までを終え、ホームの ros2_ws の learn_py に、フェーズ5-1 の vehicle_model.py、フェーズ5-2 の pi_control.py、フェーズ6-3 の metrics.py があり、ビルドしてあることです。所要時間の目安は2コマで、言語は Python です。ROS2 のノードは書きません。

この手順書の位置づけの囲みです。フェーズ7、つまり7-0 から7-6 は、ひととおり作成を終えた段階で、今後の見直しで内容を改めることがある、とあります。このページは、2026年10月11日に、PI 制御のゲインを選ぶ環境から、ペダルを直接選ぶ環境に作り直しました。最終ゴールまでの道筋を短くするためです。ゲインを選ぶ環境は、任意のフェーズ7-2 に移しました。

進め方の囲みです。1節で全体像を見て、2節で環境の設計、つまり何を観測し、何を選ばせ、どんな目標速度で走らせ、何を報酬にするかを決めます。3節で、ワークスペースのコードを、仮想環境から読み込めるようにします。4節で環境のクラスを書き、5節で点検して動かします。サンプルは、学習の手がかりとして最小限に書いたもので、公式の文書の転載ではありません。Gymnasium の環境の決まりごとは、公式の文書の Create a Custom Environment を、自分の言葉でまとめたもの、とあります。

## 0. 学習目標と完了の条件

学習目標は6つです。

1つ目。Gymnasium の環境のクラスが持つべきもの、つまり観測と行動の空間、reset、step を説明し、自分で書ける。

2つ目。車両の環境の観測、行動、報酬、エピソードを、フェーズ5 と6 の部品に当てはめて説明できる。

3つ目。目標速度をランダムに変えるシナリオにする理由と、乱数の種でシナリオを再現する方法を説明できる。

4つ目。観測に、前回のペダルと、次に目標が変わるまでの時間を入れる理由と、観測と行動の大きさをそろえる理由を説明できる。

5つ目。報酬の合計、つまり収益が、フェーズ6-3 の RMS と、どう関係するかを説明できる。

6つ目。SB3 の check_env で環境を点検し、PI 制御を方策として当てはめたものと、ほかの方策の収益を、複数のシナリオで比べられる。

完了の条件です。5-1節で、check_env が通り、1つのシナリオを PI 制御で走らせた結果を、フェーズ6-3 の指標で読めること。そのうえで、ブレーキの遅いプラントでは、PI 制御が減速の段で大きく行き過ぎることと、収益の内訳、つまり最初の加速の段、RMS に当たる分、行き過ぎの減点を説明できることです。5-2節で、SB3 の SAC の学習が、この環境で動くことを確かめます。

## 1. 全体像

フェーズ5-2 では、PI 制御のゲインを、式から目安を立て、シミュレーションで確かめながら、手で決めました。PI 制御は、偏差に比例して踏み、偏差の積み重ねに応じて踏み足す、という決まった式で、ペダルを計算します。フェーズ7 の最終ゴールは、この式をやめ、強化学習で学習させたニューラルネットワーク、つまり NN に、観測から直接ペダルを選ばせることです。NN なら、目標との差や、目標が次に変わるまでの時間など、そのときの状況に応じて、毎回違うペダルを出せます。PI 制御の式に縛られないので、うまく学べば、PI 制御よりよい追従ができるかもしれません。

エージェントに試行錯誤させるには、まず、試す場所が要ります。フェーズ7-0 の振り子では、Gymnasium が環境を用意してくれていました。車両では、自分で環境を作ります。と言っても、プラントの計算、つまりフェーズ5-1 の VehicleModel は、ROS2 を使わないクラスとして、すでにあります。このページでは、それを、エージェントが行動、つまりペダルを選び、環境が観測と報酬を返す、という強化学習の形に包みます。

環境は、次のフェーズ7-3 で、フェーズ5-4 の Gazebo の物理を使っても作ります。最終ゴールに向けたフェーズ7-4 の学習は、Gazebo の環境で行います。それでも、先に Python の式で同じ形の環境を作るのは、式なら、90秒分の1エピソードを、0.1秒程度で計算できるからです。Gazebo では、1エピソードに40秒程度かかります。フェーズ7-3 の5節で測ります。観測、行動、報酬という環境の設計を確かめ、方策をいろいろ当てはめて報酬の性質をつかむのは、すぐに結果が出る式の環境のほうが向いています。フェーズ7-3 では、同じ方策の PI 制御を、式と Gazebo の両方で走らせ、物理の違いで収益がどれだけ変わるかも比べます。

題材にするのは、ブレーキの時定数を1.0秒にした、ブレーキの遅いプラントです。フェーズ5-2 の6-5節では、ブレーキの時定数を1.0秒にすると、同じゲインの PI 制御でも、減速の段で、目標より下まで落ちる、つまり行き過ぎることを見ました。手で決めた PI 制御が苦手とするプラントなので、NN が PI 制御を上回る余地があるかもしれません。結果は、フェーズ7-4 と7-5 で確かめます。

もう1つ考えるのが、どんな目標速度で走らせるかです。フェーズ6 で記録した目標速度の階段、つまり毎秒10メートルまで加速し、毎秒5メートル、0 と下げる階段は、毎回同じ1通りでした。同じ1通りの走り方だけで学ばせると、その走り方にだけ合った方策になりかねません。実際の道では、前の車に合わせて、速度を少し上げたり下げたりすることが多いです。そこで、このページでは、走るたびに、目標速度が10秒ごとにランダムな幅で上下する、シナリオを作ります。

## 2. 環境の設計

### 2-1. Gymnasium の環境の決まりごと

Gymnasium の環境は、クラス gymnasium.Env を受け継いだクラスとして書きます。フェーズ7-0 の3節で、用意された環境を reset と step で動かしました。自分で環境を書くときは、その2つと、観測と行動の範囲を、自分で用意します。公式の文書の Create a Custom Environment が示す決まりごとを、このページに要る範囲でまとめた表があります。

表は2列で、4行あります。列は、用意するものと、役割です。

1行目は self.observation_space で、観測の形と範囲です。連続値なら、spaces.Box に、下限、上限、形、型を渡して作ります。

2行目は self.action_space で、行動の形と範囲です。同じく spaces.Box で作ります。

3行目は reset で、引数は seed と options です。新しいエピソードを始め、最初の観測と info の組を返します。最初に、親のクラスの reset に seed を渡して呼びます。これで、環境の乱数の self.np_random の種が決まります。

4行目は step で、引数は action です。行動を1回受け取って環境を進め、観測、報酬、terminated、truncated、info の5つを返します。フェーズ7-0 の3-1節と同じです。

info は、学習には使わない、付加的な情報を入れる辞書です。このページでは、報酬の内訳を入れます。

環境の中で乱数を使うときは、Python の random や numpy の共通の乱数ではなく、self.np_random を使います。reset に seed の0 を渡すように種を渡すと、self.np_random が作り直され、同じ種なら、同じ乱数の並びになります。このページの環境は、目標速度のシナリオを、この乱数で作るので、種を決めれば、同じシナリオを何度でも再現できます。2-4節で扱います。

環境を書いたら、SB3 の check_env で点検します。check_env は、空間の定義、reset と step の戻り値の形、観測が空間の範囲に収まっているかを確かめます。決まりごとから外れていればエラーで、SB3 で学習しにくい作りなら警告で知らせます。SB3 の公式の文書の、Using Custom Environments の話です。

### 2-2. 観測、行動、報酬、エピソード

フェーズ7-0 の2-2節の用語の表に、このページの環境を当てはめた表があります。表は2列で、9行あります。列は、用語と、このページの環境です。

1行目はエージェントで、ペダルを選ぶものです。このページでは、PI 制御を当てはめた方策、ペダルを一定にした方策、でたらめな方策で、フェーズ7-4 では SAC に学習させます。

2行目は環境で、目標速度のシナリオと車両のプラントを、まとめて計算するものです。

3行目は行動で、ペダルの指令1つです。マイナス1 から1 で、正がアクセル、負がブレーキです。フェーズ5-1 で決めたものです。

4行目は観測で、5つです。目標速度と現在速度で、どちらも毎秒10メートルで割ります。偏差で、毎秒メートルのままです。前回のペダル。次に目標が変わるまでの時間で、10秒で割ります。

5行目は報酬で、0.1秒ごとに、誤差の2乗と行き過ぎの2乗から計算する、負の数です。2-5節で扱います。

6行目はステップで、0.1秒、つまりペダルを選ぶ間隔です。

7行目はエピソードで、1つのシナリオを最後まで走る、90秒、つまり900ステップです。走り切ると、terminated、つまり課題の終わりで終わります。2-6節で扱います。

8行目は方策で、観測からペダルを選ぶ規則です。このページでは、PI 制御の計算、一定のペダル、でたらめで、フェーズ7-4 では SAC の NN です。

9行目は収益で、1エピソード、つまり900ステップの報酬の合計です。2-5節で、RMS との関係を示します。

なぜペダルを直接選ばせるのか、の説明です。強化学習を制御に使う形は、大きく2つあります。1つは、PI 制御の式は残し、そのゲインだけを選ばせる形です。制御の仕組みは、人が理解できるまま残りますが、選ぶのは2つの数だけで、強化学習を使わずに、格子状に全部試しても足りることが多いです。任意のフェーズ7-2 で、この形を試し、格子の探索と比べます。もう1つは、式そのものをやめ、観測からペダルを直接選ばせる形です。状況に応じて毎回違うペダルを出せますが、偏差に応じてどう踏むか、という構造も、試行錯誤から学ぶことになります。最終ゴールでは、後者の形の NN を、ROS2 のノードとして、PI 制御の代わりに置きます。

なぜ0.1秒ごとに選ぶのか、の説明です。フェーズ5-2 の PI 制御は、0.02秒ごとにペダルを計算しました。同じ間隔にすると、1エピソードが4500ステップになり、学習にかかる時間が延びます。アクセルとブレーキの遅れ、つまりフェーズ5-1 の時定数は、アクセルが0.5秒、このページのブレーキが1.0秒で、それに比べれば、0.1秒は十分に短いです。PI 制御を0.1秒ごとに計算しても、目標を追いかけられることは、5-1節で確かめます。

観測に前回のペダルを入れる理由です。PI 制御には、偏差の積分という記憶があります。フェーズ5-2 の2-1節の話です。積分の項が、これまでの偏差の積み重ねを覚えていて、その分だけペダルを足し引きするので、定常偏差、つまり段の最後に残る目標との差が、0 に近づきます。NN の方策、つまり SB3 の既定の MlpPolicy は、その時点の観測だけからペダルを決め、記憶を持ちません。そこで、記憶の代わりになる手がかりとして、前回のペダルを観測に入れます。車両の駆動力と制動力は、フェーズ5-1 の時定数のとおり、ペダルに少し遅れて追いつくので、今の速度だけでは、車両がこれから加速するのか減速するのかが分かりません。前回のペダルは、その手がかりになります。偏差の積分そのものを観測に入れる方法もあり、作成時の予備の試行で試した、とあります。原文のリポジトリに、没案として残したページの7節の話です。

観測に、次に目標が変わるまでの時間を入れる理由です。目標速度は10秒ごとに変わり、90秒でエピソードが終わります。時刻が観測に無いと、エージェントは、たとえば12秒と18秒の状態、つまりどちらも目標に近づいた車両を、区別できません。しかし、次の変わり目までの長さが違うので、その先に受け取る報酬も違います。Gymnasium の公式の文書の Handling Time Limits は、長さの決まった課題では、残りの時間を観測に入れる必要がある、と述べています。この環境では、次に目標が変わるか、エピソードが終わるまでの秒数を10 で割って、0 から1 の数として入れます。

観測の大きさをそろえる理由です。SB3 の公式の文書の Reinforcement Learning Tips and Tricks は、範囲が分かっているなら、観測を正規化する、つまりおよそマイナス1 から1 の大きさにそろえるよう勧めています。NN は、入力の大きさがそろっているほうが、学びやすいためです。目標と速度は、0 から毎秒20メートル程度なので、10 で割ります。前回のペダルは、もともとマイナス1 から1 です。偏差だけは、割らずに毎秒メートルのまま渡します。10 で割ると、毎秒0.1メートルのずれは、NN には0.01 にしか見えず、目標の近くでの細かな差が、埋もれやすいからです。作成時に、10 で割った場合と、毎秒メートルのままの場合を比べ、毎秒メートルのままのほうが、NN の学習が進みやすかった、とあります。没案として残したページの3-3節の話です。偏差は、目標が変わった直後でも、プラスマイナス毎秒4メートル程度に収まります。観測の空間は、余裕をみてマイナス5 から5 とし、外に出た値は、マイナス5 から5 に切りそろえます。止まった状態から始めた直後は、偏差が毎秒5メートルを超えるので、5 になります。5-1節の最初の観測で確かめます。

### 2-3. 行動をマイナス1 から1 にそろえる

SB3 の公式の文書の Tips and Tricks は、連続値の行動の範囲を、マイナス1 から1 の対称な範囲にそろえるよう勧めています。範囲がそろっていないと、学習の初めの探索がかたよったり、範囲の端に張り付いたりして、学習がうまく進まないことがあり、原因にも気づきにくいからです。範囲が違う量、たとえば0 から2 の値を選ばせたいときも、環境が受け取る行動はマイナス1 から1 にし、環境の中で引き延ばします。任意のフェーズ7-2 では、ゲインをこの形で選ばせます。

ペダルの指令は、フェーズ5-1 で決めたとおり、もともとマイナス1 から1 で、マイナス1 がブレーキ全開、1 がアクセル全開なので、そのまま行動にできます。check_env は、行動の範囲がマイナス1 から1 でなければ、警告を出します。このページの5-1節の末尾の課題1で確かめます。

### 2-4. 目標速度のシナリオ

1つのエピソードの目標速度は、次の4つの決まりで作ります。

1つ目。最初の目標を、毎秒5 から12メートルの間で、ランダムに決めます。車両は、止まった状態から始めます。

2つ目。10秒、20秒と、80秒までの8回、目標を、毎秒1 から4メートルのランダムな幅で、ランダムな向き、つまり上げるか下げるかに変えます。

3つ目。目標は、毎秒3 から15メートルの範囲に収めます。変えた先が範囲から出るなら、向きを逆にします。

4つ目。90秒で終わります。

この形にした理由は、3つあります。

1つ目は、毎回違う走り方にするためです。1通りのシナリオだけで学ばせると、その走り方にだけ合った方策になりかねません。シナリオを乱数で作れば、上げる段と下げる段、小さな段と大きな段が混ざった、いろいろな走り方で、良し悪しを測れます。

2つ目は、方策の差が表れる大きさの段にするためです。0 から毎秒10メートルのような大きな段では、アクセルを踏み切っている、つまりペダルがプラス1 に張り付いている時間が長くなります。フェーズ6-3 の7-2節の比較表では、6.08秒でした。張り付いている間は、どんな方策でも、それ以上は速く加速できないので、その間の誤差は、方策では減らせません。段の幅を毎秒1 から4メートルにすると、張り付く時間が短くなり、方策の良し悪しが、追従に表れやすくなります。段の幅を大きくした場合は、このページの5-1節の末尾の課題2で確かめます。

3つ目は、止まった状態から始めるためです。フェーズ7-3 の Gazebo の車両は、エピソードの始めに速度を与えるのが難しいので、止まった状態から始めます。このページの環境も同じにして、式と Gazebo で、同じシナリオを、同じ条件で比べられるようにしました。最初の10秒は、止まった状態から、最初の目標へ加速する段になります。

シナリオの乱数には、2-1節の self.np_random を使います。reset に seed の0 を渡して始めれば、何度実行しても、同じ種のシナリオは同じになります。このページでは、方策の良し悪しを、種0 から19 の20通りのシナリオの、収益の平均で比べます。

### 2-5. 報酬

報酬は、フェーズ6-3 の8節で考えた2つの案を、合わせた形にしました。全体の1つの数、つまり RMS の2乗に当たる、誤差の2乗の平均に、行き過ぎの減点を、重み付きで足します。0.1秒、つまり1ステップごとに、その0.1秒の間の誤差 e と、行き過ぎ o を、0.01秒ごとに積み上げます。誤差 e は、目標 r から速度 v を引いたものです。

式は、報酬イコール、マイナス、90分の10 かける、その0.1秒の間の、e の2乗に20 かける o の2乗を足したものに、デルタ t を掛けて足し合わせたもの、です。

記号の説明は3つです。

1つ目。デルタ t は、プラントの刻み幅の0.01秒、90 はエピソードの長さの秒数、10 は報酬に掛ける数で、reward_scale という名前です。この節の末尾で扱います。

2つ目。行き過ぎ o は、目標が変わった向きに、速度が目標を超えた量で、超えていなければ0 です。目標を上げた段では、速度から目標を引いたもの、下げた段では、目標から速度を引いたもの、の正の部分になります。フェーズ6-3 の2-2節の行き過ぎ量と同じ向きの考え方で、こちらは割合ではなく、速度の差、つまり毎秒メートルのまま使います。最初の10秒は、目標がまだ変わっていないので、行き過ぎは数えません。止まった状態から最初の目標へ加速する段で、上げる、下げる、の向きが無いためです。

3つ目。目標を超えた側の誤差は、e の2乗に20 かける o の2乗を足すと、21 かける e の2乗になり、21倍重く数えることになります。目標に届かない側の誤差は、o が0 なので、e の2乗のままです。

収益と RMS の関係です。1エピソードの報酬を全部足すと、90秒全体で、e の2乗に20 かける o の2乗を足したものを積み上げて、90 で割り、10 を掛けた量の、マイナスになります。つまり、収益イコール、マイナス10 かける、誤差の2乗の平均に、20 かける 行き過ぎの2乗の平均を足したもの、です。

平均は、どちらも90秒の平均です。収益が大きい、つまり0 に近いほど、追従がよいことになります。報酬を90 で割ったのは、収益を、エピソードの長さによらない、平均の大きさにそろえるためです。フェーズ6-3 の RMS は、最初に目標が変わった10秒からの80秒で数えます。フェーズ6-3 の2-2節の表の話です。そのため、収益には、RMS に入らない、最初の10秒の加速の段の誤差も入ります。実際の値での内訳は、このページの5-1節で確かめます。

報酬に10 を掛ける理由です。0.1秒ごとの1ステップの報酬は、10 を掛けないと、とても小さくなります。目標と毎秒1メートルずれていても、1 の2乗かける0.1 を90 で割った、約0.0011 です。値が小さすぎると、追従のよしあしの差が、NN の学習の中で埋もれやすくなります。作成時に、Python の式の環境で比べると、報酬を10倍にし、偏差を毎秒メートルのまま渡す組み合わせで、NN の学習が進みやすかった、とあります。没案として残したページの3-3節の話です。掛ける数は、引数 reward_scale で変えられます。報酬の内訳、つまり info は、掛ける前の値で返すので、掛ける数を変えても、同じ物差しで比べられます。

報酬の重みの決め方について、補足の囲みがあります。3つの点です。

1つ目は、一般的な考え方です。報酬に複数の項を足し合わせるとき、それぞれの重みは、何をどれだけ嫌うか、という設計者の判断です。強化学習のエージェントは、報酬を大きくすることだけを目指すので、報酬に入れなかった性質、たとえば乗り心地は気にしませんし、重みの比のとおりに、性質を取引します。

2つ目は、この環境で重みを20 にした理由です。フェーズ6-3 の7-2節の比較表のとおり、RMS だけでは、行き過ぎるが速い、と、行き過ぎないが遅い、の区別がつきません。車両では、目標を超える、つまり前の車に近づきすぎるほうが、届かないより困ることが多いです。そこで、行き過ぎを大きく減点するように、筆者が目安として20 を選びました。重みを変えると、学習した方策の行き過ぎの大きさが変わります。これは、フェーズ7-4 で確かめます。任意のフェーズ7-2 では、ゲインを選ぶ形で、追従の速さと行き過ぎのバランスがどう変わるかを、より詳しく確かめます。

3つ目は、実務の目安です。重みは、学習させた結果の振る舞い、つまり行き過ぎ量や整定時間などの指標を見て、調整します。報酬の値だけを見ていると、重みを変えたことによる見かけの改善と、本当の改善を、取り違えやすいです。そのため、報酬とは別に、フェーズ6-3 の指標のような、人が読める数で、結果を確かめます。

### 2-6. エピソードの終わり方

この環境には、失敗して終わる条件がありません。フェーズ7-0 の3-1節の CartPole で、棒が倒れる、のようなものです。エピソードは常に、シナリオを最後まで走り切った90秒で終わります。このとき、step は、terminated、つまり課題の終わりを、True にして返します。

フェーズ7-0 の2-3節で見たとおり、Gymnasium は終わり方を2つに分け、学習のアルゴリズムは、この2つを違うものとして扱います。振り子は、本来はいつまでも続けられる課題を、200ステップで区切っているだけなので、truncated、つまり時間切れでした。アルゴリズムは、この先も報酬が続いていたはず、とみなし、終わりの観測からの見込み、つまりその先の収益の見積もりを、収益に足し込んで学びます。一方、この環境の90秒は、走るシナリオそのものの終わりで、その先に続きはありません。そのため、terminated にします。2-2節で、残りの時間を観測に入れたのも、この終わり方に合わせたものです。エージェントは、観測から、あと何秒で終わるかが分かります。

6行目。targets や収益が、このページの5-1節の期待する結果と違う場合です。reset で、親のクラスの reset に seed を渡して最初に呼び、シナリオを self.np_random で作っているかを確かめます。make_targets の乱数の呼び方の順、つまり最初の目標、幅、向き、の順を変えていないか。定数、たとえば CHANGE_INTERVAL や FIRST_TARGET や、引数の既定値、つまり overshoot_weight、reward_scale、step_range、ブレーキの時定数を変えていないかも確かめます。

7行目。ROS2 のノードが、ビルドし直した後に動かなくなった場合です。仮想環境を有効にしたまま、colcon build しなかったかを確かめます。強化学習の環境構築の5節の話です。

## 8. 次へ

最終ゴールへの道筋では、次はフェーズ7-3 です。フェーズ7-3 では、このページと同じ形の環境を、フェーズ5-4 の Gazebo の物理で作り、同じシナリオを PI 制御で走らせて、式の環境との違いを比べます。次のフェーズ7-4 で、その環境で、ペダルを直接選ぶ NN を学習させます。

任意の寄り道のフェーズ7-2 では、ペダルではなく、PI 制御のゲインを選ぶ環境を、このページの vehicle_env.py のシナリオを使って作り、SAC にゲインを学習させます。強化学習を使わない格子の探索や、手で決めた既定のゲインと、収益とフェーズ6-3 の指標で比べ、報酬の重みを変えると、追従の速さと行き過ぎのバランスが変わることを確かめます。
