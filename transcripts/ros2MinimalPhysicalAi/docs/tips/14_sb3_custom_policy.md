## 14. SB3 の方策に、MlpPolicy 以外の NN を使う

読める時期について、囲みがあります。フェーズ7-0 の5節、つまり学習した NN の中身を見る節の後に読めます。14-6節の、重みを書き出して使う話は、フェーズ7-4 の2節、3-1節、4-2節を読んだ後のほうが分かりやすい、とあります。

### 14-1. 疑問: MlpPolicy のほかの NN は使えるのか

フェーズ7-0 の4節では、SAC に、文字列の MlpPolicy と env を渡して、エージェントを作りました。5節で中身を見ると、方策は、256個の数を持つ層が2つの、全結合の NN でした。フェーズ7 の残りのページも、すべてこの形で学習させています。では、層の数や大きさを変えたり、別の種類の NN を使ったりはできるのでしょうか。

まず、言葉を1つ整理します。SAC に渡した MlpPolicy は、ファイルを読み込む指定ではありません。方策と critic の NN を、どの形で新しく作るかの指定です。学習したものを読み込むのは、SAC.load のほうです。

形の選び方には、軽いものから順に、4つの段階があります。表は3列で4行です。列は、段階、やり方、節です。

1行目の段階は、名前で選ぶことです。やり方は、MlpPolicy、CnnPolicy、MultiInputPolicy の名前を渡すことで、14-2節で扱います。

2行目の段階は、層の数、大きさ、活性化関数を変えることです。やり方は、policy_kwargs に、net_arch と activation_fn を入れた辞書を渡すことで、14-3節で扱います。

3行目の段階は、観測を受け取る部分を、自分で書いた NN にすることです。やり方は、policy_kwargs に、features_extractor_class を入れた辞書を渡すことで、14-4節で扱います。

4行目の段階は、記憶を持つ NN、つまり LSTM を使うことです。やり方は、sb3-contrib の RecurrentPPO を使うことで、アルゴリズムが PPO になります。14-5節で扱います。

### 14-2. 名前で選べる3種類

SB3 の SAC が、名前で受け付けるのは、3つです。SB3 2.9.0 のソースの、SAC の policy_aliases で確かめた、とあります。名前の違いは、観測を受け取る最初の部分、つまり特徴の抽出器の違いで、その後ろの全結合の層は、どれも同じです。

表は3列で3行です。列は、名前、観測を受け取る部分、向いている観測です。

1行目は、MlpPolicy です。観測を受け取る部分は、観測をそのまま1列に並べるもので、FlattenExtractor です。フェーズ7-0 の5節の表示の、features_extractor です。向いている観測は、数の並びで、フェーズ7 のすべての環境が、これにあたります。

2行目は、CnnPolicy です。観測を受け取る部分は、畳み込みの NN、つまり NatureCNN で、画像を、特徴の数の並びにします。向いている観測は、カメラの画像です。

3行目は、MultiInputPolicy です。観測を受け取る部分は、観測の項目、つまり辞書の項目ごとに特徴を作り、つなげるもので、CombinedExtractor です。向いている観測は、画像と数の組み合わせなどです。

PPO や TD3 など、ほかのアルゴリズムも、同じ3つの名前を持っています。ただし、名前が同じでも、既定の層の大きさと活性化関数は、アルゴリズムごとに違います。PPO は、64個の層が2つで、tanh です。TD3 は、400個と300個の層で、ReLU です。SB3 2.9.0 のソースで確かめた、とあります。名前にない形の NN を使うには、14-3節や14-4節のように、policy_kwargs で指定します。

### 14-3. 層の数、大きさ、活性化関数を変える、policy_kwargs

policy_kwargs は、方策の NN を作るときに渡す、設定の辞書です。SAC の MlpPolicy の既定は、net_arch が、256 と256 のリスト、つまり256個の数を持つ層が2つで、activation_fn が、nn の ReLU です。SB3 2.9.0 のソースで確かめた、とあります。

2つの項目があります。

1つ目は、net_arch です。層ごとの数を、リストで並べます。64 と64 のリストなら、64個の層が2つになります。リストで書くと、方策、つまり actor と、critic の両方に、同じ形を使います。critic は、行動の良さの見積もりです。pi と qf の2つの項目を持つ辞書で書けば、方策の pi と、critic の qf で、形を分けられます。たとえば、pi を64 と64、qf を256 と256 にします。

2つ目は、activation_fn です。層の間に挟む関数、つまり活性化関数を、PyTorch のクラスで渡します。nn の Tanh なら、ReLU の代わりに tanh を使います。

形を変えて、学習はせずに、NN の形だけを表示してみます。14-4節の、自作の特徴の抽出器も、同じスクリプトで確かめます。ファイルは、ホームの rl_practice の policy_shapes.py です。

スクリプトの構成を説明します。先頭で、gymnasium、PyTorch の nn、SB3 の SAC と、特徴の抽出器の元になる BaseFeaturesExtractor を読み込みます。

次に、自作の特徴の抽出器のクラス、SmallExtractor を書きます。観測を、全結合の層1つで、features_dim 個の特徴にするものです。features_dim の既定は16 です。__init__ で、観測の数から features_dim 個への Linear と、ReLU を並べた層を作り、forward で、観測の束を、その層に通して返します。このクラスの中身は、14-4節で読みます。

その後、Pendulum-v1 の環境を作り、3通りの形で SAC を作って、それぞれ、見出しの1行と、NN の形を表示します。

1つ目は、net_arch を64 と64 にし、activation_fn を nn の Tanh にした形です。方策の、latent_pi を表示します。

2つ目は、net_arch を、方策の pi が64 と64、critic の qf が256 と256 の辞書にした形です。方策の latent_pi と、critic の qf0 を表示します。

3つ目は、features_extractor_class に、SmallExtractor を渡した形です。方策の features_extractor と、latent_pi の最初の層を表示します。

フェーズ7-0 の3節と同じく、練習用のフォルダで、仮想環境を有効にしてから実行します。ホームの rl_practice のフォルダに移り、source で、ホームの rl_venv の bin の activate を読み込んで、python で policy_shapes.py を実行します。

期待する結果を説明します。表示は、見出しの付いた3つの塊です。1つ目の塊には、Sequential が1つあり、中に4つの部品が、番号付きで並びます。2つ目の塊には、Sequential が2つあり、中に、4つと5つの部品が並びます。3つ目の塊には、SmallExtractor があり、その中の net という Sequential に、2つの部品が並びます。その後に、Linear が1行あります。

中身を説明します。Linear の部品には、入口の数の in_features と、出口の数の out_features が表示されます。どの Linear も、bias は True です。

1つ目の塊は、Linear の3から64、Tanh、Linear の64から64、Tanh です。

2つ目の塊の、1つ目の Sequential は、Linear の3から64、ReLU、Linear の64から64、ReLU です。2つ目の Sequential は、Linear の4から256、ReLU、Linear の256から256、ReLU、Linear の256から1 です。

3つ目の塊の、SmallExtractor の中は、Linear の3から16 と、ReLU です。その後の1行は、Linear の16から256 です。

表示の読み方は、3つです。

1つ目。1つ目の塊は、フェーズ7-0 の5節の latent_pi と比べると、256 が64 に、ReLU が Tanh に変わっています。入口の3は、観測の数で、SB3 が環境から決めるので、net_arch には書きません。

2つ目。2つ目の塊の1つ目は方策で、64個の層になっています。2つ目は critic で、256個の層のままです。critic の入口が4 なのは、観測3つに行動1つを足したものを受け取り、その観測でその行動をとったときの良さを、1つの数、つまり最後の出口の1 で見積もるからです。SAC は、critic を2つ、つまり qf0 と qf1 を持ち、見積もりの小さいほうを使って、見積もりが甘くなるのを防ぎます。

3つ目。3つ目の塊は、14-4節で読みます。

層を小さくすると、1回の計算は軽くなりますが、表せる関数の幅が狭くなります。大きくすると、その逆になります。どちらが良いかは、題材と学習の時間で変わります。

比べてみる方法が書かれています。フェーズ7-0 の4-2節のスクリプトを写し、保存する名前、つまり model.save の引数を変えます。そのままでは、フェーズ7-0 の5節と6節が読み込む、sac_pendulum.zip を上書きするためです。それから、SAC を作るところに policy_kwargs を足して、報酬の平均、つまり ep_rew_mean と評価の結果を比べてみるとよい、とあります。

比べるときは、学習の乱数の種、つまり seed を同じにし、できれば種を変えて、何回か学習させます。同じ設定でも、種を変えるだけで結果が大きく違うことがあり、1回ずつの比較では、良し悪しを取り違えやすいためです。フェーズ7-4 の6節にあります。

### 14-4. 観測を受け取る部分を、自分で書いた NN にする

14-3節のスクリプトの SmallExtractor は、BaseFeaturesExtractor を継承した、PyTorch の NN のクラスです。policy_kwargs に、features_extractor_class を SmallExtractor にした辞書を渡すと、FlattenExtractor の代わりに、観測を受け取る最初の部分になります。

2つの点があります。

1つ目。__init__ では、親クラスの __init__ に、observation_space と features_dim を渡して、出口の数、つまり features_dim を SB3 に知らせ、層を作ります。

2つ目。forward では、観測の束から、特徴の束を計算して返します。束になっているのは、学習のときに、記録した多くの観測を、まとめて計算するからです。

3つ目の塊の表示のとおり、観測3つが16個の特徴になり、その後ろの全結合の層、つまり latent_pi の入口が16 になります。features_dim を変えるときは、policy_kwargs に、features_extractor_class と一緒に、features_extractor_kwargs として、features_dim を、たとえば32 にした辞書を渡します。SAC の既定では、方策と critic は、特徴の抽出器を別々に持ちます。share_features_extractor が False です。

この形は、観測に画像や時系列が含まれ、数を並べるだけでは扱いにくいときに使います。フェーズ7 の環境の観測は数個の数なので、MlpPolicy のままで足ります。

全結合の層の部分まで自分で書きたい場合は、SAC の方策のクラス、つまり stable_baselines3 の sac の policies の SACPolicy を継承したクラスを作ります。そして、名前の代わりに、SAC に MyPolicy のようなクラスを渡します。こちらは SB3 の内部の作りに合わせる必要があるので、まずは policy_kwargs で済むかを考える、とあります。

### 14-5. 記憶を持つ NN、LSTM を使う

フェーズ7-1 の2-2節で見たとおり、MlpPolicy は、その時点の観測だけから行動を決め、記憶を持ちません。そこでフェーズ7-1 では、記憶の代わりの手がかりとして、前回のペダルを観測に入れました。NN そのものに記憶を持たせる方法として、LSTM を使う方策があります。LSTM は、前の時刻の内部の状態を、次の時刻に引き継ぐ層です。

4つの点があります。

1つ目。SB3 の本体には、LSTM の方策はありません。SAC に MlpLstmPolicy を渡すと、ValueError という種類のエラーで止まります。エラーの内容は、MlpLstmPolicy という方策は知らない、というものです。この資料を作ったときに確かめた、とあります。

2つ目。追加の部品集の sb3-contrib の RecurrentPPO に、MlpLstmPolicy、CnnLstmPolicy、MultiInputLstmPolicy があります。sb3-contrib は、強化学習のライブラリの環境構築の4節で、導入済みです。sb3-contrib 2.9.0 のソースで確かめた、とあります。

3つ目。アルゴリズムは、SAC ではなく PPO になります。既定の活性化関数も tanh で、LSTM の層は256個の数を持ちます。sb3-contrib 2.9.0 のソースで確かめた、とあります。PPO は、SAC と違い、集めた経験を、その場の学習にだけ使って捨てる作りなので、一般に、同じ成績に届くまでに、環境とのやり取りが多く要ります。

4つ目。predict では、内部の状態を受け取って、次の呼び出しに渡します。model の predict に、obs と一緒に、state と episode_start を渡す形です。エピソードの切れ目で、状態を初めに戻す必要があり、MlpPolicy より、使い方が少し込み入ります。

この資料では、RecurrentPPO でフェーズ7 の環境を学習させてはいない、とあります。フェーズ7-4 の5-2節の末尾の、NN の方策を改良する手がかりの1つです。

### 14-6. 学習済みの NN を読み込む、持ち出すときの注意

2つの注意があります。

1つ目。SAC.load が読めるのは、SB3 で保存した .zip のファイルだけです。PyTorch で別に作った NN の重みを使うには、14-3節や14-4節の方法で、SB3 の方策の中に同じ形の NN を作り、PyTorch の load_state_dict などで、重みを写します。他の人から受け取った .zip のファイルを読み込まない理由、つまり pickle の危険は、フェーズ7-4 の2-2節にあります。

2つ目。形を変えたら、持ち出す側も合わせます。フェーズ7-4 の4-2節の NpzPolicy は、層の数と大きさは .npz のファイルの中身に合わせて変わりますが、中間の層の活性化関数を、ReLU と決め打ちしています。np の maximum で、0.0 との大きいほうをとる書き方です。activation_fn を nn の Tanh にして学習させた重みを、そのまま使うと、エラーは出ずに、違う関数として計算してしまいます。

また、フェーズ7-4 の3-1節の export_policy は、latent_pi と mu の層だけを書き出すので、14-4節の自作の特徴の抽出器の重みは、書き出されません。アルゴリズムを、PPO や RecurrentPPO などに変えた場合も、activation_fn を指定しなくても、既定が tanh になります。方策の層の名前も違い、PPO では、latent_pi と mu の代わりに、mlp_extractor の policy_net と、action_net です。そのため、export_policy と NpzPolicy は、そのままでは使えません。形やアルゴリズムを変えるときは、書き出しと計算のコードも合わせて直し、SB3 の predict と同じ行動になるかを確かめます。
