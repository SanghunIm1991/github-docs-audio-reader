# Tips集 1: シミュレーション時刻、use_sim_time（聞くための原稿）

これは、ros2MinimalPhysicalAi という教材の、Tips集の1つ目の項目です。

Tips集は、手順書、つまりフェーズの本文に入れると流れが途切れる、分量の少ない補足をまとめた資料です。どの項目も独立しているので、関係する手順書を読んでいるときや、疑問を持ったときに、その項目だけを読めばよい、とあります。

対象は、ROS2 Jazzy と Ubuntu 24.04 です。版に依存する記述は、この資料を作ったときに、/opt/ros/jazzy と Ubuntu のパッケージに入っていたもので確かめた、とあります。所要の目安は、1項目あたり5 から15分の読み物です。

この項目に関係する手順書は、4つです。フェーズ1 のパラメータの一覧、フェーズ3-1 の時刻の取り方、フェーズ5-0 の Gazebo、フェーズ5-4 の Gazebo の物理と閉ループです。

出どころについて、断りがあります。内容は、/opt/ros/jazzy のソース、つまり rclpy と rclcpp などを読んで確かめ、自分の言葉で書いたもので、ソースやドキュメントの転載ではない、とあります。1-4節の、ノードを起動した後の表示は、ROS2 の仕様から想定したもの、とあります。

この原稿では、コマンドの表示を書き写さずに、何が表示されるかを言葉で説明します。

## 1. シミュレーション時刻（use_sim_time）

読める時期について、囲みがあります。フェーズ1 やフェーズ3-1 の時点では、1-1節の最初の段落、つまり2つの時計の話と、1-4節の切り替え方、1-5節の気をつける点だけを読めばよい、とあります。1-4節の例はフェーズ3-1 の talker を使うので、試すのはフェーズ3-1 の後です。1-1節の2つ目の段落、つまりフェーズ5-0 の Gazebo の話をする段落と、1-2節、1-3節は、Gazebo、つまりフェーズ5-0 や、PI 制御、つまりフェーズ5-2 を前提にしているので、フェーズ5-0 を済ませた後に読むと分かりやすい、とあります。

### 1-1. 時計が2つある

フェーズ1 の ros2 param list や、フェーズ3-3 の ros2 param list には、自分で宣言していない use_sim_time というパラメータが並んでいました。これは、ノードの時計を、現実の時刻にするか、シミュレーションの時刻にするかを切り替えるスイッチで、すべてのノードが自動で持っています。Node が作られるときに用意されるもので、参考資料の、Node クラスの構造の2節に書かれています。

2つの時計を説明します。

現実の時刻は、use_sim_time が false のときで、これが既定です。PC の時計そのもので、1秒は現実の1秒です。

シミュレーションの時刻は、use_sim_time が true のときです。シミュレータが、今、シミュレーションの中では何秒か、を知らせてくる時刻です。シミュレータを一時停止すれば止まり、PC が重ければ、現実よりゆっくり進みます。

フェーズ5-0 の2-1節では、Gazebo が一時停止の状態で始まることと、右下の RTF、つまりシミュレーションの時間が現実の何倍の速さで進んでいるかが、100パーセントを下回ることがあることを見ました。このとき、シミュレーションの中の車両は、シミュレーションの時刻で動いています。フェーズ5-0 の3-4節、オドメトリを観察する節で見た header.stamp も、Gazebo を起動してからの、シミュレーションの時刻でした。

### 1-2. なぜ合わせる必要があるのか

制御のノードが現実の時刻で動き、車両がシミュレーションの時刻で動いていると、2つの時計がずれます。例えば RTF が50パーセントのとき、制御のノードが、1秒たったので速度を上げる、と判断しても、シミュレーションの中では、まだ0.5秒しかたっていません。PI 制御の積分のように、経過時間かける値、を足していく計算では、このずれがそのまま誤差になります。一時停止中も制御のノードの時計だけが進み、再生したとたんに大きな指令を出す、ということも起こります。

use_sim_time を true にすると、ノードの時計がシミュレーションの時刻に合うので、PC の速さに関係なく同じ結果になります。記録したデータ、つまり rosbag を再生して、ノードを当時と同じ時刻で動かすときにも、同じ仕組みを使います。

### 1-3. 仕組み: /clock トピック

シミュレーションの時刻は、/clock というトピックで配られます。型は、rosgraph_msgs の msg の Clock です。use_sim_time が true のノードは、このトピックを自動で購読し、届いた時刻を、自分の時計の現在時刻にします。rclpy のソースの time_source.py では、この購読の QoS は best_effort で、depth が1になっています。最新の時刻だけが大事なので、取りこぼしても再送しない、という設定です。

Gazebo の場合、時刻は、まず Gazebo の側の /clock に出ます。フェーズ5-0 の2-1節の、gz topic マイナス l の一覧にあるものです。ROS2 のノードに届けるには、ほかのトピックと同じく、ブリッジが必要です。

ブリッジに渡す1本は、/clock のトピックを、ROS2 の rosgraph_msgs の msg の Clock と、Gazebo の gz.msgs.Clock の間で中継する、という指定です。parameter_bridge の引数にこの1本を足すと、Gazebo の時刻が、ROS2 の /clock に中継されます。2つの型の間の区切りには、開きの角かっこを使います。これは、Gazebo から ROS2 への片方向、という意味で、フェーズ5-0 の3-1節で扱いました。

フェーズ5-0 で使ったデモの diff_drive.launch.py は、3-1節の マイナス2つの print の表示のとおり、cmd_vel と odometry の4本しか中継しておらず、/clock は中継していません。したがって、フェーズ5-0 の課題6、つまり10秒走ったら止まるノードの self.get_clock().now() は、現実の時刻で測っています。フェーズ5-3 の launch も、このデモを取り込むだけなので同じです。制御のループは、Gazebo と関係なく、自作のノードだけで閉じているので、困らない、とあります。Gazebo の物理をプラントにするフェーズ5-4 の5節で、自分の launch のブリッジにこの1本を足し、計算するノードに use_sim_time を渡します。

### 1-4. 切り替え方

実行時に、ほかのパラメータと同じ書き方で渡します。フェーズ3-3 の5-2節の、マイナス p です。launch ファイルでは、ノードに渡すパラメータに、use_sim_time を True にする指定を加えます。フェーズ4 のパラメータの渡し方と同じです。

次の例は、フェーズ3-1 の talker を、シミュレーションの時刻で動かし、別のターミナルで設定を確かめるものです。マイナス2つの ros-args、マイナス p、名前、コロンとイコール、値、という形は、起動するときにパラメータの値を指定する書き方で、ここでは use_sim_time を true にして起動します。詳しくは、フェーズ3-3 の5-2節、起動時に指定する節で扱います。シミュレータは動かしていないので、/clock はどこからも届きません。

コマンドは2つです。T1 で、ros2 run learn_py talker に、マイナス2つの ros-args と、マイナス p で use_sim_time を true にする指定を付けて起動します。T2 で、ros2 param get /talker use_sim_time を実行します。

期待する結果です。T1 には、publish のログが1行も出ません。T2 には、フェーズ1 の ros2 param get と同じ書式で、真偽の値が表示されます。

T2 に表示される値は True で、これは、そのノードの時計が、シミュレーションの時刻を使っていることを示します。T1 にログが出ないのは、壊れたのではありません。/clock が届かないので、時刻が0のまま進まず、ノードの時計で数えるタイマー、つまり Python の create_timer が、一度も発火しないためです。1-5節の表の、/clock が届くまで時刻は0、と、タイマーも時計に従う、の2行に当たります。確かめたら、T1 を Ctrl+C で止めます。

### 1-5. 気をつける点

気をつける点の表は、2列で3行です。列は、気をつける点と、その内容です。

1行目は、/clock が届くまで時刻は0、です。use_sim_time を true にしたのに /clock が来ていないと、now() は0を返し続けます。rclpy の TimeSource は、最後に受け取った時刻を覚えておく変数を、0で始めるからです。時刻が0のままなら、ブリッジに /clock を足したか、シミュレータが一時停止していないかを確かめます。

2行目は、タイマーも時計に従う、です。Python の create_timer と、C++ の create_timer は、ノードの時計で数えます。シミュレーションの時刻を使うと、一時停止中はタイマーも止まります。C++ の create_wall_timer、つまりフェーズ3-1 の C++ の版で使ったものは、名前のとおり、常に現実の時刻で数えます。

3行目は、ノードごとにそろえる、です。一部のノードだけ true にすると、ノードによって時刻の基準が違うメッセージが混ざります。シミュレーションに関わるノードは、全部そろえます。launch でまとめて起動すると、そろえやすい、とあります。
