# Tips集 13: bag の記録を、トピックごとの CSV に書き出す（聞くための原稿）

これは、ros2MinimalPhysicalAi という教材の、Tips集の13個目の項目です。

Tips集は、手順書、つまりフェーズの本文に入れると流れが途切れる、分量の少ない補足をまとめた資料です。どの項目も独立しているので、関係する手順書を読んでいるときや、疑問を持ったときに、その項目だけを読めばよい、とあります。

対象は、ROS2 Jazzy と Ubuntu 24.04 です。版に依存する記述は、この資料を作ったときに、/opt/ros/jazzy と Ubuntu のパッケージに入っていたもので確かめた、とあります。所要の目安は、1項目あたり5 から15分の読み物です。

この項目に関係する手順書は、2つです。ros2 bag の記録を扱うフェーズ6-1 と、記録の解析を扱うフェーズ6-3 です。

出どころについて、断りがあります。この資料の内容は、/opt/ros/jazzy のソースなどを読んで確かめ、自分の言葉で書いたもので、ソースやドキュメントの転載ではない、とあります。

13節については、次のようにあります。ros2 bag のサブコマンドと、ros2 topic echo の、マイナス2つの csv と、マイナス i の意味は、手元の、マイナス2つの help の表示で確かめた、とあります。rosbag2_py と rosidl_runtime_py が入っていることは、/opt/ros/jazzy で確かめた、とあります。13-3節のサンプルは、自分で書いたもので、入れ子の型、つまり nav_msgs の msg の Odometry の書き出しも、練習用の記録で確かめた、とあります。2026年10月16日のことです。

期待する結果についても、断りがあります。13-2節と13-3節の表示と、CSV の中身は、この資料を作ったときに、rosbag2_py で練習用の短い記録を作り、使い捨ての環境で、実際に再生と書き出しをして確かめたもの、とあります。練習用の記録は、std_msgs の msg の Float64 のトピック3つを記録したものです。13-2節は、ほかの PC と混ざらない設定で、ros2 bag play と ros2 topic echo を起動した、とあります。フェーズ6-1 の記録そのものでは、確かめていない、とあります。

この原稿では、コマンドとスクリプトと表示を書き写さずに、何を書き、何が表示されるかを言葉で説明します。

## 13. bag の記録を、トピックごとの CSV に書き出す

### 13-1. 疑問: 記録した時系列を、表計算ソフトや Python で扱いたい

フェーズ6-1 では、ros2 bag で記録した値を、ros2 bag play で再生して、rqt_plot で見直しました。値を表計算ソフトで並べたり、自分の Python のスクリプトで細かく計算したりするには、トピックごとの時系列を、CSV にしておくと扱いやすいです。CSV は、値をコンマで区切って、1行ずつ並べたテキストのファイルです。

ところが、ros2 bag には、CSV に書き出すコマンドはありません。Jazzy の ros2 bag のサブコマンドは、burst、convert、info、list、play、record、reindex の7つです。このうち convert も、記録の保存の形式や分け方を変えるもので、CSV には直せません。保存の形式とは、MCAP などのことで、フェーズ6-1 の2-2節にあります。

Jazzy に標準で入っているものだけで済ませるなら、CSV にするには、2つの方法があります。PlotJuggler のような、ROS2 の外の道具を使う方法もありますが、この教材では扱わない、とあります。

表は4列で2行です。列は、方法、やり方、時刻、向く場面です。

1行目は、方法1で、13-2節で扱います。やり方は、記録を再生し、ros2 topic echo に、マイナス2つの csv を付けて受けて、ファイルに保存することです。時刻は、再生したときの時刻です。向く場面は、コードを書かずに、手早く中身を見たいときです。

2行目は、方法2で、13-3節で扱います。やり方は、記録のファイルを、Python のライブラリの rosbag2_py で直接読んで、CSV に書くことです。時刻は、記録したときの時刻です。向く場面は、取りこぼしなく、再生の速さに左右されずに残したいときです。

### 13-2. 方法1: 再生しながら、ros2 topic echo に マイナス2つの csv を付けて受ける

ros2 topic echo に、マイナス2つの csv を付けると、メッセージの項目を、コンマで区切った1行で表示します。マイナス i も付けると、各行の先頭に、メッセージの時刻などの情報が付きます。マイナス i は、マイナス2つの include-message-info の短い形です。std_msgs の msg の Float64 には、時刻の項目がないので、時系列として残すには、マイナス i が要ります。

表示を、大なりの記号でファイルに保存しておき、別のターミナルで、フェーズ6-1 の4-5節で取った記録の sim_default を再生します。受ける側の T1 と T2 を先に起動してから、再生の T3 を始めます。

コマンドを説明します。3つのターミナルとも、ホームの ros2_ws の bags のフォルダで作業します。T1 では、ros2 topic echo に、マイナス2つの csv と、マイナス i を付け、トピックの /plant/velocity と、型の std_msgs の msg の Float64 を渡し、表示を、大なりの記号で velocity.csv に保存します。T2 では、同じ形で、トピックを /plant/pedal にし、pedal.csv に保存します。T3 では、ros2 bag play で sim_default を再生します。

T3 の再生が終わったら、T1 と T2 を、Ctrl+C で止めます。最後の引数の型を付けているのは、再生が始まる前でも、受ける側が型を決められるようにするためです。

期待する結果は、velocity.csv の中身の先頭です。練習用の短い記録を再生した場合のもので、時刻は実行ごとに変わります。3行で、どの行も、コンマで区切った5つの値が並びます。

1行が1つのメッセージです。列の表は、2列で5行です。列は、列の番号と、中身です。

1行目は、1列目で、送った時刻です。UNIX 時刻を、ナノ秒の単位で表した数です。UNIX 時刻は、1970年1月1日0時、UTC からの経過時間で、ナノ秒は10億分の1秒です。

2行目は、2列目で、受け取った時刻です。表し方は、1列目と同じです。

3行目は、3列目で、送った側の通し番号です。

4行目は、4列目で、受け取った側の通し番号です。この資料を作ったときの環境、つまり Fast DDS では、None だった、とあります。

5行目は、5列目以降で、メッセージの項目です。Float64 なら、data の1列です。

例の3行では、1列目と2列目が、ナノ秒の大きな数です。3列目の送った側の通し番号は、1、2、3。4列目は、どの行も None。5列目の data は、0.0、0.5、1.0 です。

1列目の差を見ると、記録したときと同じ間隔で流れていることが分かります。この例では0.02秒です。フェーズ6-1 の sim_default の /plant/velocity なら、0.01秒です。マイナス i を付けないと、5列目以降の値だけが並びます。この資料を作ったときに、/plant/pedal を、マイナス i なしで受けて確かめた、とあります。

この方法には、3つの注意があります。

1つ目。時刻は、記録した時刻ではなく、再生した時刻です。たとえば、ros2 bag play に、マイナス r 5 を付けて、速く再生すると、時刻の間隔も5分の1に詰まります。

2つ目。列の名前の行、つまりヘッダは出ません。表計算ソフトで使うときは、自分で1行目に足します。

3つ目。受ける側がつながる前に流れた分は、取りこぼします。受ける側を先に起動しておきますが、それでも、再生が始まってから相手を見つけるまでの間に、最初のいくつかが欠けることがあります。確実にするには、フェーズ6-3 の6-1節のようにします。ros2 bag play に、マイナス p を付けて、一時停止の状態で再生を始めます。別のターミナルで、ros2 topic info に /plant/velocity を渡して実行し、Subscription count が、受ける側の数になったのを確かめます。それから、T3 でスペースキーを押して、再生を進めます。

### 13-3. 方法2: 記録のファイルを、Python で直接読む

Jazzy には、bag のファイルを読み書きする、Python のライブラリの rosbag2_py が入っています。ROS2 の標準の Python、つまり python3 で使えるので、追加で入れるものはありません。このライブラリで、記録を先頭から順に読み、トピックごとの CSV のファイルに書くスクリプトを作ります。ファイルは、ros2_ws の bags のフォルダの、bag_to_csv.py です。

スクリプトの構成を説明します。先頭で、標準の csv などと、rosbag2_py、rclpy、rosidl_runtime_py の部品を読み込みます。その後に、2つの関数があります。

1つ目の関数は、flatten です。値が辞書なら、項目ごとに、それまでの名前の後ろに、項目の名前とドットを足して、自分自身を呼び直します。辞書でなければ、最後のドットを除いた名前と、値の組を返します。flatten の役割は、後の解説の3つ目で述べます。

2つ目の関数は、main です。引数で受け取った bag を読み、bag の名前の後に、アンダースコアと csv を付けたフォルダの下に、トピックごとの CSV を書きます。流れは4つです。

1つ目。後の解説の1つ目の部品で、bag を開きます。このとき、保存の場所と、変換の設定に cdr を2つ渡します。記録に含まれる、トピックの名前と型の名前の対応を、辞書にしておきます。

2つ目。書き出し先のフォルダを作り、記録が続く間、1件ずつ読みます。読んだものは、後の解説の2つ目と3つ目の部品で、名前と値の並びにします。

3つ目。そのトピックが初めて出てきたときは、CSV のファイルを開き、1行目に、time と、項目の名前を並べて書きます。その後は、1件ごとに、時刻と値を1行で書き、行の数を数えます。

4つ目。読み終わったら、ファイルを閉じ、トピックごとに、何行を、どのファイルに書いたかを表示します。

原文の解説は、4つです。

1つ目は、SequentialReader です。bag を、記録した順に1件ずつ読む部品です。read_next は、トピックの名前、メッセージの中身、記録した時刻の3つを返します。メッセージの中身は、送るときの形のバイト列で、記録した時刻はナノ秒です。

2つ目は、deserialize_message です。バイト列を、型に合わせて、Python のメッセージに戻します。型は、get_message で、std_msgs の msg の Float64 のような型の名前から取り出します。

3つ目は、message_to_ordereddict と flatten です。メッセージを、項目の名前と値の辞書にし、入れ子の項目を、twist.twist.linear.x のような、1つの名前の列に並べ直します。どの型のトピックでも、同じスクリプトで書き出せます。ただし、配列の項目は分けずに、1つのセルに入ります。この節の末尾の段落で述べます。

4つ目は、時刻の列です。記録全体の最初のメッセージを0秒として、記録した時刻を秒で、小数第3位、つまりミリ秒まで書きます。どのトピックの CSV も同じ基準なので、target_velocity.csv が0.000 から始まるとは限りません。再生しないので、取りこぼしも、再生の速さによるずれもありません。ただし、記録した時刻は PC の時計なので、PC の時計が飛ぶ環境では、その分だけ間があきます。フェーズ6-1 の2-2節にあります。

フェーズ6-1 の記録の sim_default を書き出します。ROS2 を読み込んだターミナルで実行します。自分で定義した型のトピックを含む記録なら、ホームの ros2_ws の install の setup.bash も、source しておきます。コマンドは、ホームの ros2_ws の bags のフォルダで、python3 に、bag_to_csv.py と sim_default を渡して実行するものです。

期待する結果は、練習用の短い記録の場合のものです。フェーズ6-1 の記録では、行の数がずっと多く、トピックの順は記録によって変わる、とあります。表示は3行で、トピックごとに1行です。各行には、トピックの名前、書いた行の数、矢印、書き出したファイルの場所が並びます。

表示の中身を説明します。/plant/velocity は5行で、sim_default_csv のフォルダの plant__velocity.csv に書かれます。/plant/pedal は5行で、plant__pedal.csv に書かれます。/target_velocity は1行で、target_velocity.csv に書かれます。

記録のフォルダの隣に、sim_default_csv のフォルダができ、トピックごとの CSV が入ります。ファイルの名前は、トピックの名前のスラッシュを、アンダースコア2つに直したものです。

中身は、1行目が列の名前で、2行目から値が並びます。plant__velocity.csv の先頭の例は、3行です。1行目は列の名前で、time と data です。2行目は、time が0.000 で、data が0.0 です。3行目は、time が0.020 で、data が0.5 です。

nav_msgs の msg の Odometry のような入れ子の型は、header.stamp.sec や pose.pose.position.x のように、項目ごとの列に分かれます。共分散のような配列の項目は、分けずに、角かっこで囲んだ値の並びの形で、1つのセルに入ります。メッセージの配列、つまり入れ子の型の並びも、同じく1つのセルに入り、画像のような大きな配列は、とても大きなセルになります。

### 13-4. どちらを使うか

手早く中身を見たいだけなら、方法1で足ります。記録を後で解析するなら、取りこぼしがなく、再生の速さにも左右されない方法2が向きます。

フェーズ6-3 の解析のノード、つまり metrics は、再生した値をノードで受けて計算する作りで、方法1と同じく、再生の仕組みに乗っています。方法2の形にすれば、同じ計算を、再生を待たずに、記録のファイルから直接行えます。そのときも、時刻は time の列でなく、フェーズ6-3 の3節と同じく、行の番号に、プラントの周期を掛けて数えます。PC の時計の飛びの影響を受けないためです。
