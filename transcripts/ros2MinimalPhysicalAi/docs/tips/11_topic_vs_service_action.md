# Tips集 11: トピックの組み合わせで、サービス・アクションの代わりになるか（聞くための原稿）

これは、ros2MinimalPhysicalAi という教材の、Tips集の11個目の項目です。

Tips集は、手順書、つまりフェーズの本文に入れると流れが途切れる、分量の少ない補足をまとめた資料です。どの項目も独立しているので、関係する手順書を読んでいるときや、疑問を持ったときに、その項目だけを読めばよい、とあります。

対象は、ROS2 Jazzy と Ubuntu 24.04 です。版に依存する記述は、この資料を作ったときに、/opt/ros/jazzy と Ubuntu のパッケージに入っていたもので確かめた、とあります。所要の目安は、1項目あたり5 から15分の読み物です。

この項目に関係する手順書は、2つです。フェーズ3-4 のサービスと、フェーズ3-5 のアクションです。

出どころについて、断りがあります。この資料の内容は、/opt/ros/jazzy のソースなどを読んで確かめ、自分の言葉で書いたもので、ソースやドキュメントの転載ではない、とあります。

11節のサービスとアクションの中身は、Jazzy の次のソースなどで確かめた、とあります。rcl_action では、アクションが作る5つの名前と、結果を持つ時間の既定値。rclpy では、隠れた名前の決まり、result_timeout の既定値、wait_for_service などの関数。rmw では、要求の識別子の中身と、サービスの既定の QoS。action_msgs では、ゴールの状態です。そして、rmw_fastrtps_shared_cpp の共有ライブラリに含まれる、名前の頭の文字列、つまり rq、rr、rt です。2026年10月15日のことです。

確かめていないことも書かれています。トピックで組んだ場合との比べは、これらの仕組みから自分の言葉でまとめたもので、実際にトピックで組んで比べてはいない、とあります。要求の識別子で応答を振り分ける処理そのものは、RMW のソースを読んで確かめてはいない、とあります。11-2節の、隠れた名前も含めた一覧に出る名前は、rcl_action と rclpy の仕組みから書いたもので、動かして確かめてはいない、とあります。

## 11. トピックの組み合わせで、サービス・アクションの代わりになるか

### 11-1. 疑問: 配信と購読を2本ずつ組めば、同じことができるのではないか

サービスは、1回の要求に1回の応答を返す通信です。フェーズ3-4 で扱います。アクションは、時間のかかる処理、つまりゴールを頼み、途中経過、つまりフィードバックを受け取りながら、結果を待つ通信です。フェーズ3-5 で扱います。

どちらも、トピックで代わりを作れそうに見えます。たとえば、要求を送るトピックと、応答を返すトピックを1本ずつ用意し、片方のノードが要求を購読して、計算した値を応答のトピックに配信すればよい、という考えです。

この見方は、半分は正しい、とあります。ROS2 のサービスとアクションは、実際に、トピックと同じ仕組みの上に作られています。11-2節で述べます。一方で、トピックだけで組むと、サービスとアクションが引き受けている決まりごとを、自分で全部作り直すことになります。11-3節で述べます。

### 11-2. 中身: サービスもアクションも、トピックの仕組みの上にある

サービスは、DDS の中で、要求用と応答用の、2本のトピックとして実現されています。DDS は、ROS2 の下で通信を受け持つ層で、Tips集の6節にあります。

名前の付け方は、RMW の実装によって違います。RMW は、ROS2 と DDS の間の層で、これも Tips集の6節にあります。Jazzy の既定の Fast DDS では、要求用の名前の頭に rq、応答用の名前の頭に rr を付けます。ふつうの ROS2 のトピックは rt です。これらは、ROS2 の側からはサービスとして見えるので、ros2 topic list には出てきません。

トピックと違うのは、要求ごとに識別子が付くことです。識別子は、2つの組です。1つは、要求を送ったクライアントを表す番号で、送り手の GUID です。GUID は、DDS が送り手ごとに付ける、ほかと重ならない識別子です。もう1つは、そのクライアントの中での通し番号です。識別子は ROS2 が自動で付けます。応答にも同じ識別子が付いて戻り、クライアントの側では、この識別子で、自分の要求への応答だけが取り出されます。

アクションは、3つのサービスと、2つのトピックを組み合わせたものです。アクションの名前が /fibonacci なら、5つの名前が作られます。どれも、/fibonacci の後に、スラッシュで区切って _action、つまりアンダースコアで始まる action を挟み、その後に、それぞれの名前を付けたものです。

表は3列で5行です。列は、名前、種類、役割です。

1行目は、/fibonacci/_action/send_goal です。種類はサービスで、ゴールを送り、受け付けたかどうかの返事をもらいます。

2行目は、/fibonacci/_action/cancel_goal です。種類はサービスで、ゴールの中断を頼みます。

3行目は、/fibonacci/_action/get_result です。種類はサービスで、結果を受け取ります。終わるまで返事が来ません。

4行目は、/fibonacci/_action/feedback です。種類はトピックで、途中経過を流します。

5行目は、/fibonacci/_action/status です。種類はトピックで、各ゴールの状態を流します。状態は、受付、実行中、成功、中断、失敗などです。

名前をスラッシュで区切ったどこかの部分が、アンダースコアで始まる名前は、隠れた名前として扱われ、ふだんの一覧には出ません。ここでは、_action の部分です。ros2 topic list に、マイナス2つの include-hidden-topics を付けると、アクションのサーバかクライアントが動いている間は、feedback と status の2本も、一覧に出るはずだ、とあります。どちらも、サーバが配信し、クライアントが購読します。

ゴールには、UUID のゴール ID が付きます。UUID は、16バイトの、重ならない番号です。フィードバックも、状態も、結果も、この ID で、どのゴールの分かを区別します。

### 11-3. トピックだけで作る場合に、自分で用意するもの

トピックだけで同じことをするなら、次の表の、トピックだけで作る場合の列を、すべて自分で作ることになります。

表は4列で9行です。列は、観点、トピックだけで作る場合、サービス、アクションです。

1行目の観点は、応答をだれに返すかです。トピックだけで作る場合、応答のトピックは、購読しているすべてのノードに届きます。要求に自分の名前と通し番号を入れ、応答にもそれを入れて返し、受け取った側で、自分の分だけを選びます。サービスでは、識別子が自動で付き、要求したクライアントにだけ渡ります。アクションでは、ゴール ID で区別します。複数のゴールを同時に扱えます。

2行目の観点は、相手がいるかです。トピックだけで作る場合、要求のトピックの購読者の数、つまり count_subscribers などで、自分で確かめます。サービスでは、wait_for_service と service_is_ready で確かめられます。アクションでは、wait_for_server と server_is_ready で確かめられます。

3行目の観点は、届かなかったら、です。トピックだけで作る場合、既定の QoS はサービスと同じで、reliable、volatile、keep_last の10件です。volatile は、後から参加した相手に過去の分を渡さない設定なので、相手がつながる前に送った要求は失われます。volatile については、Tips集の4-3節にあります。相手がいることを、自分で確かめてから送ります。サービスでは、既定の QoS はトピックと同じです。サーバが見つかる前の要求も失われうるので、wait_for_service で待ってから呼びます。reliable で送り直せるのは、手元に残している件数の分だけです。これも Tips集の4-3節です。アクションでは、サービスの部分は同じで、wait_for_server で待ってから送ります。

4行目の観点は、応答を待つことです。トピックだけで作る場合、応答の購読のコールバックで受け、待つ仕組みと時間切れを、自分で作ります。サービスでは、call_async が返す Future で待てます。Future は、あとで結果が入る入れ物です。アクションでは、ゴールの受付と結果の、それぞれを Future で待てます。

5行目の観点は、型です。トピックだけで作る場合、要求と応答のメッセージの型を、別々に決めます。サービスでは、1つの .srv のファイルに、要求と応答を組で書きます。アクションでは、1つの .action のファイルに、ゴール、結果、フィードバックを組で書きます。

6行目の観点は、途中経過、中断、状態です。トピックだけで作る場合、状態の移り変わりも含めて、すべて自分で決めます。サービスには、ありません。アクションには、標準の仕組みがあります。状態は、action_msgs の msg の GoalStatus の7種類で、不明の状態、つまり UNKNOWN を含みます。それを除く6つの移り変わりは、フェーズ3-5 の1節の状態遷移図にあります。

7行目の観点は、結果を後から受け取ることです。トピックだけで作る場合、自分で取っておく仕組みを作ります。サービスには、ありません。応答は1回だけです。アクションでは、終わった後も、サーバが決めた時間だけ、結果を持っています。既定は、rclpy で900秒、rclcpp で10秒です。

8行目の観点は、コマンドの道具です。トピックだけで作る場合、ros2 topic pub と ros2 topic echo を、別々に使います。サービスでは、ros2 service call で、要求と応答を1回で確かめられます。アクションでは、ros2 action send_goal に、マイナス2つの feedback を付けて、途中経過まで確かめられます。

9行目の観点は、ほかのパッケージとの組み合わせです。トピックだけで作る場合、自分の決めた形を、相手も知っている必要があります。サービスでは、std_srvs の srv の Trigger などの標準の型で、他人のノードと組み合わせられます。アクションでは、control_msgs の action の FollowJointTrajectory などの標準の型で、他人のノードと組み合わせられます。

### 11-4. サービスとアクションを使う利点

表をまとめると、サービスとアクションを使う利点は、3つです。

1つ目は、決まりごとを作り直さなくてよいことです。応答の宛先の振り分け、相手がいるかの確認、待ち方、途中経過、中断、状態の管理は、どれも自分で作ると、取り違えや抜けが起きやすいです。とくに、クライアントが2つ以上あるときの応答の取り違えや、同時に動くゴールの区別は、テストで見つけにくい、とあります。

2つ目は、ほかの人のノードや道具と組み合わせられることです。標準の型と、標準のやり取りの手順を使えば、自分で書いていないノードとも、そのままつながります。たとえば、2つの例があります。Gazebo の物理の間章の5-4節では、ros2_control のコントローラが用意しているアクション、つまり FollowJointTrajectory に、ros2 action send_goal でゴールを送るだけで、アームを動かしました。フェーズ7-3 では、Gazebo のワールドを操作するサービス、つまりブリッジ経由の ControlWorld を呼んで、物理を、決めた回数、つまり刻みの数だけ進めました。どちらも、相手の中身を知らなくても使えます。ros2 service call や ros2 action send_goal で、コードを書かずに試せるのも、同じ理由です。

3つ目は、読む人に意図が伝わることです。コードやノードの一覧に、サービスやアクションとあれば、1回の頼みごとなのか、時間のかかる仕事なのかが、名前を見ただけで分かります。トピックの組で作ると、どのトピックとどのトピックが組なのかを、コードを読んで探すことになります。

### 11-5. それでもトピックを選ぶ場面

逆に、次のような場面では、サービスやアクションでなく、トピックを使います。3つあります。

1つ目は、データが流れ続けるときです。センサの値や、制御の指令のように、一定の周期で新しい値が来るものは、1回ごとに要求と応答をやり取りすると、往復の待ち時間が、制御の遅れになります。制御の指令の例は、フェーズ5 の /target_velocity と /plant/pedal です。受け手は最新の値だけを使えばよいので、トピックが向きます。

2つ目は、受け手が何人いてもよいときです。トピックは、受け手が増えても、送り手を変えなくてよいです。フェーズ6-1 の ros2 bag record も、受け手の1つとして加わっています。サービスは、1つの要求に1つの応答を返す通信で、受け手、つまりサーバは1つにする前提で使います。同じ名前のサーバを2つ動かすと、どのサーバが要求を受けて応答するかを、呼ぶ側から決められず、動きが分かりにくくなるので、一般的な使い方として避ける、とあります。

3つ目は、返事が要らないときです。この値に変えておいて、で済み、変わったかどうかを確かめる必要がない指令は、トピックで送れば足ります。

なお、サービスとアクションの応答を待つ書き方には、注意がいります。ノードのコールバックの中で、別のサービスの応答を止まって待つと、既定の設定、つまり1つのスレッドで順番に処理する設定では、その応答を受け取る処理が回ってこず、止まったままになります。Tips集の7-4節にあります。待つときは、Future にコールバックを付けて、応答が来たときに続きを処理する形にします。
