# Tips集 7: ROS1 との違いと、ROS1 のコードの移植（聞くための原稿）

これは、ros2MinimalPhysicalAi という教材の、Tips集の7つ目の項目です。

Tips集は、手順書、つまりフェーズの本文に入れると流れが途切れる、分量の少ない補足をまとめた資料です。どの項目も独立しているので、関係する手順書を読んでいるときや、疑問を持ったときに、その項目だけを読めばよい、とあります。

対象は、ROS2 Jazzy と Ubuntu 24.04 です。版に依存する記述は、この資料を作ったときに、/opt/ros/jazzy と Ubuntu のパッケージに入っていたもので確かめた、とあります。所要の目安は、1項目あたり5 から15分の読み物です。

この項目に関係する手順書は、フェーズ0 の1節と、移植の書き換え先としての、フェーズ2 から4 です。

出どころについて、断りがあります。この資料の内容は、/opt/ros/jazzy のソースなどを読んで確かめ、自分の言葉で書いたもので、ソースやドキュメントの転載ではない、とあります。7-1節は、フェーズ0 の本文から移したもので、ROS2 と DDS の公式ページの記載に基づいて書いた、とあります。ページのアドレスは、フェーズ0 の10節にあります。7-2節から7-4節、つまり ROS1 のコードの移植は、ROS2 の公式の移植のガイド、つまり GitHub の ros2_documentation の jazzy ブランチの原稿と、ros1_bridge の README を読んで、要点を自分の言葉でまとめた、とあります。tf のパッケージが無いことは /opt/ros/jazzy の share のフォルダで、ament_python の雛形に buildtool_depend の要素が無いことは ros2pkg のソースで確かめた、とあります。フィールドの名前の決まり、Header の中身、rclpy と rclcpp の Rate の作り、set_parameter を、どこで確かめたかは、本文の中で述べています。ROS1 の .bag のファイルが、ros2 bag で直接は再生できないことは、一般的な情報から書いたもので、確かめていない、とあります。また、ROS1 のコードを実際に移植して動かしてはいない、とあります。ここまでは、2026年10月15日の時点のものです。

## 7. ROS1 との違いと、ROS1 のコードの移植

### 7-1. 違いの要点

ROS2 は、初代の ROS、つまり ROS1 を作り直したものです。古い記事やサンプルには ROS1 向けのものが多いので、読み分けるために、違いの要点を知っておくと役に立ちます。

ROS1 では、roscore、つまりマスターという中央のプロセスが、ノードの名前の取りまとめを担い、通信には、ROS 独自の規約の TCPROS と XMLRPC を使っていました。マスターが止まると、新しい接続が作れなくなり、複数台のロボットの構成、セキュリティ、リアルタイム制御には、別の工夫が必要でした。

ROS2 は、この反省から、通信の層に業界標準の DDS を採用し、中央の管理者がいない分散型の構成に作り直されました。DDS は、Tips集の6節で扱っています。リアルタイム制御、組み込み機器、複数台のロボット、セキュリティを、最初から考えに入れた設計になっています。

ROS1 の最後の版、Noetic のサポートは、2025年5月に終了しており、今の新規開発は ROS2 が前提です。記事やサンプルが、roscore、rosrun、catkin_make を使っていたら、ROS1 向けと見分けられます。ROS2 では、ros2 run と colcon build を使います。

### 7-2. 移植する前に決めること

ROS1 で作られたパッケージ、つまりレガシーコードを、ROS2 で使いたいときは、ROS2 のパッケージとして書き直す、つまり移植することになります。ROS1 と ROS2 は、ビルドの仕組みも、ノードを書くライブラリも別物です。ライブラリは、ROS1 では rospy と roscpp、ROS2 では rclpy と rclcpp です。ROS1 のコードは、そのままではビルドも実行もできません。手を付ける前に、次の3つを確かめておきます。

1つ目は、依存するものが、ROS2 にそろっているかです。移植するパッケージが使うパッケージ、つまりメッセージの型、ライブラリ、ドライバが、ROS2 の版、この教材では Jazzy に、すべてそろっていないと、移植は終わりません。ROS2 で名前が変わったものや、ROS2 には無いものもあります。例えば、座標変換の古い tf パッケージです。ROS2 には、後継の tf2 だけがあります。そこで、package.xml の依存を1つずつ、ROS2 の側にあるか調べます。足りないものがあれば、それを先に移植するか、代わりを探します。

2つ目は、書き直すか、構造を保って写すかです。コードの構造をなるべく保って、ROS2 の API へ置き換えていく方法と、同じ機能を ROS2 の流儀で一から書き直す方法があります。小さなノードなら、7-3節の対応表を見ながら置き換えるほうが早い、とあります。設計が ROS1 の仕組み、例えば7-4節で扱うグローバルなパラメータや、同期のサービスの呼び出しに強く依存しているなら、書き直したほうが、後で困らない、とあります。

3つ目は、ROS1 と並べて動かせるかです。ROS1 と ROS2 の間でトピックを中継する ros1_bridge を使えば、一部のノードだけを先に移植して、残りを ROS1 のまま動かす、という段階的な移植ができます。ただし、ROS1 の最後の版の Noetic は Ubuntu 20.04 向けで、Ubuntu 24.04 には ROS1 がありません。そのため、Jazzy は、ros1_bridge の公式の対応から外れています。ros1_bridge の README の対応表で、Ubuntu 24.04 と Jazzy は対象外で、apt にも Jazzy 向けのパッケージがありません。この教材の環境では、パッケージを丸ごと移植してから動かすことになります。

ライセンスは、移植しても、元のパッケージのものを引き継ぎます。公式の移植のガイドも、そう勧めている、とあります。移植したコードは、元のコードの改変にあたるので、著作権の表示を残すなど、元のライセンスの条件に従います。

移植の順番は、依存される側から進めます。複数のパッケージがあるなら、まず、メッセージの型だけを持つパッケージ、つまりインターフェースのパッケージ、次にライブラリ、次にノード、最後に launch ファイルとパラメータのファイル、の順に移します。そうすると、移した部品から順に、ビルドして確かめられます。

### 7-3. 書き換える場所の対応表

主な置き換え先は、次のとおりです。ROS1 の欄は、古い記事やコードで見かける書き方です。

表は3列で18行です。列は、対象と、ROS1 と、ROS2 です。

1行目は、ビルドです。ROS1 は、catkin_make と catkin build で、devel のフォルダができます。ROS2 は、colcon build で、install のフォルダができます。devel に当たるものはありません。

2行目は、package.xml です。ROS1 では、形式1 も使われていて、buildtool_depend の要素に catkin を書きます。ROS2 は、形式2 以上です。C++ は、buildtool_depend の要素に ament_cmake を書き、export の中の build_type の要素にも ament_cmake を書きます。Python は、export の中の build_type の要素に ament_python を書くだけです。ros2 pkg create の雛形のとおりです。

3行目は、C++ の CMakeLists.txt です。ROS1 は、find_package で catkin と、その COMPONENTS を探し、catkin_package を呼び、ドル記号と中かっこで catkin_LIBRARIES を囲んだものを使います。ROS2 は、依存ごとの find_package と、末尾の ament_package、それにターゲットにリンクする書き方です。この書き方は、Tips集の2節で扱っています。

4行目は、Python のパッケージです。ROS1 は、CMakeLists.txt と setup.py で、catkin を経由します。ROS2 は、ament_python の setup.py と setup.cfg です。setup.cfg は、Tips集の10節で扱っています。Python だけなら、CMakeLists.txt は要りません。Python 3 が前提です。

5行目は、メッセージの型の生成です。ROS1 は、add_message_files と generate_messages です。ROS2 は、rosidl_generate_interfaces です。型は、ament_cmake のパッケージ、つまり CMakeLists.txt のあるパッケージでしか作れません。C++ のコードは無くて構いません。そのため、Python だけのパッケージに型があったら、型だけのパッケージに分けます。

6行目は、ノードを作る、の Python です。ROS1 は、rospy.init_node に名前を渡します。ROS2 は、rclpy.init の後、Node を継承したクラスを作ります。フェーズ3-1 で扱っています。

7行目は、ノードを作る、の C++ です。ROS1 は、ros::init と ros::NodeHandle です。ROS2 は、rclcpp::init と、rclcpp::Node、またはそれを継承したクラスです。

8行目は、送る・受ける、です。ROS1 は、rospy.Publisher に、名前、型、queue_size イコール10、の順で渡します。ROS2 は、create_publisher に、型、名前、10、の順で渡します。型とトピック名の順番が逆になり、最後の数は QoS です。QoS は、7-4節で扱います。

9行目は、型の C++ の名前です。ROS1 は std_msgs::String で、include するのは、std_msgs のフォルダの String.h です。ROS2 は std_msgs::msg::String で、include するのは、std_msgs の msg のフォルダの string.hpp です。msg、srv、action の段が入り、ヘッダのファイル名は、小文字とアンダースコアになります。

10行目は、ログです。ROS1 は、rospy.loginfo と ROS_INFO です。ROS2 は、self.get_logger().info と、RCLCPP_INFO の最初の引数に this の get_logger() を渡す形です。

11行目は、周期の処理です。ROS1 は、rospy.Rate と、while not rospy.is_shutdown のループです。ROS2 は、タイマー、つまり create_timer のコールバックです。7-4節で扱います。

12行目は、パラメータです。ROS1 は、rospy.get_param に、名前と既定値を渡します。ROS2 は、declare_parameter に、名前と既定値を渡して宣言してから読みます。フェーズ3-3 で扱っています。

13行目は、サービスの呼び出しです。ROS1 は、rospy.ServiceProxy で、同期的に呼びます。ROS2 は、create_client と call_async で、非同期に呼びます。フェーズ3-4 と、7-4節で扱います。

14行目は、時刻です。ROS1 は、ros::Time と、メッセージの中の time 型と duration 型です。ROS2 は、rclcpp::Time と self.get_clock().now()、それに builtin_interfaces の Time 型と Duration 型です。フィールドは、sec と nanosec です。

15行目は、launch ファイルです。ROS1 は、XML だけで、拡張子は .launch です。ROS2 は、Python、XML、YAML で、フェーズ4 で扱っています。XML の書き方も一部変わり、7-4節で扱います。

16行目は、座標変換です。ROS1 は tf と tf2、ROS2 は tf2 だけです。

17行目は、記録です。ROS1 は rosbag で、.bag のファイルです。ROS2 は ros2 bag です。ファイルの形式が違い、ROS1 の .bag は、ros2 bag で直接は再生できないので、変換が要ります。

18行目は、C++ の Boost です。ROS1 は、boost::shared_ptr や boost::function などです。ROS2 は、標準の C++ の std::shared_ptr や std::function などです。

### 7-4. 注意点: 書き換えても、同じように動くとは限らない

7-3節の表の置き換えには、名前を変えるだけでは済まないものがあります。ROS1 と ROS2 で動き方が違うために、ビルドが通っても、動かすと違う結果になる点を挙げます。8つあります。

1つ目は、メッセージの型の名前の決まりが厳しいことです。ROS2 では、フィールドの名前は、小文字で始まり、小文字、数字、アンダースコアだけを使います。アンダースコアの連続や、末尾のアンダースコアは使えません。Jazzy の rosidl_adapter のソースで確かめた、とあります。ROS1 で許されていた、途中に大文字を使う targetSpeed のような名前は、アンダースコアで区切った target_speed に変えないと、型を生成できません。名前を変えると、それを読み書きしているコードも、すべて直すことになります。

2つ目は、Header に seq が無いことです。ROS1 の std_msgs/Header にあった、通し番号の seq は、ROS2 の std_msgs/msg/Header にはありません。あるのは、stamp と frame_id だけです。ros2 interface show に std_msgs/msg/Header を付けると、確かめられます。seq で取りこぼしを調べていたコードは、別の方法に変えます。

3つ目は、グローバルなパラメータが無いことです。ROS1 では、roscore がパラメータの置き場、つまりパラメータサーバを持ち、どのノードからも読み書きできました。ROS2 のパラメータは、ノードごとに持ち、使う前に宣言が要ります。フェーズ3-3 で扱っています。複数のノードで同じ値を共有していたなら、launch ファイルから、各ノードに同じ値を渡す形に変えます。パラメータの YAML のファイルも、ノード名と、ros__parameters の段が要る形に書き換えます。フェーズ3-3 の5-4節で扱っています。

4つ目は、サービスは非同期で呼ぶことです。ROS1 の ServiceProxy は、応答が返るまで待つ、同期の呼び出しでした。ROS2 では、call_async で呼んで、後で結果を受け取ります。既定の、1つのスレッドでコールバックを順に実行する形のままで、コールバックの中に、応答を待つ処理、例えば rclpy.spin_until_future_complete などを書くと、ノードが応答を受け取れなくなり、止まってしまいます。デッドロックです。ROS1 のコードで、コールバックの中からサービスを呼んでいた箇所は、作りを見直します。

5つ目は、Rate のループを、そのまま写さないことです。Python では、rclpy にも Rate はありますが、その sleep は、ノードを回す処理、つまり spin がタイマーを動かすのを待つ作りになっています。Jazzy の rclpy のソースで確かめた、とあります。ROS1 のように、spin せずに、while と sleep だけで回すと、待ったまま戻りません。C++ の rclcpp::Rate は、決めた時間だけ待つ作りで、この問題はありません。Jazzy の rclcpp のヘッダで確かめた、とあります。ただし、ループの間は spin しないので、受信のコールバックが呼ばれません。どちらの言語でも、周期の処理は、タイマーのコールバックに書き換えるのが基本です。フェーズ3-1 で扱っています。

6つ目は、queue_size が QoS になることです。ROS1 の queue_size は、ROS2 では、QoS、つまり通信の送り方の約束の、depth、つまりためておく数に当たります。QoS は、フェーズ3-2b で扱い、詳しくは Tips集の6節にあります。ROS2 では、送る側と受ける側の QoS が合わないと、エラーにはならず、受ける側に警告が出るだけで、つながらないことがあります。これもフェーズ3-2b で扱っていて、警告の文面は Tips集の4-2節にあります。例えば、センサのドライバには、best_effort で送るものが多く、reliable で受けるとつながりません。ROS1 の、最後の値を後から来た相手にも渡す設定、つまり latch は、ROS2 では、durability の transient_local に当たり、送る側と受ける側の両方で指定します。

7つ目は、launch の XML も書き方が変わることです。ROS2 も XML の launch ファイルを読めますが、ROS1 のファイルは、そのままでは動きません。例えば、ノードの type は exec に、ns は namespace になります。ROS1 のように、param の要素を launch ファイルの直下に置いて、グローバルなパラメータにすることはできません。グローバルなパラメータが無いためです。パラメータは、node の要素の中に書くか、set_parameter を使います。set_parameter は、その launch ファイル、またはグループの中で、後に起動するすべてのノードに、同じ値を渡します。Jazzy の launch_ros で、XML でも使える形であることを確かめた、とあります。パッケージの場所を返す、ドル記号とかっこの find とパッケージ名は、ドル記号とかっこの find-pkg-share とパッケージ名になります。引数を読む、ドル記号とかっこの arg と名前は、ドル記号とかっこの var と名前になります。

8つ目は、シミュレーション時刻です。ROS1 の use_sim_time はグローバルなパラメータでしたが、ROS2 では、ノードごとのパラメータです。Tips集の1節で扱っています。シミュレータとつなぐノードには、1つずつ設定します。

移植の後は、ROS1 で動かしていたときの記録、つまりログや bag と見比べて、同じ入力で同じ結果になるかを確かめます。上の注意点は、ビルドでは見つからず、動かして初めて違いが分かるものが多い、とあります。
