# Tips集 12: Python のノードを速くするには、ROS2 に専用の仕組みはない（聞くための原稿）

これは、ros2MinimalPhysicalAi という教材の、Tips集の12個目の項目です。

Tips集は、手順書、つまりフェーズの本文に入れると流れが途切れる、分量の少ない補足をまとめた資料です。どの項目も独立しているので、関係する手順書を読んでいるときや、疑問を持ったときに、その項目だけを読めばよい、とあります。

対象は、ROS2 Jazzy と Ubuntu 24.04 です。版に依存する記述は、この資料を作ったときに、/opt/ros/jazzy と Ubuntu のパッケージに入っていたもので確かめた、とあります。所要の目安は、1項目あたり5 から15分の読み物です。

この項目に関係する手順書は、3つです。Python のパッケージを扱うフェーズ2、numpy だけで計算するノードを扱うフェーズ7-5、そして、コンポーネントの間章です。

出どころについて、断りがあります。この資料の内容は、/opt/ros/jazzy のソースなどを読んで確かめ、自分の言葉で書いたもので、ソースやドキュメントの転載ではない、とあります。

12節については、次のようにあります。12-2節で確かめたビルドは、マイナス2つの symlink-install の有無の両方で行ったもので、ノードは起動していない、とあります。ament_cmake_python と pybind11_vendor が入っていることと、rclpy のネイティブのモジュールは、/opt/ros/jazzy で確かめた、とあります。pybind11_vendor が、Ubuntu の pybind11-dev に依存することは、その package.xml で確かめた、とあります。Cython や Nuitka と、numpy の速さの話は、それらの道具についての一般的な情報から書いたもので、この環境には入れていない、とあります。rclpy の executor と、メッセージの変換の負担は、rclpy についての一般的な情報から書いたもので、測ってはいない、とあります。12-5節の、周期の最短の値は、手順書のタイマーとパラメータの period の値と、launch や YAML での上書きを検索して確かめた、とあります。2026年10月16日のことです。

## 12. Python のノードを速くするには、ROS2 に専用の仕組みはない

### 12-1. 疑問: Python のノードを実行ファイルにすれば、速くなるのではないか

C++ のノードは、colcon build でコンパイルされ、機械語の実行ファイルになります。Python のノードも、ビルドすると、ros2 run learn_py talker のように、実行ファイルの名前で起動できます。talker は、フェーズ3-1 で作るノードです。そのため、同じように機械語になって、速くなるように見えます。

実際には、そうはなりません。ROS2 には、Python のノードを機械語の実行ファイルに直して速くする仕組みは、用意されていません。

### 12-2. Python のノードの実行ファイルの中身

ros2 run が起動する、install の下の、learn_py の lib の learn_py の talker は、setup.py の entry_points から、setuptools が作った、短い Python のスクリプトです。この場所については、Tips集の10-3節にあります。この資料を作ったときに、使い捨てのワークスペースで雛形のパッケージをビルドして確かめた、とあります。

2つの点があります。

1つ目。1行目が #!/usr/bin/python3 で、Python の処理系を起動します。処理系は CPython です。CPython は、Python のコードを、機械語でなく、バイトコードという中間の形に直し、その命令を1つずつ解釈して実行するプログラムです。

2つ目。中身は、entry_points に書いたモジュールの main 関数を探して、呼ぶだけです。マイナス2つの symlink-install の有無で、中身は少し違いますが、どちらも Python のスクリプトです。

つまり、ノードの処理は、ふつうに python3 でスクリプトを動かすのと同じく、CPython が解釈して実行します。colcon build は、ファイルを決まった場所に置き、起動用の短いスクリプトを作るだけで、処理を機械語に直して速くはしません。Python は、読み込んだモジュールのバイトコードを、.pyc のファイルに取っておきますが、これは次の起動を少し早くするための仕組みで、機械語にはなりません。

### 12-3. ROS2 で速さが要るときの、標準的なやり方

ROS2 で速さが要る部分は、C++ で書くのが標準的なやり方です。3つの方法があります。

1つ目は、ノードを C++ で書くことです。rclcpp でノードを書けば、コンパイルされた実行ファイルになります。この教材の C++ 版、つまり learn_cpp が、この形です。

2つ目は、重い計算だけを C++ にして、Python から呼ぶことです。ノードは Python のままにして、重い計算だけを、C++ の拡張モジュールにする方法もあります。拡張モジュールは、Python から import して呼べる、コンパイル済みの部品です。Jazzy には、そのための部品が入っています。1つは、C++ と Python を1つのパッケージに入れるための、ament_cmake_python です。もう1つは、pybind11_vendor です。pybind11 は、C++ の関数を Python から呼べるようにするライブラリで、Ubuntu のパッケージでは pybind11-dev です。pybind11_vendor は、それを ROS2 のパッケージから使えるようにするものです。

3つ目は、同じプロセスにまとめることです。C++ のノードを、コンポーネントにして1つのプロセスにまとめ、プロセス内通信を指定すると、ノードの間のデータの受け渡しが DDS を通らなくなり、コピーを減らせます。コンポーネントは、コンポーネントの間章で扱います。プロセス内通信の指定は use_intra_process_comms で、コンポーネントの間章の7-3節にあります。指定しなければ、同じプロセスの中でも DDS を通ります。

なお、rclpy 自体も、通信の中心の部分、つまり rcl は、C や C++ で書かれていて、rclpy の中の _rclpy_pybind11 という、ネイティブのモジュールから呼んでいます。このモジュールも、上の拡張モジュールと同じく、コンパイル済みの部品です。

ただし、受け取ったメッセージを Python のオブジェクトに直す処理や、コールバックを順に呼ぶ仕組み、つまり executor の一部は、Python の側で動きます。そのため、画像のような大きなメッセージや、周波数の高い通信では、それらが効いてくることもあります。この教材のように、Float64 を数十 Hz で送る程度なら、まず疑うのは、自分で書いたコールバックの中の計算だ、とあります。

### 12-4. ROS2 の外の道具と、手軽な改善

Python のコードを機械語に直す一般的な道具は、あります。Cython や Nuitka などです。ただし、ROS2 のビルド、つまり colcon と ament_python には組み込まれていないので、使うなら、自分でビルドの手順に足すことになります。ROS2 のノードに使ったときに、どこまで速くなるかや、どんな手間が出るかは、この資料では確かめていない、とあります。

それより手軽なのは、Python のまま、計算の書き方を変えることです。たとえば、for の繰り返しで1つずつ計算している部分を、numpy の配列の計算にまとめると、繰り返しが numpy の中、つまりコンパイル済みのコードで行われるので、速くなりやすいです。

その一例が、フェーズ7-4 と7-5 のニューラルネットワークの計算、つまり nn_controller が使うものです。各層の掛け算と足し算を、for で1つずつ計算するのでなく、numpy で、w と h の行列の積に b を足す式の、1回で書いています。フェーズ7-5 のねらいは、PyTorch のような重いライブラリを入れずに済ませることですが、計算を配列にまとめている点は同じだ、とあります。

ただし、数個の値しか扱わない計算は、numpy にしても、呼び出しの手間のほうが大きく、速くならないことがあります。

### 12-5. 速くする前に、要るかどうかを確かめる

この教材のノードのタイマーの周期は、短いものでも0.01秒です。フェーズ5-1 の疑似プラントの vehicle_plant と、フェーズ5-4 の gz_plant です。制御のノード、つまりフェーズ5-2 の pi_controller は、0.02秒です。この程度の周期で、1回の計算が小さいものなら、Python のままで足ります。

速さが問題になったら、先に、どこが遅いかを測ります。トピックが決めた周期で出ているかは、ros2 topic hz で確かめられます。フェーズ1 の3-4節にあります。コールバックの中のどの計算に時間がかかっているかは、Python の標準の道具の cProfile で調べられます。cProfile はプロファイラ、つまり、関数ごとに、呼ばれた回数とかかった時間を数える道具です。

遅い部分が分かってから、その部分だけを、numpy に直すか、C++ にします。全体を書き直す前に測るのは、遅い原因が、計算でなく、周期の設定や、ほかのノードとのやり取りにあることもあるからです。
