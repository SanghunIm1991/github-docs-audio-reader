# Tips集 4: トピック通信の裏側、相手をどう見つけ、届いたことをどう確かめるか（聞くための原稿）

これは、ros2MinimalPhysicalAi という教材の、Tips集の4つ目の項目です。

Tips集は、手順書、つまりフェーズの本文に入れると流れが途切れる、分量の少ない補足をまとめた資料です。どの項目も独立しているので、関係する手順書を読んでいるときや、疑問を持ったときに、その項目だけを読めばよい、とあります。

対象は、ROS2 Jazzy と Ubuntu 24.04 です。版に依存する記述は、この資料を作ったときに、/opt/ros/jazzy と Ubuntu のパッケージに入っていたもので確かめた、とあります。所要の目安は、1項目あたり5 から15分の読み物です。

項目の一覧では、この項目は、トピック通信の裏側、つまりディスカバリと届いたことの確認、と書かれています。関係する手順書は、フェーズ3-2b、つまり QoS の手順書です。

出どころについて、断りがあります。この資料の内容は、/opt/ros/jazzy のソースなどを読んで確かめ、自分の言葉で書いたもので、ソースやドキュメントの転載ではない、とあります。ただし、4節の DDS の仕組み、つまりディスカバリ、HEARTBEAT、ACKNACK、既定の送り方は、DDS と Fast DDS の一般的な仕組みから書いたもので、この資料を作ったときに、通信を観察して確かめてはいない、とあります。既定の実装が rmw_fastrtps_cpp、つまり Fast DDS の2.14系であることは、/opt/ros/jazzy で確かめた、とあります。4-2節の警告の文面は、フェーズ3-2b に載せたもの、つまりコードと ROS2 の仕様から想定した表示を引いた、とあります。

## 4. トピック通信の裏側: 相手をどう見つけ、届いたことをどう確かめるか

### 4-1. 疑問: 配信側は受信側のことを知っているのか

ネットワークでブロードキャストをするとき、送る側は、ふつう受け手の事情を考えません。では、ROS2 の Publisher も、Subscriber のことを知らずに、送りっぱなしにしているのでしょうか。

答えは、コードの上では知らないが、下の層は知っている、です。publish() を呼ぶプログラムは、相手が何人いるかを意識しません。一方で、その下でトピック通信を担う DDS は、送る前に相手を探し、トピック名、型、QoS を確かめ合ってから送っています。DDS は、Data Distribution Service の略です。ROS2 Jazzy の既定の実装は Fast DDS で、ROS2 からは rmw_fastrtps_cpp として使われます。

### 4-2. 送る前に相手を見つける（ディスカバリ）

DDS は、データを送る前に、次の2段階で相手を探します。

1段階目は、参加者を見つけることです。各プロセスが、ここに ROS2 の参加者がいる、と、定期的に知らせ合います。既定の設定では、この知らせをマルチキャストで送ります。ブロードキャストに近い送り方をするのは、この段階だけです。

2段階目は、送受信口を見つけることです。見つけた相手と、どのトピックを、どの型で、どの QoS で、送る側か受ける側か、を交換します。

2段階目で、トピック名と型が同じでも、QoS が条件を満たさなければ、つながりません。つまり、マッチしません。条件は、購読側が求める水準を、配信側が満たしているか、です。配信側が reliable、購読側が best_effort なら、つながります。逆に、配信側が best_effort、購読側が reliable なら、つながりません。

フェーズ3-2b の5-1節の4番、つまり talker が best_effort、listener が reliable の組み合わせで出る警告は、この段階で出ています。

期待する結果です。ログが1行出ます。角かっこで囲んだ WARN の後に、qos_listener のノードの名前が続き、その後に、/qos_test のトピックについての英語の文が続きます。

書き出しは、New publisher discovered、つまり、新しい配信側を見つけた、です。そのとおり、相手を見つけたうえで、QoS が合わないので、やり取りしない、と判断しています。最後に合わなかったポリシーとして、RELIABILITY が示されます。

ros2 topic info マイナス v で、相手のノード名や QoS が表示されるのも、この段階で交換した情報を見せているからです。

なお、どこまで相手を探しに行くかは、環境変数の ROS_AUTOMATIC_DISCOVERY_RANGE で絞れます。LOCALHOST にすると、同じ PC の中だけになります。

### 4-3. 送るときと、届いたことの確かめ方

マッチした後のデータは、全員に一斉に送るのではなく、マッチした購読側それぞれの宛先へ送ります。Fast DDS の既定では、別の PC へはユニキャストの UDP で、同じ PC の中では共有メモリで送ります。届いたことを確かめるかどうかは、QoS の reliability で変わります。

best_effort は、送りっぱなしで、届いたかどうかを確かめません。途中で失われたデータは、そのまま失われます。受け手の事情を考えない送り方に近いのは、こちらです。

reliable は、配信側が、ここまで送った、という知らせ、つまり HEARTBEAT を出し、購読側が、ここまで受け取った、これが欠けている、という ACKNACK を返します。配信側は、欠けた分を送り直します。TCP に似た仕組みですが、DDS の通信規約の RTPS が、UDP の上で、自前で行っています。送り直せるのは、配信側が手元に残している分、つまり QoS の depth の件数だけです。

durability の transient_local も、相手を把握しているからこそできます。配信側が、送ったデータを手元に残しておき、後から参加した購読側を見つけた時点で、残しておいた分を渡します。渡すのは、購読側も transient_local を求めている場合だけです。

フェーズ3-2b の5-2節では、5番、つまり talker と listener がどちらも transient_local の組み合わせで、過去の分が届きます。6番、つまり listener が volatile の組み合わせでは、つながりますが、過去の分は届きません。7番、つまり talker が volatile、listener が transient_local の組み合わせは、この項目の4-2節で説明した QoS の突き合わせで、つながりません。

### 4-4. まとめ

まとめの表は、3列で3行です。列は、段階と、相手を把握しているか、届いたことの確認、です。

1行目は、ディスカバリです。相手は把握します。トピック名、型、QoS を交換します。届いたことの確認は、なしです。参加者の知らせは、既定ではマルチキャストです。

2行目は、best_effort の送信です。相手は把握していて、宛先を知っています。届いたことの確認は、しません。送りっぱなしです。

3行目は、reliable の送信です。相手は把握しています。届いたことの確認は、します。HEARTBEAT と ACKNACK で、欠けた分を送り直します。
