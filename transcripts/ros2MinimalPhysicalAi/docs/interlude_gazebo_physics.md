# 間章: Gazebo の物理シミュレーションの基本（聞くための原稿）

これは、ros2MinimalPhysicalAi という教材の、フェーズ5 の補足の間章の話です。フェーズ5-4 までを読み終えた人向けの、任意の章です。フェーズ5 では、Gazebo に付属する2輪車のワールドを写し、車輪にトルクをかけて走らせました。車両の形や重さ、地面との摩擦は、付属のファイルに書かれたものをそのまま使い、中身にはほとんど触れませんでした。けれども、自分のロボットをシミュレーションしたくなったら、ロボットの形、重さ、関節を自分で書き、地面や物との接触がどう計算されるかを知っておく必要があります。この章では、箱を落とす、坂で滑らせる、球を跳ねさせる、ばねでおもりを揺らす、腕を振り下ろす、という小さな体験を通して、ワールドとロボットの書き方と、物理エンジンが何を計算しているかを、ひととおり見ていきます。

想定する環境は、WSL2 と Ubuntu 24.04 と ROS2 Jazzy と、フェーズ5-0 で導入した Gazebo Harmonic です。5節だけは、ros2_control のパッケージを、5節の冒頭で追加で導入します。前提はフェーズ5-4 で、フェーズ6 と7 の本文は、この章に依存しません。所要時間の目安は1から2コマです。XML のファイルを書き、コマンドで動かすだけで、Python や C++ のコードは書きません。

この章の位置づけの囲みです。小さな体験つきの読み物です。体験に使うファイルは、どれも数十行の XML で、パッケージやビルドは要りません。練習のファイルは、ワークスペースの ros2_ws とは別のフォルダ、ホームの gz_practice に置きます。サンプルは学習の手がかりとして最小限に書いたもので、公式のチュートリアルの転載ではありません。要素の名前と書き方は、公式の文書と同じです。センサの節は、今後書き足す予定、とあります。

期待する結果の出どころの囲みもあります。gz sdf、xacro、check_urdf の表示は、章を作るときに実際に実行した表示です。2節と3節の位置の数値、つまり gz model の表示は、作るときに Gazebo を画面なしで起動し、一時停止したまま、決めた刻みだけ進めて読んだ表示です。4-4節の角度とノードのログは、画面なしの Gazebo で同じ手順を実行し、15秒進めた後に読んだ表示で、ログの時刻と stamp は実行ごとに違います。5節の、ノード、コントローラ、アクションの表示と角度、5-4節の表の角度も、画面なしの Gazebo で同じ手順を実行して読んだ表示です。一部は、ほかの表示と別の回の実行のものです。ログの時刻、stamp、アクションの ID は、実行ごとに違います。5節の冒頭の dpkg の表示は、作るときの環境で実際に実行した表示です。Gazebo の画面での見え方は、その数値から筆者が想定したものです。

この原稿では、練習のファイルを書き写さず、ブロックの構成を言葉で説明し、要の行は、原文の解説の要点の側で説明します。ツールの表示も、写さずに言葉で説明します。

## 0. この章で得てほしいこと

5つあります。

1つ目。Gazebo のワールドの記述、SDF の入れ子、つまりワールド、モデル、リンク、関節と、リンクが持つ3つの情報、つまり慣性、衝突、見た目を説明できる。

2つ目。物理エンジンが刻みごとに動きを計算していることと、刻み幅の max_step_size と、実時間の倍率の real_time_factor の意味を説明できる。

3つ目。摩擦係数と反発係数を書き換えて、滑り方と跳ね方が変わることを、手計算の値と比べて確かめられる。関節の軸にばねと減衰を持たせて、ばねとダンパーを表せる。

4つ目。ロボットの記述、URDF と SDF の違いを説明でき、xacro で書いた2関節のアームを Gazebo に出して、関節の角度を ROS2 のトピックで読める。

5つ目。ros2_control の部品、つまりハードウェアの部品、インターフェース、コントローラ、コントローラマネージャの役目を説明でき、位置と軌道のコントローラでアームを動かせる。

完了の条件です。2節から4節の体験で、Gazebo が計算した位置や角度が、手計算の値、つまり落下、坂、反発、ばね、関節の制限と、どこまで合い、どこがなぜずれるかを説明できること。5節の体験で、アームが位置のコントローラの目標の角度に止まり、軌道のコントローラの軌道を少し遅れて追うことを確かめ、その理由を説明できることです。

Gazebo でシミュレーションを動かす部品は、大きく4つあります。

1つ目は、記述のファイルです。何がどこにあるかを書いたファイルで、ワールド全体は SDF、つまり Simulation Description Format で書きます。ロボット1台は、SDF でも書けますが、ROS2 の世界では URDF、つまり Unified Robot Description Format で書くことが多いです。URDF は、そのままでは長くなりやすいので、マクロで短く書ける xacro で書いて、URDF に展開します。これは4節で扱います。

2つ目は、サーバー、gz sim です。記述を読み込み、物理エンジンで、決まった刻み幅ごとに、すべての物の位置と速度を計算し直します。物理エンジンの既定は DART で、3-1節で扱います。物理の計算そのもの、外からのコマンドの受け付け、状態の配信などは、システム、つまりプラグインという部品が受け持ち、ワールドやモデルの記述に plugin の要素で書いて足します。

3つ目は、画面、GUI です。サーバーから届く状態を3D で描き、再生や一時停止などの操作を受け付けます。gz sim に -s を付けて起動すると、画面を開かずに、サーバーだけが動きます。

4つ目は、ブリッジ、ros_gz_bridge です。Gazebo のトピック、つまり gz-transport と、ROS2 のトピックは別の仕組みなので、間で型を変換しながら中継します。フェーズ5-0 の4-1節で使った parameter_bridge です。

フェーズ5 の車両は、この全部を、付属のワールドファイルと launch ファイルで、一度に起動していました。この章では、記述のファイルを自分で書き、1つずつ起動して、それぞれの役割を確かめます。

## 2. SDF でワールドとモデルを書く

### 2-1. 入れ子の構造

SDF のファイルは、入れ子になった XML です。単位は、長さがメートル、質量がキログラム、角度がラジアン、時間が秒、つまり SI 単位です。

表は3列で、4行あります。列は、要素、意味、主な中身です。

world は、ワールド全体です。中身は、物理の設定の physics、重力の gravity、光の light、システムの plugin、モデルの model です。

model は、ひとまとまりの物、たとえば地面、箱、ロボットです。中身は、置く位置の pose、動かない物かどうかの static、リンク、関節、システムです。

link は、形と質量を持つ1つの部品、つまり剛体です。中身は、慣性の inertial、衝突の形の collision、見た目の visual です。

joint は、リンクとリンクのつなぎ目、つまり関節です。中身は、親と子のリンク、回る軸の axis、動ける範囲の limit、減衰の dynamics です。

リンクの3つの中身は、役割がはっきり分かれています。

慣性、inertial は、質量の mass と、慣性モーメント、つまり回転のしにくさの inertia です。物理エンジンが、力から加速度を計算するのに使います。

衝突、collision は、物理エンジンが、ぶつかったかどうか、つまり接触を判定する形です。摩擦や反発の係数も、ここの surface に書きます。3節で扱います。

見た目、visual は、画面に描く形と色です。物理の計算には使われません。

衝突と見た目を分けて書くのは、計算を軽くするためです。見た目は細かな形、つまりメッシュにしても、衝突は箱や円柱のような単純な形で近似する、という使い分けがよく行われます。この章のサンプルは、どちらも同じ単純な形にしています。

pose は、x、y、z、ロール、ピッチ、ヨーの6つの数で、位置、つまりメートルと、向き、つまり x 軸、y 軸、z 軸のまわりの回転のラジアンを表します。何も指定しなければ、親から見た位置になります。ワールドに直接置いたモデルなら、親はワールドです。

### 2-2. 体験: 箱と球を落とす

地面の上2メートルの高さに、箱と球を1つずつ置き、落としてみます。まず、mkdir -p でホームに gz_practice のフォルダを作り、cd で移ります。ファイルを作る方法、つまり touch と nano、または VS Code は、サンプルコードを練習環境に置く方法の文書と同じです。

ファイルは、gz_practice の drop.sdf です。

drop.sdf は、70行ほどの XML で、構成は、先頭の XML の宣言と概要のコメント、sdf の要素、その中の drop という名前の world です。world の中には、physics、gravity、plugin が3つ、太陽の light、そしてモデルが3つ、つまり ground、box、ball が並びます。要の行は、このあとの解説の要点で説明します。

原文の解説の要点です。ファイルの中身を、上から順に読んでいます。

physics は、物理エンジンの設定です。1刻みを0.001秒、つまり1ミリ秒にし、現実の時間と同じ速さで進めます。3-1節で扱います。type の属性は、今の Gazebo では使われないので、ignored と書いておきます。

gravity は、重力加速度のベクトルで、z 軸の負の向き、つまり下向きに9.8 です。書かなければ、この値が既定です。

plugin の3行は、このワールドで動かすシステムです。物理の計算の Physics、モデルを出したり消したりするコマンドの受け付けの UserCommands、画面への状態の配信の SceneBroadcaster です。Physics を書き忘れると、何も落ちません。

ground は、static が true の、動かないモデルです。無限に広い平面、plane を衝突の形にし、見た目は20メートル四方にします。

box は、一辺0.2メートル、質量1キログラムの箱です。慣性モーメントは、直方体の式、I イコール、m かける、a の2乗プラス b の2乗、割る12、に、m を1、a と b を0.2 として入れた値で、約0.00667キログラム平方メートルです。

ball は、半径0.1メートルの球です。質量と慣性モーメントを書く代わりに、inertial の auto の属性を true にし、密度の500、つまり水の半分を書いて、衝突の形から自動で計算させています。これは2-3節で扱います。

文法を確かめてから、Gazebo で開きます。gz sdf に -k を付けて drop.sdf を確かめると、期待する結果は、Valid、つまり正しい、という1語です。要素の名前のつづりや入れ子を間違えると、どこが違うかが表示されます。

ターミナル1 で、gz_practice に移り、gz sim drop.sdf で開きます。

期待する結果です。Gazebo の画面が開き、灰色の地面の上に、青い箱と赤い球が浮いて見えます。gz sim は一時停止した状態で始まるので、まだ落ちません。左下の再生のボタンを押すと、2つは同時に落ち始め、約0.6秒で地面に着いて止まります。止まったら、ウィンドウを閉じるか、ターミナル1 で Ctrl+C を押します。次の手順は、落ちる前の状態から始めるので、もう一度 gz sim drop.sdf で開き直します。

画面の再生のボタンの代わりに、決めた刻みの数だけ進めることもできます。ターミナル2 から、ワールドを操作するサービス、world の drop の control に、300刻み、つまり0.3秒進めて、また止める、という要求を、gz service で送ります。要求の中身は、multi_step を300、pause を true にしたものです。そのあと、gz model に -m で box、-p を付けて、箱の位置を読みます。

期待する結果です。gz service は、data が true、つまり要求を受け付けた、と応答します。gz model は、ワールド drop の状態を要求していると出たあと、モデルの番号と名前の box、そして位置と向きを2行で表示します。1行目が位置の x、y、z で、z、つまり箱の中心の高さが、2メートルから1.557530メートルに下がっています。2行目が向きで、ロール、ピッチ、ヨーはすべて0 です。モデルの番号は、Gazebo の中でモデルに付けられた番号で、ファイルの書き方によって変わります。画面では、箱と球が少しだけ下がって止まって見えます。

multi_step も、real_time_factor に従って、現実の時間と同じ速さで進みます。300刻みなら0.3秒かかるので、gz model は、画面の動きが止まってから実行します。同じように、さらに300刻み、400刻みと進めて読むと、高さは次のように変わります。球も、箱と同じ高さになります。

表は3列で、4行あります。列は、進めた時間、Gazebo での箱の中心の高さ、自由落下の式、つまり z イコール、2 マイナス、2分の1 かける g かける t の2乗、の値です。

0秒では、Gazebo が2.000000メートル、式が2.000メートルです。

0.3秒では、Gazebo が1.557530、式が1.559 です。

0.6秒では、Gazebo が0.233060、式が0.236 です。

1.0秒では、Gazebo が0.095492 で、式の欄は、地面に着いている、です。

読み方が2つあります。

1つ目。0.3秒と0.6秒の高さは、自由落下の式と、1から3ミリメートルの差で合います。差は、物理エンジンが、連続した時間でなく、0.001秒の刻みで計算していることから来ます。Gazebo の既定の物理エンジン、DART は、刻みごとに、まず重力で速度を更新し、その新しい速度で位置を進めます。半陰的オイラー法と呼ばれ、考え方は Tips集の9-5節にあります。この計算で n 刻み進めた高さは、2 から、g かける デルタ t の2乗かける、n かける n プラス1 割る2、を引いたものになります。n を300、デルタ t を0.001 として入れると1.557530、n を600 にすると0.233060 で、表の Gazebo の値と、小数第6位まで一致します。

2つ目。1.0秒の時点で、箱の中心は、箱の半分の高さの0.1メートルではなく、0.0955メートルにあり、地面に約4.5ミリメートルめり込んでいます。物理エンジンは、接触した物どうしが少し重なることを許し、重なりを刻みごとに少しずつ押し戻します。作るときに3秒まで進めると、0.0962メートルまで戻った、とあります。重なりを一気に押し戻すと、跳ね飛ぶような大きな力が出てしまうためです。ロボットの足が地面に数ミリ沈んで見えるのも、同じ理由によります。

### 2-3. 慣性を自動で計算させる

ball のように、inertial の auto を true にすると、Gazebo は、衝突の形と密度から、質量と慣性モーメントを計算します。計算した値は、gz sdf の -p に --expand-auto-inertials を付けると表示できます。-p は、ファイルを読み込んで、解釈した結果の SDF を表示するオプションです。

期待する結果は、ball の部分だけの抜粋です。ball のリンクの inertial の中に、密度の500 と、自動で計算された値として、質量の約2.0944 と、慣性モーメントの ixx、iyy、izz がどれも約0.0083776、ほかの3つは0、が表示されます。

質量は、球の体積、3分の4 かける パイ かける r の3乗に密度を掛けて、500 かける3分の4 パイ かける0.1 の3乗で、約2.094キログラムです。慣性モーメントは、球の式、5分の2 かける m かける r の2乗で、約0.00838キログラム平方メートルです。どちらも手計算と合います。

質量と慣性モーメントは、物理の計算の土台です。慣性モーメントを実際より小さく書くと、少しの力で激しく回転し、シミュレーションが不安定になります。これはよくある失敗です。単純な形なら、自動の計算に任せるか、公式で計算した値を書きます。メッシュの形の部品では、CAD などで求めた値を書きます。

## 3. 物理でできること

### 3-1. 物理エンジンと刻み幅

physics の主な設定の表があります。既定値は、gz sdf の -d で表示される SDF の仕様で確かめた、とあります。3列の表で、3行あります。列は、要素、既定値、意味です。

### 3-4. 体験: ばねとダンパー

ばね、つまり変位に比例して押し戻す力と、ダンパー、つまり速さに比例して動きを妨げる力は、機械の振動や、サスペンション、柔らかい関節を表すのに欠かせません。Gazebo には、ばねやダンパーを1つの部品として置く要素はありません。代わりに、関節の軸に、ばねと減衰を持たせます。関節の axis の dynamics に、次の3つを書きます。

表は3列で、3行あります。列は、要素、意味、単位です。単位は、まっすぐ動く関節のものと、回転の関節のものを並べています。

spring_stiffness は、ばね定数 k です。単位は、メートルあたりのニュートン、または、ラジアンあたりのニュートンメートルです。

spring_reference は、ばねの力が0 になる関節の位置、x ゼロ、つまり自然長の位置です。単位は、メートル、またはラジアンです。

damping は、減衰係数 c、つまりダンパーです。単位は、メートル毎秒あたりのニュートン、または、ラジアン毎秒あたりのニュートンメートルです。

関節には、マイナス k かける、x マイナス x ゼロ、から、c かける x ドットを引いた力、回転の関節ならトルクがかかります。x は関節の位置、x ドットは、その速さです。まっすぐ伸び縮みするばねは、直動の関節、つまり type が prismatic の、軸の向きにだけ動く関節で表し、ねじりばねは、回転の関節、type が revolute で表します。

天井から、質量1キログラムのおもりを、ばね定数100の、メートルあたりのニュートンのばねで吊るします。減衰の無いものと、減衰のあるものの2つを並べます。

ファイルは、gz_practice の spring.sdf です。

spring.sdf は、80行ほどの XML で、構成は、spring という名前の world の中に、plugin が3つ、light、そしてモデルが2つ、つまり減衰の無い spring_free と、減衰のある spring_damped が並びます。どちらのモデルも、おもりのリンク weight と、関節の spring を持ちます。要の行は、このあとの解説の要点で説明します。

原文の解説の要点です。

地面は置いていません。おもりは天井、つまりワールドから吊るされていて、地面まで届かないので要りません。

関節の parent を world、つまりワールドそのものにすると、関節の付け根がワールドに固定されます。おもりは、この関節で動ける向きにだけ動き、ほかの向きには動きません。

type を prismatic、axis の xyz を0、0、1 にしているので、おもりは z 軸、つまり上下の向きにだけ動けます。関節の位置 x は、最初の位置、つまり高さ1メートルから上へ測った変位で、x イコール0 が、ばねの自然長の位置です。spring_reference が0 だからです。

## 4. URDF と xacro でロボットを書く

### 4-1. URDF と SDF の違い

ROS2 の世界では、ロボットの形と関節を、SDF でなく URDF で書くことが多いです。URDF は、ROS、つまり ROS1 の時代からの、ロボット1台を記述する XML の書き方です。

表は3列で、4行あります。列は、項目、SDF、URDF です。

記述できる範囲は、SDF はワールド全体、つまり光、物理の設定、複数のモデルです。URDF は、ロボット1台だけです。

リンクのつながりは、SDF は自由で、輪になったつながりも書けます。URDF は木の形だけで、親は1つです。

使う道具は、SDF は Gazebo です。URDF は、ROS2 の道具、つまり robot_state_publisher、RViz、MoveIt、ros2_control と、読み込むときに SDF に変換する Gazebo です。

Gazebo 特有の設定、つまりシステムや摩擦などは、SDF ならそのまま書けます。URDF では、gazebo の要素の中に書き、変換のときに SDF に写されます。

URDF は、ROS2 の道具の多くが読める共通の形式なので、ロボットの記述は1つの URDF に書き、Gazebo にも、ROS2 のノードにも、同じものを渡す、という使い方が一般的です。要素の名前は、SDF とよく似ていて、link、joint、inertial、collision、visual があります。違いは、位置を pose でなく、origin の要素の xyz と rpy の属性で書くこと、関節の位置が、子のリンクの座標系の原点になること、などです。

### 4-2. xacro で短く書く

URDF には、変数や繰り返しの仕組みがありません。同じ形の腕を2本書くと、ほぼ同じ数十行が2回並び、長さを変えるときに、何か所も直すことになります。xacro、つまり XML Macros は、URDF に次の仕組みを足した書き方で、xacro のコマンドで、ふつうの URDF に展開してから使います。

1つ目は、名前を付けた値、つまり変数で、xacro の property の要素で、たとえば arm_len を0.5 と決め、ドル記号と中かっこで arm_len を囲んで使います。

2つ目は、式で、ドル記号と中かっこの中に、たとえば arm_mass かける arm_r かける arm_r 割る2 と書くと、値を計算して埋め込みます。パイも使えます。

3つ目は、マクロ、つまり部品のひな形で、xacro の macro の要素で、名前と引数を決めておくと、xacro の、そのマクロの名前の要素を書くだけで、中身が展開されます。

### 4-3. 体験: 2関節のアームを書く

台、つまり高さ1メートルの柱の上に、長さ0.5メートルの腕を2本つないだアームを書きます。腕は、x 軸の向きに水平に伸びた姿勢で現れ、重力で振り下ろされます。

ファイルは、gz_practice の arm.urdf.xacro です。

arm.urdf.xacro は、80行ほどの XML で、構成は、arm という名前の robot の中に、xacro の property が3つ、腕のマクロの arm_link、中身の無いリンク world、台のリンク base、台を world に固定する関節 fix_base、マクロを2回使った link1 と link2、2つの回転の関節 joint1 と joint2、そして gazebo の要素が並びます。要の行は、このあとの解説の要点で説明します。

原文の解説の要点です。

腕のマクロ arm_link は、質量1キログラム、半径0.03メートル、長さ0.5メートルの円柱を、リンクの原点から x 軸の向きに伸ばします。円柱は、そのままでは z 軸の向きに伸びるので、rpy で y 軸のまわりに2分の パイ、つまり90度回して横に倒し、中心を arm_len の半分、つまり0.25メートルだけずらします。慣性モーメントは円柱の式で、軸のまわりが、m かける r の2乗割る2、軸に直交する向きが、m かける、3 r の2乗プラス L の2乗、割る12 です。このマクロを link1 と link2 の2回使います。

world と fix_base です。world という名前の、中身の無いリンクに、固定の関節、つまり type が fixed で台をつなぐと、台はワールドに固定されます。Gazebo に読み込むとき、world は特別な名前として、ワールドそのものを指します。これが無いと、台ごと倒れます。

関節の joint1 と joint2 です。type の revolute は、動ける範囲のある回転の関節です。origin が関節の位置、つまり親のリンクの座標系での位置で、子のリンクの原点もここになります。joint1 は柱の上端、joint2 は link1 の先端、つまり x が0.5メートルのところにあります。y の値の0.1 と0.07 は、腕どうしと柱が、見た目で重ならないように横にずらしたものです。回る軸は、どちらも y 軸で、角度が正の向きに増えると、腕の先が下がります。

limit です。joint1 は、マイナス1.0 から1.0ラジアン、つまり約プラスマイナス57度しか回りません。joint2 は、マイナス2.5 から2.5ラジアンです。effort と velocity は、関節に出せる力と速さの上限で、URDF の回転の関節では、書くことが必須です。

dynamics の damping の0.5 は、関節の減衰です。角速度に比例する抵抗のトルクで、これが無いと、腕はいつまでも揺れ続けます。

gazebo の要素は、Gazebo にだけ伝えたい設定です。ここでは、関節の角度を Gazebo のトピックに送るシステム、JointStatePublisher を足します。reference の属性を付けずに書くと、モデル全体に付きます。

URDF でばねを書く場合、の説明があります。URDF の関節の dynamics に書けるのは、減衰の damping と摩擦の friction だけで、3-4節のばね、つまりばね定数と自然長の位置の項目はありません。Gazebo に読み込む URDF では、gazebo の要素に、関節の名前を reference の属性で付けて書き、その中に、springStiffness、つまりばね定数と、springReference、つまり自然長の位置を書きます。作るときに、reference が spring の gazebo の要素の中に、springStiffness を100 と書いた URDF を、gz sdf の -p で SDF に変換し、関節の dynamics に spring_stiffness の100 が入ることを確かめた、とあります。このアームでは、ばねは使いません。

腕が水平な姿勢、つまり角度0 から放すと、joint1 は重力で正の向きに回り、上限の1.0ラジアンで止まるはずです。link2 は、joint1 が止まった後も回り続け、真下に垂れて落ち着くはずです。link1 が水平から1.0ラジアン下がっているので、link2 が真下、つまり水平から2分の パイ、約1.571ラジアンを向くときの joint2 の角度は、2分の パイ マイナス1.0 で、約0.571ラジアンになります。

xacro を URDF に展開し、URDF として正しいかを check_urdf で確かめます。xacro と check_urdf は、それぞれ ros-jazzy-xacro と ros-jazzy-urdfdom のパッケージに含まれ、フェーズ5-0 の1-2節の Gazebo の導入で、依存するパッケージとして一緒に入ります。作るときの環境で確かめた、とあります。見つからない場合は、sudo apt install でこの2つを入れます。

gz_practice で、xacro arm.urdf.xacro の出力を arm.urdf に書き出し、check_urdf arm.urdf を実行します。

期待する結果、check_urdf の分です。ロボットの名前が arm であることと、XML の読み込みに成功したことが表示され、続いて、リンクの木の形が、字下げで表示されます。根のリンクは world で、その子が base、その子が link1、その子が link2 です。

読み込みの成功と、この木の形が出れば、URDF として正しいです。arm.urdf を開くと、ドル記号と中かっこの式が、計算された値に置き換わり、たとえば link1 の iyy は約0.0210583 になり、マクロが2本の腕に展開されているのが分かります。

Gazebo が読み込むときの、SDF への変換は、gz sdf の -p に arm.urdf を渡すと見られます。

期待する結果、joint1 の部分だけの抜粋です。type が revolute の joint1 の要素の中に、base から見た位置として、y が0.1、z が1 の pose、親の base、子の link1、そして axis の中に、xyz の0、1、0、limit の下限マイナス1、上限1、effort の100、velocity の10、dynamics の減衰0.5、摩擦0、ばねの自然長0、ばね定数0 が並びます。

URDF の origin が、SDF の、relative_to が base の pose に変わっています。ほかに、fix_base は、親を world とする固定の関節になり、gazebo の要素の中の plugin は、モデルのすぐ下に写されています。これは抜粋の外です。

### 4-4. 体験: Gazebo に出して、関節の角度を ROS2 で読む

アームを、Gazebo の空のワールドに出し、関節の角度を ROS2 のトピックで読みます。4つのターミナルを使います。

ターミナル1 で、gz sim に -r を付けて empty.sdf を開きます。empty.sdf は、Gazebo に付属する、地面と光だけのワールドで、ワールド名は empty です。-r を付けると、一時停止せずに、すぐに時間が進み始めます。

ターミナル2 で、gz_practice に移り、ros2 run robot_state_publisher robot_state_publisher に、--ros-args と、-p で robot_description に、xacro arm.urdf.xacro の出力をその場で渡して起動します。robot_state_publisher は、パラメータ robot_description で受け取った URDF を、同じ名前のトピック、/robot_description、型は std_msgs の msg の String に、送っておくノードです。このトピックは、後から購読したノードにも最後の値が届く設定、つまり QoS の transient_local で送られるので、ターミナル4 の create を後から起動しても受け取れます。本来の役目は、関節の角度、つまり /joint_states を受け取って、各リンクの位置関係、TF を計算して配ることで、RViz でロボットを表示するときなどに使います。xacro の出力をその場で渡す書き方は、xacro を展開した結果の文字列を、パラメータに渡すシェルの書き方です。

ターミナル3 で、ros2 run ros_gz_bridge parameter_bridge で、world の empty の model の arm の joint_state を、ROS2 の sensor_msgs の JointState と、Gazebo の gz.msgs.Model の間で、開きの角かっこ、つまり Gazebo から ROS2 への一方向で中継し、--ros-args の -r で、ROS2 の側のトピック名を /joint_states に付け替えます。JointStatePublisher が送る Gazebo のトピックは、world の、ワールド名の、model の、モデル名の joint_state で、それを ROS2 の、ROS の慣習の名前の /joint_states にしています。

ターミナル4 で、ros2 run ros_gz_sim create に、-topic で robot_description、-name で arm を渡します。

期待する結果、ターミナル2 から4 の表示です。ターミナル2 には、robot_state_publisher の、ロボットを初期化した、という1行が出ます。ターミナル3 には、ブリッジが、Gazebo から ROS への中継として、arm の joint_state を、gz.msgs.Model から sensor_msgs の JointState へ作った、という1行が出ます。ターミナル4 には、ros_gz_sim が、ワールドの名前の一覧を求めている、robot_description のトピックでメッセージを待っている、そして、エンティティの作成に成功した、という3行が出ます。

ターミナル1 では、地面だけの Gazebo の画面が開き、時間が進んでいます。ターミナル2 と3 は、起動したときの1行だけを表示し、その後は何も出さずに動き続けます。ターミナル3 の行に出る ROS2 の側のトピック名は、付け替える前の名前のままですが、実際には /joint_states に送られています。

create は、トピック /robot_description から URDF を受け取り、動いているワールドに、モデル arm として出して、終わります。エンティティの作成に成功した、と出れば成功です。ターミナル1 の画面では、柱の上に水平な腕が現れ、すぐに振り下ろされます。link1 は斜め下、約57度で止まり、link2 は振り子のように何度か揺れて、真下に垂れて落ち着きます。

腕が落ち着いたら、10秒ほど待って、ターミナル4 で、ros2 topic echo の /joint_states に --once を付けて、関節の角度を読みます。

期待する結果です。header の stamp は、シミュレーションの時刻の15秒で、読んだ時刻によって変わります。name には、fix_base、joint1、joint2 が並び、position には、0.0、約1.0000000000000195、約0.5797 が並びます。velocity は、0.0 と、10 のマイナス13乗や15乗の、ほとんど0 の値で、effort は、すべて0.0 です。

読み方が3つあります。

1つ目。name と position は、同じ順番で対応しています。固定の関節 fix_base も並びますが、角度は常に0 です。

2つ目。joint1 は1.0ラジアンで、limit の上限で止まっています。

3つ目。joint2 は約0.580ラジアンで、手計算の0.571 より、約0.009ラジアン、つまり約0.5度大きくなっています。velocity がほぼ0 なので、揺れている途中ではなく、この角度で止まっています。このずれは、刻みごとの計算から来るものです。作るときに、関節の減衰を4倍の2.0 にすると、ずれも約4倍の0.034ラジアンになり、刻み幅を半分の0.0005秒にすると、ずれも半分の0.0045ラジアンになりました。連続の時間の物理では、減衰は動いているときだけ効くので、止まった位置を変えないはずです。3-4節で、減衰の無いばねの揺れの幅が、刻み幅に比例して少しずつ小さくなったのと、同じ種類のずれです。joint1 を上限に押し付けたまま、刻みごとに計算するうちに、減衰の力が、わずかに残る形になっていると考えられる、とあります。DART の内部の計算までは確かめていません。シミュレーションの結果は、刻み幅や物理エンジンの設定で少し変わるので、実機と比べるときは、どのくらいずれうるかを、刻み幅を変えて確かめておきます。

止めるときは、ターミナル3、2、1 の順に Ctrl+C で止めます。ターミナル4 の create と、ros2 topic echo の --once は、自分で終わります。

## 5. ros2_control で関節を動かす

この節では、フェーズ5-0 で入れた Gazebo のパッケージに含まれない、ros2_control のパッケージを使います。体験の前に、sudo apt install で、ros-jazzy-gz-ros2-control と ros-jazzy-ros2-controllers の2つを導入し、dpkg の -l で確かめます。

期待する結果は、dpkg の -l の表示の最後の2行です。2つのパッケージの行が、どちらも、導入済みを表す ii で始まり、版、アーキテクチャの amd64、説明が並びます。版と日付は、導入した時期によって変わります。2行とも先頭が ii なら、準備ができています。ros-jazzy-gz-ros2-control は、Gazebo の中で ros2_control を動かすためのもの、ros-jazzy-ros2-controllers は、この節で使うコントローラ、つまり5-1節の表のコントローラを含む、パッケージの集まりです。コントローラマネージャ、つまり controller_manager などの、ros2_control の本体も、依存するパッケージとして一緒に入ります。

### 5-1. ros2_control の仕組み

4-4節では、関節の角度を読むだけで、腕は重力に任せて垂れ下がりました。腕を狙った角度に動かすには、関節に指令を送る仕組みが要ります。3-5節の表のように、Gazebo のシステム、たとえば ApplyJointForce で関節に力をかけることもできますが、それは Gazebo の中だけの書き方で、実機のロボットに移すときには、指令を送る側を書き直すことになります。

ros2_control は、この、指令を送る側と、関節を実際に動かす側を分けて、間をそろえた形でつなぐ、ROS2 の仕組みです。関節を動かす側は、実機ならモータのドライバを読み書きする部品、シミュレーションなら Gazebo の関節を読み書きする部品に替わりますが、指令を送る側、つまりコントローラと、さらにその上のノードは、どちらでも同じものを使えます。腕の動作計画の MoveIt は、計画した動きを、ros2_control の軌道のコントローラ、つまり5-4節で使うものに送って関節を動かすのが標準の構成で、移動ロボットでも、車輪を ros2_control のコントローラで動かす構成が多い、とあります。

ros2_control の部品の表は、3列で、4行あります。列は、部品、役目、この節で使うものです。

1行目は、ハードウェアの部品、hardware component です。関節の状態を読み、指令を書き込みます。実機とシミュレーションで差し替える部分です。この節では、gz_ros2_control の GazeboSimSystem、つまり Gazebo の関節を読み書きするものを使います。

2行目は、インターフェースです。関節ごとに、読める値、つまり状態のインターフェースの、角度 position や角速度 velocity などと、書ける値、つまり指令のインターフェースの、角度、角速度、トルク effort のどれかを決めます。この節では、指令は角度、状態は角度と角速度です。

3行目は、コントローラです。状態を読み、ROS2 のトピックやアクションで受けた目標から、指令を計算して書き込みます。この節では、joint_state_broadcaster、position_controllers の JointGroupPositionController、joint_trajectory_controller の JointTrajectoryController を使います。

4行目は、コントローラマネージャ、controller manager です。決まった周期、update_rate で、ハードウェアの読み、コントローラの計算、ハードウェアへの書き、を繰り返します。コントローラの読み込みと、有効と無効の切り替えも受け付けます。この節では、Gazebo の中で動かし、gz_ros2_control のシステムが起動します。

コントローラのうち、joint_state_broadcaster は、指令を書かず、全部の関節の状態を /joint_states に送るだけのものです。4-4節でブリッジが担っていた役目を、ros2_control の中で果たします。

ここに、2枚目の図があります。全体を、薄い緑の破線の枠が囲み、その見出しは、gz sim の中、です。その中の上の部分を、さらに薄いオレンジ色の破線の枠が囲み、見出しは、コントローラマネージャ、update_rate ごとに繰り返す、です。オレンジ色の枠の中には、薄いオレンジ色の箱が2つ、左右に並びます。左の箱は、コントローラ、位置のコントローラ、軌道のコントローラ。右の箱は、joint_state_broadcaster、状態を送る、です。緑の枠の中の下には、薄い緑の箱が上下に2つあり、上は、ハードウェアの部品、GazeboSimSystem、下は、Gazebo の関節、物理エンジンが動きを計算、です。

緑の枠の外の左には、薄い青の箱があり、ROS2 のノード、ros2 topic pub、ros2 action send_goal、と書いてあります。外の右には、薄い青の箱があり、ros2 topic echo など、と書いてあります。

矢印は4本で、どれも実線です。左の ROS2 のノードから、コントローラの箱へ、目標、の矢印。joint_state_broadcaster の箱から、右の ros2 topic echo などの箱へ、/joint_states の矢印。コントローラの箱とハードウェアの部品の間は、上下の両向きの矢印で、指令と状態。ハードウェアの部品と Gazebo の関節の間も、上下の両向きの矢印で、書く、読む、です。

コントローラの読み込みと、有効と無効の切り替えは、図の外から、コントローラマネージャのサービスを呼んで行います。5-3節の spawner です。

### 5-2. 体験: アームに ros2_control の記述を足す

4-3節のアームに、ros2_control の記述を足します。4-3節のファイルは書き換えずに残し、それを読み込む新しいファイルを作ります。

ファイルは、gz_practice の arm_control.urdf.xacro です。

arm_control.urdf.xacro は、30行ほどの XML で、構成は、arm という名前の robot の中に、xacro の include、ros2_control の要素、gazebo の要素の3つが並びます。ros2_control の要素の中には、hardware と、joint1 と joint2 の2つの joint があります。要の行は、このあとの解説の要点で説明します。

原文の解説の要点です。

xacro の include は、ほかの xacro のファイルを読み込み、その robot の中身を、ここに展開します。パスは、このファイルからの相対パスで書けます。filename を arm.urdf.xacro にしているので、4-3節の台と2本の腕が、そのまま入ります。4-3節の JointStatePublisher も入りますが、この節では使いません。

ros2_control の要素は、ros2_control の記述です。名前は GazeboSimSystem、type は system です。hardware の plugin に、gz_ros2_control の GazeboSimSystem を書いて、ハードウェアの部品に Gazebo の GazeboSimSystem を使うと決め、joint ごとに、指令のインターフェース、つまり command_interface と、状態のインターフェース、つまり state_interface を並べます。ここでは、2つの関節とも、角度、つまり position を指令し、角度と角速度、つまり position と velocity を読みます。

gazebo の要素の plugin は、Gazebo のシステム、gz_ros2_control の GazeboSimROS2ControlPlugin を足します。filename は gz_ros2_control-system です。このシステムが、Gazebo の中でコントローラマネージャを起動し、URDF の ros2_control の要素に従って、ハードウェアの部品を作ります。parameters の要素は、コントローラの設定のファイルの場所で、ドル記号とかっこの env HOME の後ろに、gz_practice の arm_controllers.yaml を続けています。env HOME は、xacro が展開するときに、環境変数 HOME の値、つまりホームのフォルダに置き換わります。

設定のファイルの場所の補足があります。一般的には、URDF と設定のファイルを ROS2 のパッケージに入れ、ドル記号とかっこの find とパッケージ名を使って、パッケージの場所から書きます。この章ではパッケージを作らないので、ホームのフォルダからの絶対パスにしました。練習のフォルダを gz_practice 以外に置いた場合は、このパスも合わせて直します。

次のファイルは、gz_practice の arm_controllers.yaml です。

arm_controllers.yaml は、30行ほどの YAML で、構成は、先頭のコメントのあと、3つのまとまり、つまり controller_manager、arm_position_controller、arm_trajectory_controller が並びます。どのまとまりも、その下に ros__parameters があります。要の行は、このあとの解説の要点で説明します。

原文の解説の要点です。

controller_manager は、コントローラマネージャのパラメータです。update_rate は、読む、計算する、書く、を繰り返す周期で、ここでは100、つまり毎秒100回です。続く3つは、使うコントローラの名前、つまり自分で付ける joint_state_broadcaster、arm_position_controller、arm_trajectory_controller と、それぞれの種類、type の対応です。ここに書いただけでは、まだ動きません。

arm_position_controller は、位置のコントローラです。トピックで受けた角度を、そのまま関節の指令に書きます。joints に、動かす関節の joint1 と joint2 を並べます。

arm_trajectory_controller は、軌道のコントローラです。何秒後にどの角度、という点の並び、つまり軌道を受け取り、間をなめらかにつないで、刻みごとの指令を書きます。joints のほかに、使う指令のインターフェースの position と、状態のインターフェースの position と velocity も書きます。

### 5-3. 体験: 位置のコントローラで動かす

4-4節と同じく、4つのターミナルを使います。4-4節の Gazebo とノードが動いていたら、先にすべて止めておきます。同じ名前のモデル arm は、1つのワールドに2つ出せないからです。

ターミナル1 では、4-4節と同じく、gz sim に -r を付けて empty.sdf を開きます。ターミナル2 では、4-4節と同じく robot_state_publisher を起動しますが、展開するファイルを arm_control.urdf.xacro にします。ターミナル3 では、ros2 run ros_gz_bridge parameter_bridge で、/clock を、ROS2 の rosgraph_msgs の Clock と、Gazebo の gz.msgs.Clock の間で、開きの角かっこ、つまり Gazebo から ROS2 への一方向で中継します。ターミナル4 では、4-4節と同じく、ros_gz_sim の create で arm を出します。

ターミナル3 は、関節の角度の代わりに、Gazebo のシミュレーションの時刻、/clock を中継します。GazeboSimROS2ControlPlugin は、コントローラマネージャとコントローラを、シミュレーションの時刻で動かす設定、use_sim_time で起動するので、この時刻が届かないと、/joint_states の時刻、stamp が0 のままになります。

期待する結果、ターミナル1 から4 の表示の抜粋です。ターミナル2 から4 には、4-4節と同じ形の行が出ます。ターミナル3 は /clock の中継を作ったという1行です。ターミナル1 には、モデルが出た後に、gz_ros_control と controller_manager のログが続きます。controller_manager を読み込む、/robot_description のトピックからロボットの記述を購読する、トピックからロボットの記述を受け取った、position_proportional_gain が0.1 に設定された、joint1 を読み込む、joint2 を読み込む、そして、リソースマネージャの初期化に成功し、コントローラマネージャのサービスを始める、という行です。

ターミナル4 の、robot_description のトピックでメッセージを待っている、という行は、2回以上出ることもあります。ターミナル1 の、トピックからロボットの記述を受け取った、という行は、コントローラマネージャも、create と同じトピック /robot_description から URDF を受け取ったことを示します。関節を読み込む、という行で、URDF の ros2_control の要素に書いた2つの関節が読み込まれ、サービスを始める、という行で準備ができます。ここに載せた行のほかに、WARN の行もいくつか出ますが、この体験では問題になりません。

ターミナル1 の画面では、腕は4-4節と違い、水平に伸びたまま止まっています。GazeboSimROS2ControlPlugin は、どのコントローラも指令を書いていない関節を、その場の角度に保ちます。これは hold_joints の設定で、既定で有効です。作るときには、create の5秒後に、Gazebo のトピック、つまり4-3節の JointStatePublisher が送る関節の状態に、2つの関節の角度の値が出ていないこと、この表示の形式では0 の値は省かれること、から、角度が0 のままであると判断した、とあります。

コントローラを読み込んで有効にします。ターミナル4 で、ros2 run controller_manager spawner に、joint_state_broadcaster と arm_position_controller を並べて実行します。

期待する結果です。サービスの list_controllers が使えるようになるのを待っている、という行が出ることがあり、続いて、joint_state_broadcaster を読み込んだ、設定して有効にした、arm_position_controller を読み込んだ、設定して有効にした、という行が出ます。

spawner、つまりスポナーは、コントローラマネージャのサービスを呼んで、名前を並べたコントローラを、順に読み込み、つまり Loaded、準備して有効にする、つまり Configured and activated、小さなプログラムで、終わると自分で終了します。ノードの名前は、最初に並べたコントローラの名前から付きます。2つとも、設定して有効にした、と出れば成功です。この時点では、位置のコントローラに、まだ目標が届いていないので、腕は水平のままのはずです。これは hold_joints の説明からの想定で、作るときには、この時点の角度を読んでいない、とあります。

位置のコントローラに、目標の角度を送ります。位置のコントローラは、トピックの、スラッシュ、コントローラの名前、スラッシュ commands で、関節の角度を、std_msgs の msg の Float64MultiArray、つまり数の並びとして受け取ります。並びの順は、設定のファイルの joints の順、つまり joint1、joint2 です。

ターミナル4 で、ros2 topic pub に --once を付けて、/arm_position_controller/commands に、Float64MultiArray で、data を0.5 とマイナス1.0 の並びにした値を送ります。

期待する結果です。少なくとも1つの、合う購読者を待っている、という行のあと、publisher がループを始めた、という行と、1番目の publish として、data が0.5 とマイナス1.0 の Float64MultiArray を送った、という行が出ます。1回だけ送って終わります。待っている、という行は、出ないことや、2回出ることもあります。ターミナル1 の画面では、link1 が水平から0.5ラジアン、つまり約29度下がり、link2 は link1 に対して1.0ラジアン、つまり約57度上に折れ、すぐに止まります。

ターミナル4 で、ros2 topic echo の /joint_states に --once を付けて、角度を読みます。

期待する結果です。header の stamp は、シミュレーションの時刻の19秒あまりで、frame_id は base_link です。name には joint1 と joint2 が並び、position は、約0.5000000000030748 と、約マイナス0.9999999999948956 です。velocity は、10 のマイナス14乗の、ほとんど0 の値で、effort は、どちらも nan、つまり値が無い、です。

読み方が2つあります。

1つ目。今度の /joint_states は、ブリッジでなく joint_state_broadcaster が送っています。並ぶのは、ros2_control の要素に書いた2つの関節だけで、固定の関節 fix_base は入りません。effort が nan なのは、状態のインターフェースにトルクを書いていないからです。frame_id の base_link は、joint_state_broadcaster の既定の値で、この体験では使いません。

2つ目。角度は、送った目標、つまり0.5 とマイナス1.0 に、小数第10位まで一致しています。4-4節では、重力と減衰の計算から止まる角度が決まり、手計算と小さくずれました。それと違い、ここでは、重力に逆らって、目標の角度にぴったり止まっています。

ぴったり止まるのは、GazeboSimSystem の角度の指令が、関節に力をかけるのでなく、関節の角速度を直接決めているからです。公式の説明によると、刻みごとに、角度の差かける position_proportional_gain、既定は0.1、かける update_rate、の角速度を関節に与えます。差が縮むほど遅くなり、目標に近づいていく動きで、時定数、つまり差が約37パーセントに縮むまでの時間は、1 割る、0.1 かける100、で0.1秒になります。角速度を直接決めるので、腕の重さや重力、関節の減衰は、止まる角度に効きません。

実機との違いの補足があります。実機のモータは、目標の角度にすぐには向かえず、重さや重力に応じたトルクを出しながら近づきます。シミュレーションでも、指令のインターフェースをトルク、つまり effort にし、コントローラの側に PID の係数を書けば、重さや重力を含めた動きになります。作るときには確かめていない、とあります。角度の指令は、動きが単純で扱いやすいので、この体験のように、まず関節を思いどおりに動かしてみるときや、物理の細部より上の層、たとえば動作計画を試すときに向きます。

### 5-4. 体験: 軌道のコントローラに切り替える

位置のコントローラは、目標を受けるとすぐにそちらへ向かうので、大きく離れた角度を送ると、腕が急に動きます。軌道のコントローラは、2秒後にこの角度、4秒後にこの角度、という点の並びを受け取り、間の角度を補間して、刻みごとに少しずつ指令を書きます。

2つのコントローラは、どちらも joint1 と joint2 の、角度の指令のインターフェースを使います。1つの指令のインターフェースは、1つのコントローラしか使えません。ros2_control は、これを claim、つまり確保と呼びます。そのため、位置のコントローラを有効にしたまま、軌道のコントローラを有効にすることはできません。位置のコントローラを止めて外してから、軌道のコントローラを読み込みます。

ターミナル4 で、ros2 run controller_manager unspawner に arm_position_controller を渡して実行し、そのあと、ros2 run controller_manager spawner に arm_trajectory_controller を渡して実行します。

期待する結果です。unspawner は、サービスの switch_controller が使えるようになるのを待っている、という行のあと、コントローラを無効にした、外した、という行を出します。spawner は、list_controllers を待っている、という行のあと、arm_trajectory_controller を読み込んだ、設定して有効にした、という行を出します。

unspawner は、spawner の逆で、コントローラを止めて、つまり Deactivated、外します、つまり Unloaded。外した後は、どのコントローラも指令を書かないので、腕は、5-3節の hold_joints のとおり、その場の角度に保たれます。

順番を逆にして、位置のコントローラを外す前に軌道のコントローラを読み込むと、spawner は、arm_trajectory_controller の有効化に失敗した、と表示して失敗し、ターミナル1 には、joint1 の position の指令のインターフェースが、ほかのコントローラに確保されているので、arm_trajectory_controller を有効にできない、という趣旨の行が出ます。作るときに確かめた、とあります。

軌道のコントローラは、アクションの、スラッシュ、コントローラの名前、スラッシュ follow_joint_trajectory で、型は control_msgs の action の FollowJointTrajectory で、軌道を受け取ります。アクションは、時間のかかる処理を頼み、終わったら結果を受け取る通信の形です。フェーズ3-5 で扱いました。任意の章なので、読んでいなければ、終わるまで待って結果が返るサービス、と考えればよい、とあります。次の軌道は、2秒後に、マイナス0.5 と1.0、4秒後に、0 と0 を通ります。

ターミナル4 で、ros2 action send_goal に、/arm_trajectory_controller/follow_joint_trajectory と、型の FollowJointTrajectory と、軌道を渡します。軌道は、joint_names に joint1 と joint2、points に2つの点、つまり positions がマイナス0.5 と1.0 で time_from_start が2秒の点と、positions が0.0 と0.0 で time_from_start が4秒の点、です。

期待する結果、最後の抜粋です。前に、送った目標の全体が表示されます。ゴールが ID 付きで受け付けられた、という行のあと、Result として、error_code が0、error_string が、ゴールに到達した、と出て、ゴールが SUCCEEDED の状態で終わった、と出ます。ID は実行ごとに違います。

ゴールが受け付けられ、約4秒後に SUCCEEDED、つまり成功と、error_code の0 が返れば成功です。ターミナル1 の画面では、腕が5-3節の姿勢から、2秒かけて、link1 が水平より上、つまりマイナス0.5ラジアン、link2 が下に折れた姿勢へ動き、さらに2秒かけて、水平に伸びた姿勢へ戻ります。

作るときに、動いている間の /joint_states を記録し、腕が動き始めてから0.5秒ごとに抜き出した表があります。経過の0秒から4.5秒まで、0.5秒ごとの10列で、行は joint1 と joint2 の2行です。角度の単位はラジアンで、小数第4位までに丸めてあります。原文の読み方が使う値を拾います。joint1 は、0秒で0.4995、2.0秒でマイナス0.4588、4.0秒でマイナス0.0205、4.5秒でマイナス0.0001 です。joint2 は、0秒でマイナス0.9990、2.0秒で0.9177、4.0秒で0.0409、4.5秒で0.0002 です。

読み方が2つあります。

1つ目。0秒から2秒の間、joint1 は、0.5秒ごとに約0.25ラジアンずつ、一定の速さ、つまり毎秒0.5ラジアンで変わっています。2秒から4秒の間も、別の一定の速さ、joint1 は毎秒0.25ラジアンで変わります。この軌道では、点ごとに角度だけを書き、角速度を書いていないので、軌道のコントローラは、点と点の間を直線でつなぎました。直線でつなぐと、点のところで速さが急に変わるので、公式の説明は勧めていない、とあります。点ごとに角速度も書くと3次の曲線で、さらに角加速度も書くと5次の曲線で、なめらかにつなぎます。

2つ目。2秒の時点の角度、マイナス0.4588 は、軌道の点のマイナス0.5 に届いていません。差の約0.04ラジアンは、毎秒0.5ラジアンで動く目標を、5-3節の時定数0.1秒の遅れで追いかけた分、約0.05ラジアンに近い値です。軌道のコントローラが書く指令は軌道の上にあり、GazeboSimSystem がそれを0.1秒ほど遅れて追います。4秒の時点も、同じ理由で0 に届かず、その後0.5秒ほどで0 に落ち着きます。

ros2 control のコマンドの補足があります。コントローラの一覧や状態は、ros2 control の list_controllers などのコマンドで見られますが、このコマンドは、5節の冒頭で入れたパッケージには含まれず、別のパッケージの ros-jazzy-ros2controlcli にあります。作るときの環境で確かめた、とあります。この章では使いません。

止めるときは、ターミナル3、2、1 の順に Ctrl+C で止めます。

## 6. この章のまとめ

まとめは7つです。

1つ目。Gazebo のワールドは、SDF で、ワールド、モデル、リンクと関節の入れ子に書きます。リンクは、慣性、つまり質量と慣性モーメント、衝突の形、見た目の3つを持ち、物理の計算に使うのは、慣性と衝突の形です。

2つ目。物理エンジン、既定は DART は、刻み幅、既定は0.001秒ごとに、まず速度を、次に位置を更新します。落下の位置は、この計算の式と、小数第6位まで一致しました。接触では、物どうしが数ミリ重なることを許し、少しずつ押し戻します。

3つ目。摩擦係数と反発係数は、衝突の形の surface に書きます。DART では、2つの面の摩擦係数は小さいほう、反発係数は積が使われます。坂で滑る距離と、跳ね上がる高さは、手計算と合いました。

4つ目。ばねとダンパーは、関節の軸の dynamics に、ばね定数、自然長の位置、減衰係数を書いて表します。吊るしたおもりの釣り合いの位置と揺れは手計算と合い、減衰の無いばねでも、刻み幅に比例して、揺れが少しずつ小さくなりました。

5つ目。ロボット1台は、ROS2 の道具と共通の URDF で書き、xacro で短く書いて展開します。Gazebo は、読み込むときに SDF に変換します。Gazebo 特有の設定は、gazebo の要素に書きます。

6つ目。create で URDF をワールドに出し、JointStatePublisher とブリッジで、関節の角度を ROS2 の /joint_states として読めました。関節の制限は正確に効き、止まった角度には、刻み幅に比例する小さなずれがありました。

7つ目。ros2_control は、コントローラ、つまり指令を計算する側と、ハードウェアの部品、つまり関節を読み書きする側を、インターフェースでつなぎます。URDF の ros2_control の要素に関節ごとのインターフェースを書き、Gazebo では GazeboSimROS2ControlPlugin がコントローラマネージャを動かします。コントローラは spawner で読み込んで有効にし、1つの指令のインターフェースは、1つのコントローラだけが使えます。GazeboSimSystem の角度の指令は、関節の角速度を直接決めるので、重力に関係なく目標の角度にぴったり止まり、時定数0.1秒、つまり position_proportional_gain の0.1 と update_rate の100ヘルツで決まる遅れで、目標を追います。軌道のコントローラは、点の間を補間した指令を書き、腕はそれを0.1秒ほど遅れて追いました。

## 7. つまずきやすい点

2列の表で、12行あります。列は、症状と、確かめることです。

1行目。gz sdf の -k がエラーを出す場合。要素のつづりと入れ子を確かめます。collision の中に geometry があるか、数の並び、つまり pose は6つ、箱の size は3つ、が合っているかを確かめます。

2行目。再生のボタンを押しても、何も落ちない場合。ワールドに gz-sim-physics-system の plugin があるか、つまり2-2節のとおりか、モデルに static の true を付けていないかを確かめます。

3行目。gz service が、サービスの呼び出しがタイムアウトした、になる場合。ワールド名、つまり world の名前の control の、名前の部分が、SDF の world の name と同じか、ターミナル1 で Gazebo が開いているかを確かめます。

4行目。gz model で読んだ位置が、表の値より手前の位置になる場合。multi_step は現実の時間の速さで進むので、進み終わる前に読んでいます。画面の動きが止まってから読みます。

5行目。跳ねるはずの球が跳ねない場合。相手、つまり地面の反発係数が0 のままでないかを確かめます。DART では、2つの積が使われます。3-3節のとおりです。

6行目。create が、robot_description のトピックでメッセージを待っている、で止まる場合。ターミナル2 の robot_state_publisher が動いているか、ターミナル2 の xacro の展開でエラーが出ていないかを確かめます。

7行目。アームが台ごと倒れる場合。URDF に world のリンクと、台へつなぐ固定の関節があるかを確かめます。4-3節のとおりです。

8行目。/joint_states に何も届かない場合。URDF の gazebo の要素に JointStatePublisher があるか、ターミナル3 のトピック名の、ワールド名の empty とモデル名の arm、つまり create の -name が合っているかを確かめます。4-4節のとおりです。5節では、spawner で joint_state_broadcaster を有効にしたかを確かめます。

9行目。spawner が、サービスの list_controllers を待っている、のまま進まない場合。コントローラマネージャが起動していません。ターミナル1 に、controller_manager を読み込む、が出ているか、出ていれば、サービスを始める、まで進んでいるかを確かめます。ターミナル2 の robot_state_publisher が動いていないと、URDF を待ち続けます。展開した URDF の parameters のパスに、設定のファイルがあるかも確かめます。

10行目。spawner が、コントローラの有効化に失敗した、で失敗する場合。ほかのコントローラが、同じ関節の指令のインターフェースを使っていないかを確かめます。5-4節のとおりです。失敗したコントローラは、読み込まれたまま、つまり読み込みの後の有効化だけが失敗した状態で残るので、ターミナル1 から4 をすべて止めてやり直し、先に unspawner で外してから読み込むのが確実です。

11行目。ターミナル1 に、clock を受け取っていない、という警告が続き、/joint_states の stamp が0 のままの場合。ターミナル3 の /clock のブリッジが動いているかを確かめます。5-3節のとおりです。

12行目。5節で、腕が4-4節のように垂れ下がる場合。ターミナル2 で展開しているのが arm_control.urdf.xacro かを確かめます。arm.urdf.xacro には、ros2_control の要素がありません。

## 8. 次へ

この章は任意の補足なので、本筋はフェーズ6-1 へ進みます。フェーズ7-3 では、フェーズ5-4 の車両の車輪の関節に、この章の4-3節と同じ考え方の減衰、つまり SDF では関節の axis の dynamics の中の damping の要素を足して使います。
