## 0. 学習目標と完了の条件

学習目標は4つです。

1つ目。PI 制御の式をやめ、観測から直接ペダルを選ぶ NN の方策を、Gazebo の車両で、SAC に学習させられる。

2つ目。学習した NN の方策の重みを、数の配列だけのファイル、つまり .npz に書き出し、numpy だけで方策を計算できる。pickle を含むファイルを読み込む危険と、allow_pickle を False にする意味を説明できる。

3つ目。行き過ぎの重みを変えると、NN の方策でも行き過ぎ量が変わることを、フェーズ6-3 の指標で確かめられる。

4つ目。学習した NN と PI 制御を、学習に使っていないシナリオで比べ、それぞれのよい点と弱い点を説明できる。

完了の条件は、5節の比較表を、自分で学習させた重みか、配布の重みで出し、NN と PI 制御の違いを、収益と指標で説明できることです。

## 1. 全体像

フェーズ5-2 の PI 制御は、偏差に比例して踏み、偏差の積み重ねに応じて踏み足す、という式でペダルを決めます。人が決めるのは、2つのゲインだけです。任意のフェーズ7-2 では、この2つを強化学習で選び、選ぶ数が2つだけなら、強化学習を使わずに、格子状に全部試す探索で十分なことを確かめています。強化学習が力を発揮するのは、選ぶものが多い場合や、状況に応じて選び直す場合です。このページでは、その形として、0.1秒ごとに、観測からペダルを直接選ぶ NN を学ばせます。観測は、フェーズ7-3 の4節の環境のとおり、目標、速度、偏差、前回のペダル、次の変わり目までの時間の5つです。PI 制御の式を使わないので、偏差に応じてどう踏むか、という構造そのものを、試行錯誤から学ぶことになります。

学習の舞台は、フェーズ7-3 で作った Gazebo の環境です。1本の学習、つまり110エピソード、9万9000ステップに、作成時は約1.6時間かかりました。フェーズ7-3 の5節の見積もりは、約1.7時間でした。このページでは、行き過ぎの重みを20 にした丸1 を学習させます。行き過ぎの重みを0 にした丸2 は、重みで振る舞いがどう変わるかを比べるためのもので、任意です。5節の比較には、丸2 の重みも使うので、学習させない場合は、4節で、作成時の丸2 の重みを置きます。

## 2. NN の方策と、重みの保存の形

### 2-1. NN の方策の形

SB3 の SAC の方策、つまり actor の NN は、フェーズ7-0 の5節で、振り子について見た形と同じです。違うのは、入口の数、つまり観測の数が5 になることだけです。

説明は3つです。

1つ目。観測5つから、256個の数を持つ層、また256個の数を持つ層、そして行動の中心の値 mu の1つ、という順に、掛け算と足し算と、ReLU、つまり負の値を0 にする関数を重ねます。

2つ目。最後に tanh、つまりどんな値もマイナス1 から1 に押し込む関数を通して、マイナス1 から1 のペダルにします。振り子では、この後に、トルクの範囲のマイナス2 から2 へ引き延ばしましたが、ペダルの範囲はマイナス1 から1 なので、そのまま使います。

3つ目。重みとバイアス、つまり足す数は、合わせて6万7585個あります。5 かける256 に256 を足したもの、256 かける256 に256 を足したもの、256 に1 を足したもの、の和です。PI 制御は、ゲインの2つの数で決まりました。

学習中は、SAC は、mu の周りにばらつかせた行動を試します。探索で、フェーズ7-0 の2-4節の話です。学習の後に方策として使うときは、ばらつかせず、mu に tanh を通した値だけを使います。predict の deterministic を True にする使い方です。つまり、学習した方策は、上の掛け算と足し算を、順に計算するだけの関数で、SB3 が無くても計算できます。

### 2-2. 重みを保存する2つの形

このページでは、学習したものを、次の2つの形で保存します。表は3列で、2行あります。列は、形、中身、何に使うか、です。

1行目は、SB3 の .zip で、model.save で作ります。中身は、方策、つまり actor と、価値の見積もり、つまり critic の NN、学習に使う最適化の状態、設定です。JSON で書けない値は、cloudpickle という方法で保存されます。学習の続きをするときや、SB3 の predict で使います。

2行目は、.npz で、numpy の np.savez で作ります。中身は、方策の各層の重みとバイアスの、6つの数の配列だけです。numpy だけで方策を計算するのに使い、配布もします。

.zip は、自分で学習させたものを、自分で読み込む分には便利です。一方、他の人から受け取った .zip は、読み込まないほうがよいです。cloudpickle は、Python の pickle を広げたものです。Python の公式の文書は、pickle は安全ではなく、細工されたデータを読み込むと、読み込むときに任意のコードが実行されうるので、信頼できないデータを読み込まないように警告しています。

.npz は、数の配列をまとめたファイルです。numpy の np.load に、allow_pickle を False にして渡すと、pickle を使った配列を読み込もうとしたときにエラーになり、数の配列だけを読みます。numpy の既定の値も、False です。作成時に学習させた重みを配るときは、このページでは .npz の形にしました。4節の話です。

.npz を使う理由は、もう1つあります。方策を使う側、つまり5節の比較と、フェーズ7-5 の ROS2 のノードが、SB3 と PyTorch を読み込まずに、numpy だけで動くことです。

## 3. SAC で学習させる

### 3-1. 学習のスクリプト、train_gz.py

条件、たとえば行き過ぎの重みを、コマンドの引数で切り替えられる、学習のスクリプトを作ります。

ファイルは、ホームの rl_practice の train_gz.py です。

50行ほどのコードで、ブロックは4つと、最後に main を呼ぶ2行です。4つのブロックは、import、定数、方策の重みを書き出す export_policy、そして main です。ファイルの先頭のコメントには、Gazebo のペダルの環境で SAC を学習させ、10エピソードごとに途中経過を表示して、モデルと方策の重み、つまり .npz を保存する、とあります。import では、argparse、time、numpy、SB3 の SAC、gz_pedal_env から CONTROL_INTERVAL と GazeboPedalEnv、vehicle_env から EPISODE_LENGTH を読み込みます。定数は2つで、1エピソードのステップ数の EPISODE_STEPS、つまり900 と、途中経過を表示して保存する間隔の REPORT_EPISODES、つまり10エピソードです。

要の行は1か所で、main の繰り返しの中の、途中経過を表示する行です。行の最後で flush を True にして、表示をためずに、すぐに画面に出します。

train_gz.py の解説は、9つです。

1つ目は、引数です。Python 標準の argparse で、コマンドの引数を受け取ります。マイナス2つの weight は行き過ぎの重みで、既定は20 です。マイナス2つの episodes は学習させるエピソードの数で、既定は110 です。10 の倍数で指定します。マイナス2つの seed は学習の乱数の種で、既定は0 です。報酬の倍率の10倍と、偏差を毎秒メートルのまま渡すことは、フェーズ7-3 の環境の既定のままにします。理由は、フェーズ7-3 の4節の、報酬と観測、の話です。

2つ目は、ステップの数です。1エピソードは、0.1秒ごとに90秒分で900ステップなので、110エピソードは、9万9000ステップ、つまり約10万になります。フェーズ7-3 の5節の見積もりは約1.7時間で、作成時の実測は約1.6時間でした。

3つ目は、NN の更新の回数です。SAC を作るときに gradient_steps を渡さず、SB3 の既定、つまり環境を1ステップ進めるごとに1回更新、のままにします。SB3 の SAC は、最初の100ステップは経験をためるだけで更新しません。learning_starts の既定です。なので、110エピソード、約9万9000ステップで、更新は約9万9000回になります。フェーズ7-0 の振り子、つまり2万ステップで約2万回より多いです。1ステップに時間がかかり、ステップの数を多くできない環境では、gradient_steps を増やして、1ステップごとに NN を何回も更新させ、同じ経験から多くを学ばせる方法もあります。1ステップが90秒分のシミュレーションの環境で、任意のフェーズ7-2 の4-3節が試しています。

6つ目は、エントロピーの係数、つまり ent_coef の列です。SAC が、探索のばらつき、つまりエントロピーを、どれだけ重く見るかを表す数です。フェーズ7-0 の2-4節の話です。SB3 の SAC は、既定では、この係数を1.0 から始め、学習の中で自動で調整します。調整の向きは、方策のばらつきを測った数、つまりエントロピーが、目標の値より大きければ係数を下げ、小さければ上げる、というものです。目標の値は、既定では、行動の数のマイナスで、この環境ではマイナス1 です。連続の値の行動では、ばらつきが小さいと、エントロピーは負の数になるので、目標も負の数で表します。model.log_ent_coef は係数の対数なので、exp で元の数に戻します。detach と item は、NN の学習の計算から切り離して、ふつうの数として取り出すための書き方です。

2つ目は、定常偏差が残る、ということです。NN の定常偏差の大きさは、毎秒0.57メートルと0.78メートルで、PI 制御の毎秒0.050メートルの、10倍以上あります。段の最後になっても、目標にぴったりは合いません。PI 制御は、積分の項、つまり偏差の積み重ねで、定常偏差を0 に近づけます。NN の方策は、その時点の観測だけからペダルを決めるので、積み重ねを覚える仕組みがありません。フェーズ7-3 の4節の、報酬と観測、の話です。

3つ目は、丸1 の NN は、ペダルを細かく動かし続ける、ということです。ペダルの動いた量は、PI 制御の18.4 に対して、丸1 の NN は92.6 と、約5倍です。目標の近くで、ペダルを細かく行き来させていて、なめらかに落ち着きません。

4つ目は、重みで、行き過ぎ量が変わる、ということです。行き過ぎ量は、重み20 の丸1 の NN が20.4パーセント、重み0 の丸2 の NN が30.2パーセントで、行き過ぎを重く減点した NN のほうが、行き過ぎが小さいです。ただし、1回ずつの学習の比較なので、差の大きさまでは信用できない、とあります。6節の話です。収益も、丸1 の NN は重み20 の収益で、丸2 の NN は重み0 の収益で、相手を上回ります。それぞれ、学習した報酬で測ると、自分のほうがよいです。

5つ目は、ただし、追従の速さとのトレードオフは、フェーズ6-3 の指標では、はっきりしない、ということです。報酬の重みを上げると、ふつうは、行き過ぎが減る代わりに、目標へ近づくのが遅くなる、つまり RMS が増えます。追従の速さと行き過ぎの、一方をよくすると他方が悪くなる関係、つまりトレードオフです。PI 制御のゲインを選ぶ任意のフェーズ7-2 の5節では、この関係がはっきり出ました。このページでは、RMS も、丸1 の NN のほうが小さく、よいです。丸2 の NN が上回るのは、重み0 の収益だけで、これには、フェーズ6-3 の指標が数えない最初の10秒、つまり止まった状態から最初の目標へ加速する段が含まれます。5-1節の run の解説の話です。6節のとおり、1回ずつの学習の比較なので、差の大きさまでは信用できません。

6つ目は、比べた PI 制御は、手で決めた既定のゲインだ、ということです。PIPolicy のゲインは、フェーズ5-2 で手で決めた既定の値、つまり kp 0.5、ki 0.1 で、任意のフェーズ7-2 で、格子の探索と強化学習が見つけたゲインではありません。重み20 の場合の、kp 0.3 から0.4、ki 0.025 前後のゲインです。フェーズ7-2 のゲインは、Python の式の環境で、落ち着いた状態から始め、PI 制御を0.02秒ごとに計算する条件で選んだものなので、このページの Gazebo の環境、つまり止まった状態から始め、0.1秒ごとに計算する環境でも、最もよいとは限りません。フェーズ7-2 のゲインを使えば、PI 制御の行き過ぎ量は小さくなり、重み20 の収益での NN との差は広がる見込みだが、作成時には確かめていない、とあります。比べる相手を変えるときは、PIPolicy の中で PIController を作る行のゲインを書き換えます。

PI 制御は、偏差に比例して踏み、偏差の積み重ねに応じて踏み足す、という、追従のための構造を、最初から持っています。NN は、この構造を何も知らない状態から、約110エピソードの試行錯誤だけで、観測からペダルへの対応を、一から学びます。人がよい構造を知っている問題では、その構造を使うほうが、少ない手間でよい結果が出ます。この結論は、任意のフェーズ7-2 の、選ぶ数が2つだけなら、格子の探索で十分、とも同じ向きです。NN の方策を改良するときに試せることは、原文のリポジトリに没案として残したページの6節と7節にまとめてある、とあります。たとえば、PI 制御の出力に NN の補正を足す、PI 制御をまねることから学び始める、記憶を持つ方策を使う、などです。Python の式の環境での試行ですが、考え方は同じだ、とあります。

## 6. 補足、学習の結果は、PC や実行ごとに変わる

自分で学習させた結果は、3節の期待する結果や、配布の重みと同じにはならないことが多いです。学習の乱数の種、つまりマイナス2つの seed を固定していても、次の2つのことで、学習の道筋が変わるためです。

1つ目は、計算に使うスレッドの数や PC です。計算の順番がわずかに変わり、小数の丸めの違いが、学習の中で積み重なります。

2つ目は、Gazebo とのやりとりの時機です。トルクの指令が Gazebo に届く時機によって、計算がわずかに変わることがあります。フェーズ7-3 の4節の末尾の補足の話です。学習では、その小さな違いも、学習の道筋を変えるきっかけになります。

作成時にも、丸1 を、同じ PC、同じ版、同じ種の0 で2回学習させると、途中経過がまったく違った、とあります。1回目の重みは、作成の途中で失ったので、配布していません。3節の期待する結果は、2回目のものです。1回目は、10エピソードでマイナス6714、20 でマイナス148、60 から90 でマイナス66 からマイナス76、最後の110 でマイナス519 でした。2回目の値は、3-2節の読み方のとおりです。1回目の最後の重みを、5節と同じ確かめ用のシナリオで走らせた、重み20 の収益は、マイナス35.26 で、2回目、つまり5-2節の NN w20 の値と違いました。Python の式の環境なら、同じ PC、同じ版、同じ種で、同じ結果になります。フェーズ7-1 の冒頭の注記の話です。Gazebo の環境では、やりとりの時機の小さな違いだけで、学習の道筋が変わったと考えられる、とあります。

また、作成時に、Python の式の環境で、同じ形の学習を試したときは、同じ設定でも、種やスレッドの数を変えるだけで、10万ステップの収益が数倍違った、とあります。原文のリポジトリに没案として残したページの4節の話です。設定の良し悪しを数で比べるには、条件をそろえ、種を変えて何回か学習させて、ばらつきの大きさと比べる必要があります。Gazebo の環境では、1本に約1.6時間かかるので、このページでは、丸1 と丸2 を1回ずつ学習させるだけにしました。5節の丸1 と丸2 の違いのうち、小さな差は、偶然の可能性があります。

## 7. 本フェーズのまとめ

5つあります。

1つ目。PI 制御の式をやめ、0.1秒ごとに観測からペダルを直接選ぶ NN の方策を、Gazebo の車両で、SAC に学習させました。1本の学習、つまり110エピソードは、作成時に約1.6時間かかりました。

2つ目。Gazebo の環境は1つしか作れないので、途中経過は、学習中のエピソードの収益で見ました。学習中の収益は、探索のばらつきを含むので、方策の良し悪しは、ばらつきを入れずに、決まったシナリオで走らせて確かめます。

3つ目。学習した方策は、掛け算と足し算と、ReLU と tanh を重ねるだけの関数なので、重みを数だけの .npz に書き出せば、numpy だけで計算できます。pickle を含むファイル、つまり SB3 の .zip は、信頼できない相手から受け取ったものを、読み込みません。.npz は、allow_pickle を False にして読みます。

4つ目。学習した NN は、目標を追いかけることはできますが、PI 制御には届きません。定常偏差が残り、ペダルを細かく動かし続けます。行き過ぎの重みを20 にした NN は、0 にした NN より、行き過ぎが小さかったです。ただし、1回ずつの学習なので、差の大きさまでは信用できません。6節の話です。また、PI 制御のゲインを選ぶ場合、つまり任意のフェーズ7-2 のような、追従の速さとのトレードオフは、フェーズ6-3 の指標では、はっきり見えませんでした。

5つ目。Gazebo の環境の学習は、同じ種でも、実行ごとに途中経過が変わります。設定の良し悪しを数で比べるには、何回か学習させて、ばらつきの大きさと比べる必要があります。
