# フェーズ7-3: Gazebo で学習する環境を作る（聞くための原稿）

これは、ros2MinimalPhysicalAi という教材の、フェーズ7-3 の手順書の話です。学習計画のフェーズ7 の7-3、元のアイデアのステップ6 に当たります。フェーズ7-1 では、ROS2 を使わない Python の車両の式で、方策がペダルを直接選ぶ環境を作りました。次のフェーズ7-4 では、PI 制御の式そのものをやめ、ペダルを直接選ぶニューラルネットワーク、つまり NN の方策を学習させます。その学習の舞台を、フェーズ5-4 で作った Gazebo の物理にします。このページでは、その準備として、フェーズ7-1 と同じ形の環境、つまり同じ観測、行動、報酬、シナリオの環境を、Gazebo の車両で作ります。Gazebo を一時停止した状態から少しずつ進め、ROS2 のトピックとサービスで車両を動かし、速度を受け取ります。

想定する環境は、WSL2 と Ubuntu 24.04 と ROS2 Jazzy で、Gazebo は Harmonic です。前提は3つです。1つ目はフェーズ7-1 で、ホームの rl_practice に vehicle_env.py があることです。任意のフェーズ7-2 は、読んでいなくてかまいません。2つ目はフェーズ5-4 で、learn_bringup に worlds の vehicle_force.sdf があり、learn_py に actuator_model.py があることです。3つ目は、強化学習の環境構築の7節で、仮想環境から rclpy を読み込めることです。所要時間の目安は2コマで、計算を待つ時間が、課題を除いて5分程度あります。言語は Python で、launch も Python の形式です。ほかに、ワールドファイルを書きます。

この手順書の位置づけの囲みです。フェーズ7、つまり7-0 から7-6 は、ひととおり作成を終えた段階で、今後の見直しで内容を改めることがある、とあります。

進め方の囲みです。1節で、なぜ Gazebo で学習させるのかと、そのための仕組みの全体像を見ます。2節で、学習用のワールドを作ります。フェーズ5-4 のワールドに、速度に比例する抵抗を足します。3節で、Gazebo を一時停止した状態から少しずつ進める仕組みを、launch とコマンドで確かめます。4節で、その仕組みを使う強化学習の環境のクラスを書き、5節で点検して、学習にかかる時間を見積もります。サンプルは、学習の手がかりとして最小限に書いたもので、公式の文書の転載ではない、とあります。

期待する結果の出どころの囲みもあります。2-3節の gz sdf のマイナス k とビルド、3-1節の ros2 interface show は、使い捨ての環境で実際に実行した表示です。3-2節の起動のログ、3-3節、5-2節は、使い捨ての環境で画面なしの Gazebo を起動し、実際に実行した表示です。2026年10月6日の時点で、SB3 2.9.0、Gymnasium 1.3.0 です。作成時は、フェーズ7-1 と同じく、learn_py は、ワークスペースをビルドする代わりに、同じファイルを置いたフォルダを PYTHONPATH に加えて読み込み、learn_bringup だけを、使い捨てのワークスペースでビルドしました。行頭の時刻、プロセスの番号、ビルドの秒数と、5-2節の time[s] と ms/step の列は、実行ごとに変わります。5-2節の速度と収益は、作成時に2回続けて実行して、同じ値になることを確かめた、とあります。ただし、トルクの指令が Gazebo に届く時機によって、わずかに変わる可能性はあります。4節の末尾の補足の話です。

## 0. 学習目標と完了の条件

学習目標は5つです。

1つ目。物理シミュレータを強化学習の環境にするときに要る3つのこと、つまりエピソードの始めに元に戻す、決まった時間だけ進める、進めた後の状態を受け取る、を説明できる。

2つ目。Gazebo のワールドを操作するサービスで、一時停止した Gazebo を決まった回数だけ進め、リセットできる。

3つ目。フェーズ5-1 の速度に比例する抵抗を、縮尺を使って、Gazebo の車輪の関節の減衰に直せる。

4つ目。Gymnasium の環境の中に ROS2 のノードを持たせ、check_env で点検できる。

5つ目。Gazebo の環境の速さを測り、学習にかかる時間を見積もれる。

完了の条件です。5節の点検のスクリプトで、check_env が通り、ペダル0.5 を踏み続けた速度が、毎秒約10.7メートルで頭打ちになり、PI 制御で走らせた収益と、1エピソードにかかる時間を確かめること。そのうえで、フェーズ7-4 の学習、つまり10万ステップにかかる時間を見積もれることです。

## 1. 全体像

フェーズ7-1 では、Python の車両の式、つまりフェーズ5-1 の VehicleModel で環境を作りました。式なら、90秒分の1エピソードを、0.1秒程度で計算できます。一方、フェーズ5-4 では、同じゲインの PI 制御でも、自作の式と Gazebo の物理とで、追従が変わることを見ました。式で学んだものは、式とは違う物理の上では、そのまま通用するとは限りません。実物のロボットでも、シミュレーションで学んだものを実物に移すと、同じ問題が起きます。

それなら、最初から、より現実に近い物理の上で学ばせればよい。このページと次のフェーズ7-4 では、NN の方策を、Gazebo の車両で直接学習させます。代わりに、学習には時間がかかります。Gazebo は、画面を出さずにできるだけ速く回しても、物理の計算だけで現実の約3倍の速さ、ROS2 とやりとりしながら少しずつ進めると、約2倍の速さだった、とあります。作成時に測った値で、PC によって変わります。このページの環境の速さは、5節で測ります。たとえば、1000エピソードの学習を何本も行うと、それだけで半日以上かかります。そこで、環境の設計、つまり観測、行動、報酬は、すぐに結果が出るフェーズ7-1 の式の環境で確かめておき、このページでは、同じ形の環境を、車両の計算だけ Gazebo に任せて作ります。5節では、同じ方策、つまり PI 制御を、式の環境と Gazebo の環境で走らせ、物理の違いで、収益がどれだけ変わるかを比べます。

強化学習の環境には、次の3つが要ります。

1つ目は、リセットです。エピソードの始めに、車両を、元の場所の止まった状態に戻します。

2つ目は、決まった時間だけ進めることです。方策がペダルを選んだら、物理を0.1秒分だけ進めて止めます。方策が考えている間に、車両が勝手に走り続けてはいけません。

3つ目は、進めた後の状態を受け取ることです。0.1秒分を進め終わった時点の速度を、観測として返します。

フェーズ5-4 の launch では、Gazebo は、現実の時間に合わせて、自分のペースで進み続けていました。このページでは、Gazebo を一時停止した状態で起動し、ワールドを操作するサービスで、何回分進めるか、リセットするか、を指示します。進め終わったかどうかは、オドメトリに付いている時刻、つまりシミュレーション時刻で確かめます。

ここに図が1枚あります。SVG と mermaid の版がありますが、内容は同じです。

図の左に、薄い青の箱があり、点検のスクリプト、5節、check_gz_env.py、7-4 では SAC、と書いてあります。図の真ん中には、灰色の破線の枠があり、見出しは、強化学習の環境 GazeboPedalEnv、gz_pedal_env.py です。枠の中には、薄いオレンジ色の箱が1つあり、ROS2 のノード gz_pedal_env、0.02秒ずつ進め、オドメトリの時刻で待つ、と書いてあります。図の右には、もう1つ、灰色の破線の縦長の枠があり、見出しは、gazebo_rl.launch.py、learn_bringup です。枠の中には、薄い緑の箱が上下に2つあります。上の箱は parameter_bridge、下の箱は、gz sim、画面なし、一時停止、vehicle_rl.sdf、車輪の関節に減衰、と書いてあります。

矢印です。点検のスクリプトと環境の枠の間には、実線の矢印が2本あります。上の矢印は、スクリプトから環境へ向かい、ラベルは、ペダル、0.1秒ごと、です。下の矢印は、環境からスクリプトへ向かい、ラベルは、観測と報酬です。ノードの箱と parameter_bridge の箱の間には、実線の矢印が3本あります。上の2本は、ノードからブリッジへ向かい、ラベルは、車輪のトルク、Float64 と、ワールドの操作、ControlWorld です。いちばん下の1本は、ブリッジからノードへ向かい、ラベルは、オドメトリ、Odometry です。parameter_bridge の箱と gz sim の箱の間は、両向きの矢印でつながっています。

まとめると、強化学習の環境 GazeboPedalEnv が、中に持つ ROS2 のノードから、車輪のトルクのトピックと、ワールドの操作のサービスを、ブリッジ経由で Gazebo へ送り、オドメトリを受け取る。Gazebo は、画面なし、一時停止で起動し、サービスで指示された回数だけ物理を進める。環境は0.02秒ずつ進め、オドメトリの時刻で進み終わりを確かめる。5節の点検のスクリプトと、フェーズ7-4 の SAC は、環境にペダルを渡し、観測と報酬を受け取る、という図です。

## 2. 学習用のワールド

### 2-1. なぜ抵抗を足すのか

フェーズ5-4 の7節で見たとおり、フェーズ5-4 のワールドの車両は、転がっても、ほとんど抵抗を受けません。ペダルを踏み続けると、速度はどこまでも上がっていきます。作成時に、このワールドのまま NN を学習させてみると、学習の初めのでたらめなペダルで速度が大きく外れ、誤差の2乗がとても大きな値になって、2万ステップ学習させても、収益がよくならなかった、とあります。このワールドでの PI 制御の収益の、2000倍ほど悪いままだった、とあります。

自作の式、つまりフェーズ5-1 には、速度に比例する抵抗があり、アクセル全開でも、毎秒約20メートルで頭打ちになりました。同じ性質を Gazebo の車両にも持たせると、同じ量の学習で、収益が PI 制御に近づいた、とあります。そこで、フェーズ5-4 のワールドを写し、車輪の関節に減衰を入れたワールドを、学習用にします。減衰は、回る速さに比例して、回転を止める向きに働くトルクです。

### 2-2. 減衰の大きさを、縮尺から求める

フェーズ5-1 の速度に比例する抵抗は、c かける v でした。c は、毎秒1メートルあたり140ニュートンです。これを、フェーズ5-4 の3節の縮尺で、Gazebo の単位に直します。速度は、Gazebo では s 倍、s は0.025 です。力は f 倍、f は1.9 かける10 のマイナス4乗で、フェーズ5-4 の3-2節の力の縮尺です。実車の速度 v のときの抵抗 c v は、Gazebo では力 f c v で、そのときの Gazebo の速度 v gz は、s かける v です。力を Gazebo の速度で書き直すと、f c v イコール、f c を s で割ったものかける v gz なので、Gazebo の単位での抵抗の係数は、次のとおりです。

式は、c gz イコール、c かける、f を s で割ったもの、つまり、140 かける、1.9 かける10 のマイナス4乗を0.025 で割ったもので、毎秒1メートルあたり約1.06ニュートン、です。

車輪の関節の減衰 d は、関節の回る速さ、オメガ、つまり毎秒何ラジアン回るかに比例するトルク、d かけるオメガを生みます。半径 r、つまり0.3メートルの車輪が、滑らずに転がるとき、オメガは v を r で割ったもので、トルクを車輪の縁の力に直すと、d かけるオメガを r で割ったもの、つまり d かける v を、r の2乗で割ったものになります。左右の2つの車輪の分を足して、c gz かける v に等しくすると、次のようになります。

式は、d イコール、c gz かける r の2乗を2 で割ったもの、つまり、1.06 かける0.3 の2乗を2 で割ったもので、約0.048 です。単位は、ニュートンメートル秒毎ラジアン、つまり毎秒1ラジアンあたり0.048ニュートンメートルのトルクです。

フェーズ5-1 の転がり抵抗、つまり速さによらない一定の抵抗は、足しません。そのため、ペダル0.5 を踏み続けたときに落ち着く速さは、フェーズ5-1 の毎秒9.14メートルより少し速い、0.5 かける3000 を140 で割った、毎秒約10.7メートルになり、アクセル全開では、毎秒約21.4メートルになります。速度の時定数、つまりフェーズ5-1 の2-3節の、T イコール m を c で割ったもの、は、フェーズ5-1 と同じ約10.7秒になる見込みです。力の縮尺 f は、フェーズ5-4 の3-2節で、Gazebo の有効質量 m gz を使って、f イコール、m gz かける s を m で割ったもの、と決めました。なので、Gazebo での時定数、つまり m gz を c gz で割ったものは、m gz かける s を、f かける c で割ったものになり、m を c で割ったものと等しくなるからです。5節で確かめます。

### 2-3. ワールドファイルを写して書き換える

フェーズ5-4 のワールドを写します。cp で、ホームの ros2_ws の src の learn_bringup の worlds の vehicle_force.sdf を、同じフォルダの vehicle_rl.sdf に写します。

写した vehicle_rl.sdf を、エディタで、次の3か所だけ書き換えます。

1か所目は、ファイルの先頭のコメントです。出典と変更点を書いたものにします。コメントは5行で、内容は、フェーズ7-3 用のワールドで、フェーズ5-4 の vehicle_force.sdf の緑の車両の車輪に減衰を足したこと、出典は Gazebo Sim 8 に付属する worlds の diff_drive.sdf で、Apache License 2.0 であること、そして変更点です。変更点は、ワールド名を vehicle_rl にしたこと、緑の車両の DiffDrive プラグインを、左右の車輪の ApplyJointForce と OdometryPublisher に差し替えたこと、これはフェーズ5-4 の変更です。そして、緑の車両の左右の車輪の関節に、減衰の damping 0.048 を足したこと、これはフェーズ7-3 の変更です。

2か所目は、ワールドの名前です。元は vehicle_force で、world の要素の name を vehicle_rl に変えます。ワールドの名前は、3節のサービスの名前、つまりスラッシュ world、スラッシュ vehicle_rl、スラッシュ control の一部になります。

3か所目は、緑の車両の左右の車輪の関節です。vehicle_green というモデルの中の、left_wheel_joint と right_wheel_joint の関節に、減衰の行を1行ずつ足します。それぞれの関節の axis の要素の中にある、limit の閉じのタグの次の行、つまり axis の閉じのタグより前に書きます。足す1行は、dynamics の要素の中に、damping の要素を置き、値を0.048 にしたものです。青の車両の関節は変えません。書き足した後の関節の終わりは、limit の閉じのタグ、足した行、axis の閉じのタグ、joint の閉じのタグ、の順に並びます。

書き換えたら、ファイルの書き方に誤りがないかを確かめ、ワールドを足した learn_bringup を、ビルドし直します。仮想環境を有効にしていないターミナルで行います。gz sdf のマイナス k で vehicle_rl.sdf を点検し、cd でホームの ros2_ws に移り、colcon build を、マイナス2つの symlink-install と、マイナス2つの packages-select の learn_bringup を付けて実行し、source で install の setup.bash を読み込みます。

期待する結果です。gz sdf の後に1行、colcon build の後に、始まりの行、終わりの行、空行、まとめの行が出ます。ビルドの秒数は、実行ごとに変わります。

読み方です。gz sdf の後に Valid. と出れば、SDF として正しく読めます。colcon build の後に、Finished と learn_bringup の行が出れば、ビルドできています。ワールドファイルは、フェーズ5-4 で、CMakeLists.txt の install の DIRECTORY に worlds を足してあるので、ビルドすると、install の中に、元のファイルを指すリンクができます。マイナス2つの symlink-install のためです。新しいファイルを足したときは、リンクを作るために、ビルドし直します。すでにリンクのあるファイルを書き換えただけなら、ビルドし直さなくてかまいません。

## 3. Gazebo を少しずつ進める仕組み

8つ目は、報酬と観測です。フェーズ7-1 の環境と同じです。報酬は、フェーズ7-1 と同じ式で、reward_scale、既定の10 を掛けて返します。観測の偏差は、error_scale、既定の毎秒1メートルで割ります。つまり毎秒メートルのままです。報酬を10倍にし、偏差を毎秒メートルのまま渡す理由は、フェーズ7-1 の2-2節と2-5節にあります。観測の5つ、つまり目標、速度、偏差、前回のペダル、次の変わり目までの時間を選んだ理由も、フェーズ7-1 の2-2節にあります。

トピックとサービスの順番について、補足の囲みがあります。3つの点です。

1つ目は、一般的なことです。トルクのトピックと、ワールドを操作するサービスは、ブリッジの中の別々の通り道を通ります。送った順番に、Gazebo に届くとは限りません。

2つ目は、このサンプルの扱いです。トルクを送ってから、サービスで進める順にしています。まれに、トルクが Gazebo に届く前に計算が進んだとしても、ずれるのは1回分、つまり0.02秒で、学習への影響は小さいと考えて、待ち合わせは入れていない、とあります。

3つ目は、実務の目安です。指令が確実に効いてから進めたい場合は、指令もサービスで送る、つまり応答を待てる形にするか、Gazebo のプラグインとして、指令と計算を同じ場所で扱う方法がとられます。

### 5-1. 点検のスクリプト、check_gz_env.py

ファイルは、ホームの rl_practice の check_gz_env.py です。

50行ほどのコードで、ブロックは4つと、最後に main を呼ぶ2行です。4つのブロックは、import、PI 制御で走らせるシナリオの種の定数 SEEDS、PI 制御で1エピソード走らせて収益を返す run_pi、そして main です。import では、time、numpy、SB3 の check_env、gz_pedal_env から CONTROL_INTERVAL と GazeboPedalEnv、learn_py の pi_control から PIController を読み込みます。SEEDS は、0、1、2 の3つです。main は、点検の結果、ペダル0.5 を踏み続けた速度、PI 制御の収益と1エピソードの時間を表示し、最後に環境を close します。

要の行は1か所で、ペダル0.5 で進める繰り返しの中で、100ステップごとに、経過の秒数と、環境が最後に受け取った速度 velocity を表示する行です。表示するのは、観測ではなく、環境が覚えている、実車の単位の速度です。

check_gz_env.py の解説は、4つです。

1つ目は check_env です。SB3 の環境の点検で、フェーズ7-1 の5-1節の話です。フェーズ7-1 と同じく、問題が無ければ、何も表示しません。観測と行動の範囲や、reset と step の返す値の形を確かめます。中で何回か reset と step を呼ぶので、Gazebo も少し動きます。

2つ目は、ペダル0.5 を踏み続けることです。止まった状態から60秒間、つまり600ステップ、ペダル0.5 のまま進め、10秒ごとに速度を表示します。2-2節の見込み、つまり毎秒約10.7メートルで頭打ち、時定数約10.7秒を確かめます。

3つ目は run_pi です。フェーズ5-2 の PIController を、0.1秒ごとに計算する形で使います。方策を、観測からペダルを返すもの、と見て、PI 制御を当てはめます。観測の1つめと2つめは、目標と速度を10 で割ったものなので、10 を掛けて戻します。

4つ目は、時間を測ることです。1エピソード、つまり900ステップにかかった現実の秒数と、1ステップあたりのミリ秒を表示します。経過時間は、時計の飛び、つまり PC の時刻合わせの影響を受けない、time.monotonic で測ります。

### 5-2. 動かす

T1 で Gazebo を起動し、T2 で点検のスクリプトを動かします。T2 は、強化学習の仮想環境を有効にしたターミナルです。フェーズ7-1 の3節の準備の話です。

T1 では、cd でホームの ros2_ws に移り、source で install の setup.bash を読み込み、ros2 launch で、learn_bringup の gazebo_rl.launch.py を起動します。T2 では、source で、ホームの ros2_ws の install の setup.bash を読み込み、source で、ホームの rl_venv の bin の activate を読み込み、cd でホームの rl_practice に移り、python で check_gz_env.py を実行します。

T2 は、4分程度かかります。終わったら、T1 を Ctrl+C で止めます。

期待する結果です。T2 の分で、time[s] と ms/step の列は、実行ごとに変わります。最初に、check_env: OK の1行が出ます。続いて、ペダル0.5 の速度の行が、10秒から60秒まで、10秒ごとに6行出ます。最後に、見出しの行のあと、種0、1、2 の3行が出ます。各行は、種、収益、1エピソードの秒数、1ステップあたりのミリ秒です。

読み方は5つです。

1つ目は、check_env: OK です。SB3 の点検で、警告もエラーも出ませんでした。

2つ目は、ペダル0.5 の速度です。60秒で毎秒10.65メートルと、2-2節の見込みの、毎秒約10.7メートルで頭打ちになります。10秒での毎秒6.29メートルは、毎秒10.7メートルの約59パーセントで、速度の時定数、つまり約10.7秒で約63パーセントに達する、一次遅れの形に近いです。少し遅いのは、アクセルの力の立ち上がりにも、0.5秒の遅れがあるためです。減衰が、フェーズ5-1 の速度に比例する抵抗と、同じ働きをしています。

3つ目は、PI 制御の収益です。シナリオ、つまり種によって、マイナス23.29 からマイナス41.98 と違います。目標の変わり方が、シナリオごとに違うためです。この収益は、フェーズ7-1 の環境と同じ報酬、つまり10倍、同じ始め方、つまり止まった状態、同じシナリオで測った値なので、フェーズ7-1 の5-1節の最後の行、つまり式の環境の、同じ種の PI 制御の収益と比べられます。任意のフェーズ7-2 の収益は、報酬が1倍で、落ち着いた状態から始めるので、比べられません。フェーズ7-4 では、この PI 制御の収益を、NN と比べる基準にします。

4つ目は、式の環境との比較です。同じ PI 制御、同じシナリオで、式の環境、つまりフェーズ7-1 は、種0 から2 で、マイナス46.61、マイナス35.45、マイナス23.51 でした。Gazebo の環境は、種0 がマイナス41.98、種1 がマイナス32.73、種2 がマイナス23.29 でした。Gazebo のほうが、種0 で約10パーセント、種1 で約8パーセントよく、種2 はほぼ同じです。同じ方策でも、物理、つまり式と Gazebo が違えば、収益が変わります。式と Gazebo では、抵抗のかかり方や、計算の刻みが違います。Gazebo には、フェーズ5-1 の転がり抵抗に当たるものが無く、速度に比例する抵抗は、車輪の関節の減衰で近づけています。2-2節の話です。計算の刻みは、ブレーキやアクセルの遅れを、式は0.01秒ごと、このページは0.02秒ごとに計算します。どれがどれだけ効いているかは、作成時には切り分けていない、とあります。式で学ばせた方策を、そのまま Gazebo や実物に移すと、こうした違いの分だけ、結果が変わります。このページとフェーズ7-4 で、Gazebo の上で直接学ばせるのは、このためです。1節の話です。

5つ目は、1エピソードの時間です。900ステップ、つまりシミュレーションの90秒に約42秒、1ステップ、つまり0.1秒に約47ミリ秒かかりました。現実の約2倍の速さです。Python の式の環境、つまりフェーズ7-1 なら、1エピソードは一瞬で終わります。

フェーズ7-4 の学習は、10万ステップ、つまり約111エピソードを予定しています。環境を進めるだけで、10万かける0.047 で、約4700秒、つまり約78分かかります。これに、NN の更新の時間が加わります。作成時に、Python の式の環境で、同じ設定の SAC を動かして測ると、1ステップあたり約13ミリ秒だった、とあります。フェーズ7-1 の5-2節の fps の88 からも、約11ミリ秒と分かります。PC や、ほかに動かしているものによって変わります。なので、1本の学習は、10万かける、0.047 に0.013 を足したもので、約6000秒、つまり約1.7時間と見積もれます。

課題が2つあります。

課題1 です。2-3節の減衰を半分、つまり0.024 にしたワールドで、ペダル0.5 を踏み続けたときに落ち着く速さと、速度の時定数を、2-2節の式で予想します。ワールドファイルを書き換えて、5-2節を実行して確かめます。マイナス2つの symlink-install でビルドしてあれば、ビルドし直さなくてかまいません。どちらも約2倍になり、60秒では、まだ落ち着きません。確かめたら、0.048 に戻します。

課題2 です。3-3節のコマンドで、multi_step を20 にして呼び、オドメトリの時刻が0.02秒進むことを確かめます。4節の _advance は、これを1回分として、Gazebo を進めます。

## 6. 本フェーズのまとめ

5つあります。

1つ目。物理シミュレータを強化学習の環境にするには、リセット、決まった時間だけ進めること、進めた後の状態を受け取ることが要ります。Gazebo では、一時停止で起動し、ワールドを操作するサービス、つまり ControlWorld で、決まった回数だけ進め、リセットします。

2つ目。サービスは、計算が終わる前に応答を返します。進め終わりは、オドメトリの時刻、つまりシミュレーション時刻で確かめます。

3つ目。フェーズ5-1 の速度に比例する抵抗を、縮尺で直して、車輪の関節の減衰にしました。抵抗の無い車両では、速度が際限なく上がり、学習が進みにくかったです。

4つ目。Gymnasium の環境の中に ROS2 のノードを持たせると、強化学習のライブラリから、ROS2 のトピックとサービスで、Gazebo の車両を動かせます。

5つ目。Gazebo の環境は、Python の式の環境より、ずっと遅いです。学習にかかる時間を見積もってから、学習の量を決めます。
