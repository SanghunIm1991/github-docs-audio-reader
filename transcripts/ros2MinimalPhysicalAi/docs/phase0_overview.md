# フェーズ0: ROS2の概要と全体像（聞くための原稿）

これは、ROS2 を学ぶ教材の、最初の読み物です。原文の手順書は、ros2MinimalPhysicalAi という教材のフェーズ0 にあたります。フェーズ1 で turtlesim という亀のシミュレータを動かし始める前に、コマンドは実行せず、ROS2 という技術の全体像と、この教材のゴールと学習の地図を、先につかんでおくためのものです。

前半の1節から6節は、ROS2 そのものの一般的な話です。ところどころに、この教材のどこで出会うかを添えています。後半の7節と8節は、この教材の話です。

想定する環境は特に問わず、ROS2 を入れる前でも読めます。ただし、用語の一部は、環境構築の手順書を終えた後のほうが実感しやすいそうです。所要時間の目安は1コマで、手を動かす作業はありません。

原文には、位置づけと注意の囲みがあります。このフェーズの目的は知識の地図を作ることで、終わったと言える条件は「コマンドが動く」ではなく「自分の言葉で説明できる」ことです。文章は作者の言葉で書いたものですが、ROS2、DDS、周辺の OSS の事実関係、例えばバージョン、対応する OS、ライセンスなどは、公式のページの記載に基づいています。細かい点が最新の公式の情報と食い違う場合は、公式を優先してください、とあります。

## 0. 学習目標

このフェーズを終えたら、次の8つを自分の言葉で説明できる状態を目指します。

1つ目。ROS2 が何のためのソフトウェアか。OS でもフレームワーク1つでもなく、通信の規約とツールの集まりであること。

2つ目。ROS2 の通信が、役割の違う層を積み重ねた構造、つまりプロトコルスタックになっていること。

3つ目。ROS2 で実現できることの範囲。分散システム、マルチロボット、組み込み、セキュリティなど。

4つ目。製造業、モビリティ、建設業、ドローン、介護などの業界で、ROS2 がどう使われ、どの特徴が効いているか。

5つ目。よく使われる周辺の開発ツール、colcon、rqt、RViz2、Gazebo、Nav2 などの役割を、一言で言えること。

6つ目。ノード、トピック、サービス、アクション、パラメータなどの基本の用語を、迷わず使えること。

7つ目。この教材のゴール、つまり最初のゴールのフェーズ5 と、最終ゴールのフェーズ7-5 の完成形で、どの部品にどの技術を使い、それをどのフェーズで学ぶかを見通せること。

8つ目。この教材の学習のロードマップ、フェーズ1 から7 と、保留中のフェーズ8 が、ROS2 のどの概念の領域に対応しているかを見通せること。

## 1. ROS2とは何か

ROS2 は、Robot Operating System 2 の略です。名前に反して、OS、つまりオペレーティングシステムではありません。ロボット向けのソフトウェアを作るための、通信の仕組み、ビルドツール、標準ライブラリ、開発ツールの集まりです。

ロボットのソフトウェアでは、複数のプログラム、つまりノードが、センサの値や制御の指令などのデータをやり取りしながら、協調して動きます。ROS2 は、こうしたソフトウェアに共通する土台を、車輪の再発明をせずに使えるようにします。

ROS2 は、初代の ROS、つまり ROS1 を作り直したものです。ROS1 の最後の版のサポートは、2025年5月に終わりました。ROS1 との違いは、今から ROS2 で始める分には知らなくても困らないので、Tips集の7節にまとめてあります。ROS1 で書かれた古いコードを ROS2 へ移す方法と注意点も、同じ節にあります。

## 2. 通信の仕組みの概要: 層を積み重ねた構造

ROS2 でノードどうしがデータをやり取りするとき、自分が書くコードが、直接ネットワークを操作しているわけではありません。間には役割の違う層がいくつも積み重なっていて、上の層は、すぐ下の層に「これを送って」と頼むだけで済みます。このように、通信の仕事を層に分けて積み重ねた構造を、プロトコルスタックと呼びます。Web のページを見るときに、ブラウザの HTTP の下で TCP が、その下で IP が働いているのと同じ考え方です。

原文では、この構造を図にしています。同じ内容の図が2つあり、1つは画像の SVG、もう1つは mermaid という記法で書いた図です。ここでは、その図の中身を言葉で説明します。

図の中央には、5つの箱が、上から下へ1列に並び、矢印でつながっています。

一番上の箱は「ノード」で、自分が書くコードです。Python なら rclpy、C++ なら rclcpp を使います。

2つ目の箱は「ROS クライアントライブラリ」、略して RCL です。publisher や subscription などの API を提供します。

3つ目の箱は「RMW」、ROS Middleware Interface です。DDS の実装を差し替えられるようにする、抽象の層です。

4つ目の箱は「DDS の実装」で、ミドルウェアの本体です。例として Fast DDS や Cyclone DDS が挙げられています。

一番下の箱は「ネットワーク」です。通常は UDP とマルチキャストで通信します。

この列の右側には、点線の枠の注記が2つあり、それぞれ点線の矢印でつながっています。1つは RMW の箱の横にあり、「環境変数 RMW_IMPLEMENTATION で、DDS の実装を切り替えられる」と書かれています。もう1つはネットワークの箱の横にあり、「まとめ役の中央のサーバは無い。互いに自動で見つけ合う」と書かれています。

図の層の名前、RCL、RMW、DDS は、今は覚えなくてよい、と原文は言います。押さえておきたいのは、層に分かれていることで得られる、次の3つです。

1つ目。書く人は、一番上だけを見ればよい。ノードを書くときに使うのは、一番上の rclpy や rclcpp の API だけです。データがどんな形でネットワークを流れるかは、下の層が引き受けます。

2つ目。下の層を取り替えられる。実際にデータを運ぶ層、DDS には、複数の製品があります。間に差し替えのための層、RMW が挟まっているので、ノードのコードを変えずに取り替えられます。

3つ目。まとめ役がいなくても、つながる。ノードは起動すると、同じネットワークにいる相手を、自分たちで見つけ合います。これをディスカバリと呼びます。中央で名簿を管理するサーバはありません。また、トピックごとに、確実に届けるか、多少欠けてもよいか、といった送り方の約束、QoS を決められます。QoS は、フェーズ3-2b で実際に試します。

各層の詳しい役割、つまり DDS という規格、RMW で選べる実装、ディスカバリの範囲の分け方、QoS の項目は、Tips集の6節にまとめてあります。

## 3. ROS2で実現できること

原文は、機能の一覧ではなく、「これができると何が嬉しいか」を、自分のロボットを育てていく場面を想像しながら読んでほしい、と言います。7つの話があります。

1つ目。プロセスや PC をまたいで、ノードを増やしていける。今は1台の PC の、1つのワークスペースの中で学んでいますが、ROS2 のノードは、同じネットワークに置くだけでつながります。中央の管理者に、ノードの存在を届け出る必要はありません。2節のディスカバリです。この教材のフェーズ5 では、車両のシミュレーションを、2つのノードに分けて作ります。1つは制御ノードで、目標の速度に近づくように指令を出します。もう1つはプラントノードです。プラントとは、制御される対象のことで、ここでは指令を受けて車両の速度を計算するノードです。だから、将来センサ用の基板や別の PC を足したくなったとき、これらのノードを分散させる、という選択肢が、すでに手の中にあります。倉庫の中を何十台もの搬送ロボットが同時に動く現場や、複数のロボットが同じ場所を共有する研究、つまりマルチロボットも、同じ仕組みの延長線上にあります。その仕組みとは、ROS2 のシステムを番号で分けるドメインID と、ノードやトピックの名前の前に区切りを付けて分ける namespace です。

2つ目。プログラムが実機の安全を左右する場面にも耐えられるよう、設計されている。QoS で通信の信頼性を作り込めること、そしてリアルタイム OS の上でも動く設計を志向していることは、「多少データが欠けても良いセンサの値」と「絶対に届かないと困る制御の指令」を、同じフレームワークの中で区別して扱える、ということでもあります。この教材では、フェーズ3-2b で QoS の一端に触れる程度にとどめます。ただ、産業用のロボットや自動運転が ROS2 を採用する理由の1つは、ここにあります。

3つ目。PC の中で完結しない世界にも、同じ書き方のまま出ていける。micro-ROS を使うと、一部の Arduino のボードや ESP32 のような、小さな32ビットのマイコンでも、今書いているのと同じ、ノード、トピック、パラメータという語彙で、ROS2 に参加できます。シミュレーションのプラントノードを、いつか本物のモータとセンサに置き換える、というこの教材の発展の方向、つまり実機との連携は、まさにこの延長線上にあります。

4つ目。1台の完成形にたどり着くまでの、壊れながら育てる過程も面倒を見てくれる。ライフサイクルノード、managed node という仕組みでは、ノードを「準備はできたが、まだ動いてはいけない」状態から、明示的に起動させられます。何十個ものノードが絡み合う大きなシステムほど、この「順番に、確実に立ち上げる」機能のありがたみが増します。

5つ目。実機を壊す前に、机の上で何度でも試せる。Gazebo のような物理シミュレータと組み合わせれば、モータを焼いたり部品を壊したりする心配なく、思いついた制御則を何度でも試せます。フェーズ5 の車両のシミュレーションは、まさにこの「実機の前に、まず仮想で」という発想の最小版です。フェーズ7 の強化学習と、フェーズ8 の URDF などの OSS を広げて使う段階で発展させる、二足歩行の構想でも、同じ考え方を使います。

6つ目。自律移動やアームの操作のような、1人では作りきれない機能を、借りて使える。Nav2 は自律移動と経路の計画、MoveIt2 はアームのモーションプランニング、ros2_control はアクチュエータの制御の抽象化を受け持ちます。どれも、何年もかけて磨かれてきた大規模な OSS です。センサから経路を計画してモータを動かす、という仕組みを一から書く必要はなく、まずは動かして中身を覗くところから始められます。

7つ目。離れた場所や他人とも、安全に共有できる。SROS2 による DDS Security の認証と暗号化は、「このロボットを外部のネットワークにつないでも、誰かに乗っ取られない」という安心を持ち込む仕組みです。1人で学んでいる今は意識しなくてよいのですが、将来ロボットをチームで開発したり、外部と通信させたりする日が来たときの選択肢として、覚えておくとよい、とあります。

## 4. 業界ごとのROS2の活用

3節では、ROS2 でできることを、機能の側から眺めました。この節では視点を変えて、実際の産業の現場を見ていきます。製造業、モビリティ、建設業、ドローン、介護の順に見ると、業界によって困りごとが違い、ROS2 のどの特徴が効くかも違います。

一方で、「センサで周りを知り、判断し、アクチュエータを動かす」という流れは、どの業界にも共通しています。これはフィジカルAI の骨格でもあります。フェーズ5 で作る、目標速度から制御ノード、そしてプラントノードへ、というループは、その最小版にあたります。

各業界の小節の最後には、この教材のどのフェーズとつながるかが書いてあります。今は「こういう世界の入口に立っている」と分かれば十分だ、と原文は言います。なお、団体や OSS の事実関係は、2026年9月25日の時点の公式のページと記事に基づいています。導入の事例や対応のバージョンは変わりやすいので、詳しく調べるときは、公式の最新の情報を確かめてください、とあります。

### 4-1. 製造業: 教えた通りに動くロボットから、見て考えるロボットへ

工場の産業用ロボットは、長い間、メーカーごとの専用のコントローラと専用の言語で、決まった動きを繰り返し教え込む、つまりティーチングするものでした。大量生産のラインなら、それで十分でした。

ところが、多品種を少しずつ作る現場や、形も置き方もばらばらな部品をつかむ作業、ばら積みピッキングでは、カメラで対象を見て、その場で経路を計画する必要があります。こうした知能の部分は、メーカーをまたいで共通に作れたほうがよいわけです。

この流れを支えているのが、ROS-Industrial です。ROS の機能を製造業へ広げるオープンソースのプロジェクトで、米国の SwRI、サウスウエスト研究所、ドイツの Fraunhofer IPA、シンガポールの ARTC が中心になったコンソーシアムが、方向づけをしています。

ロボットメーカー自身が ROS2 のドライバを出す動きも進んでいます。Universal Robots は公式の ROS2 のドライバを GitHub で公開していて、FANUC も、協働ロボットの CRX シリーズ向けの ROS2 のドライバを公式に出しています。どちらも、アームの動作を計画する MoveIt2 と組み合わせて使うことを想定しています。こうして、メーカーが違っても、上の「見て、計画して、動かす」部分を、同じ ROS2 の語彙で書けるようになります。

効いてくる ROS2 の特徴は、ros2_control によるハードウェアの抽象化、MoveIt2、そして URDF によるロボットの形の記述です。

この教材との接点は、フェーズ8 の URDF と xacro、そして ros2_control の概念です。フェーズ5 で、モデルの部分を、トピックの入出力から分けておくのは、あとでプラントを実機やメーカーのドライバに差し替える、という同じ発想の、小さな版です。

### 4-2. モビリティ: 自動運転と搬送ロボット

自動運転車は、LiDAR、カメラ、GNSS つまり衛星測位、IMU つまり慣性センサなど、多くのセンサを積みます。それらの情報から自分の車の位置を推定し、周りの物体を認識し、その動きを予測し、走る経路を計画して、ハンドルとアクセルを制御します。この長い処理の流れを、多くのノードに分けてトピックでつなぐ構成は、ROS2 の得意分野です。

代表例が Autoware です。ROS2 の上に作られたオープンソースの自動運転ソフトウェアで、自己位置推定、認識、予測、計画、制御の一連の処理を、ノードとトピックの集まりとして実装しています。開発は、日本のティアフォーなどが立ち上げた、Autoware Foundation が進めています。

小さな例では、工場や倉庫で荷物を運ぶ自律移動ロボット、AMR があります。ここでは、3節でも触れた Nav2 が、地図の上での経路の計画と、障害物の回避を受け持つ候補になります。

モビリティでは、センサのデータの量が多く、しかも止まっては困る制御の指令を、同時に流します。3節で見た、多少欠けても良いセンサの値と、絶対に届かないと困る制御の指令を、QoS で分けて扱う設計が、ここで効いてきます。

効いてくる ROS2 の特徴は、多数のノードへの分割、QoS、そして tf2 による座標系の管理です。

この教材との接点です。フェーズ5 の車両のシミュレーション、つまり速度の指令からプラント、そして現在の速度へ、という流れは、自動運転の制御の部分を、ぐっと小さくしたものです。フェーズ3-2a で扱う Twist 型の速度の指令は、移動ロボットで広く使われる型です。フェーズ3-2b の QoS は、この業界で重みが増します。

### 4-3. 建設業: 人手不足と危険な現場を、自律施工で補う

建設の現場は、人手不足が深刻なうえ、重機のそばで働く危険も大きいところです。そこで、油圧ショベルなどの建設機械を自動で動かす「自律施工」の研究が進んでいます。ただ、建機はメーカーごとに制御の仕組みが違います。しかも、1台で数十トンになる機械を、研究のたびに一から用意して試すことは難しいのです。

日本では、国立研究開発法人の土木研究所が、自律施工の技術基盤、OPERA を公開しています。自動運転に対応した建設機械、実験のフィールド、シミュレータ、建機を動かす共通の制御信号、そして ROS をベースにしたソフトウェア群を、まとめて提供するものです。ソフトウェアの一部は、GitHub の pwri-opera で公開されていて、油圧ショベル向けの ROS2 のパッケージもあります。

建機のハードウェアの違いを ROS の層で吸収するので、研究機関や企業の成果を持ち寄って、組み合わせやすくなります。実際に、清水建設、土木研究所、日立建機の共同で、OPERA を使って、油圧ショベルの土砂の掘削から、ダンプへの積み込みまでを自動化する実験が行われました。これは、2025年の清水建設の発表によるものです。

現場の巡回や点検では、四足歩行のロボットも使われ始めています。Boston Dynamics の Spot には、ROS2 から操作するためのドライバ、spot_ros2 が、オープンソースで公開されています。

効いてくる ROS2 の特徴は、ハードウェアの抽象化、シミュレータでの事前の検証、そして1つの現場で複数の機械を協調させる、分散した構成です。

この教材との接点です。重機のように、実機でいきなり試せないものほど、フェーズ5-0 で触る Gazebo のようなシミュレータの価値が上がります。フェーズ5 で、実機の代わりに疑似のプラントノードで制御を試すのも、同じ考え方です。

### 4-4. ドローン: 機体の中の制御と、外の知能を分ける

ドローンの姿勢の制御は、1秒間に数百回以上の速さで回り続ける必要があります。そのため、この部分は、機体に積んだフライトコントローラ、つまりマイコンの上で、専用のソフトウェアが動かしています。代表的なオープンソースのフライトコントローラ用のソフトウェアが、PX4 と ArduPilot で、どちらも ROS2 とつながる仕組みを持っています。

PX4 は、uXRCE-DDS というブリッジを使います。フライトコントローラの側で小さなクライアントが動き、その相手のエージェントが、機体に一緒に積むコンピュータ、つまりコンパニオンコンピュータの上で動きます。エージェントが代理で DDS の世界へ出入りするので、ROS2 のノードからは、機体の状態がトピックとして見え、指令もトピックで送れます。

ArduPilot は、AP_DDS というライブラリで、ROS2 との通信を標準で持っています。

どちらの場合も、速い姿勢の制御は機体の中で、地図づくり、経路の計画、画像の認識のような重い知能は、ROS2 でコンパニオンコンピュータの側で、という役割分担になります。複数のドローンを協調させる研究では、ROS2 の上に作られたフレームワーク、Aerostack2 もあります。スペインのマドリード工科大学のグループが開発したものです。

効いてくる ROS2 の特徴は、マイコンと PC をまたぐ通信、つまり XRCE-DDS と、マルチロボットです。

この教材との接点です。3節の micro-ROS も、マイコンを ROS2 に参加させるために、同じ XRCE-DDS の仕組みを使います。PX4 の構成は、3節で書いた、マイコンが PC と同じ語彙で ROS2 に参加できるという話の、実用化された例として読めます。

### 4-5. 介護・医療・生活支援: 人のすぐそばで動くロボット

介護や生活支援のロボットは、人のすぐそばで、人に触れることさえあります。そのため、工場のロボット以上に、安全と信頼性が問われます。この分野で実際に現場に出ている製品は、中身が公開されていないものが多く、ROS が目立つのは、主に次の2つの場面です。ここでの ROS は、ROS2 を含みます。

1つは、研究のための共通の土台です。トヨタの HSR、Human Support Robot は、移動する台車、アーム、カメラ、マイクを備えた生活支援ロボットで、ソフトウェアは ROS をもとにしています。ただし、ROS1 と ROS2 のどちらに対応しているかは、原文の手順書では確かめていません。使う場合は、公式の最新の情報を確かめてください、とあります。HSR は、家庭の中の支援の作業を競う RoboCup@Home や、World Robot Summit で、標準の機体として採用されています。研究者は同じ機体の上で成果を共有でき、ハードウェアを一から作る手間が省けます。

もう1つは、施設の中で、複数のロボットと設備をつなぐ仕組みです。病院では、薬や検体を運ぶロボット、清掃ロボットなど、メーカーの違う複数のロボットが、同じ廊下やエレベーターを使います。これらを交通整理し、自動ドアやエレベーターとも連携させる仕組みが、Open-RMF です。シンガポール政府の支援で病院向けに始まったプロジェクト、RoMi-H が前身で、ROS2 の上に作られています。導入の前の検証には、Gazebo のシミュレーションも使われます。2021年10月に新しい版の公開を報じた The Robot Report の記事では、病院に限らず、空港や商業施設、倉庫などでの利用が紹介されています。今の利用の状況は、公式の最新の情報で確かめてください、とあります。

効いてくる ROS2 の特徴は、異なるメーカーのロボットの相互運用、ライフサイクルノードによる確実な立ち上げ、そして3節の SROS2 による通信の保護です。

この教材との接点です。この教材では、直接は扱いません。ただ、フェーズ4 の4-6節で扱う namespace、つまりノードやトピックの名前の前に demo のような区切りを付けて住み分ける仕組みは、同じノードを複数台ぶん起動するときに、名前がぶつからないようにする基本の道具です。複数のロボットを1つのシステムで動かすときの土台になります。

## 5. よく使われるROS2の周辺開発環境・ツール

全部を今覚える必要はありません。「ROS2 を学んでいて、こういう場面が来たら、これを思い出せばいい」という地図として眺めてほしい、と原文は言います。ツールは、ROS2 の開発で実際に踏む5つの場面ごとに、表に分けて並べてあります。表はどれも、ツールの名前と、その説明の2列です。

場面1は、まず手元で動かす、作る、です。この後すぐ使う、コードを書く前後に必ず触る、道具箱の土台です。ツールは3つあります。

colcon は、ワークスペースの中の複数のパッケージを、一括でビルドします。ワークスペースは、パッケージをまとめてビルドする作業のフォルダで、パッケージは、ROS2 の配布とビルドの単位です。

ament は、ビルドの仕組みや Lint などを支えるツール群です。Lint は、コードの誤りや書き方の乱れを、自動で調べる検査のことです。ament_python や ament_cmake は、この一部です。

rosdep は、パッケージが必要とする依存関係を、自動で解決して導入します。

場面2は、今、中で何が起きているかを目で見る、です。コードを読むだけでは、ノードどうしが実際につながっているか、センサの値がどう流れているかは分かりません。そこで役立つのが、可視化のツールです。4つあります。

rqt_graph は、誰が誰と話しているかを、ノードとトピックの線の図で見せます。フェーズ1 で早速使います。

rqt_console と rqt_plot は、それぞれ、ログの一覧と、数値の時系列のグラフを見せます。

RViz2 は、ロボットの姿勢、座標系、センサの点群を、3D の空間で見せます。

Foxglove Studio は、RViz2 や rqt の機能を、Web やデスクトップのアプリでまとめて使える、サードパーティの可視化ツールです。

場面3は、あの時の挙動を記録して、後から検証する、です。一発勝負で確かめるのではなく、動かした結果を保存しておいて、後でじっくり見返したり、ほかの人と共有したりする使い方です。2つあります。

ros2 bag、つまり rosbag2 は、トピックを記録して、再生します。記録したファイルを bag と呼びます。フェーズ6 で、制御の効き方を後から評価するのに使います。

PlotJuggler は任意のツールで、bag のデータを、より高い機能で可視化します。

場面4は、何年もかけて磨かれた機能を、自分の手で書かずに使う、です。自律移動やアームの操作、座標の変換、ロボットの3D の形の記述といった、それ自体が奥深い専門分野は、車輪の再発明をせず、既存の OSS に乗るのが定石です。まずは動かして中身を覗くところから、理解が始まります。6つあります。

tf2 と tf2_tools は、ロボットの各部位の座標系どうしの関係、つまり位置と向きを、管理して変換します。

URDF と xacro は、ロボットの構造と見た目を記述します。xacro は、URDF を書きやすくするマクロの拡張です。RViz2 で表示して確かめることが多いそうです。

ros2_control は、モータなどのアクチュエータの制御を抽象化する、フレームワークです。

Gazebo は、Harmonic などの版がある、3D の物理シミュレータです。実機を壊す心配なく試せます。

Nav2 は、自律移動のスタックです。経路の計画や、SLAM との連携などを受け持ちます。SLAM は、走りながら地図を作り、同時に自分の位置を推定する技術です。

MoveIt2 は、アームなどのモーションプランニング、つまり、動かす経路を、障害物を避けながら計画することを受け持ちます。

場面5は、実機につなぐ日、人と共有する日が来たとき、です。1人で机の上のシミュレーションを動かしている今は、まだ出番がありません。学習が進んで、本物のモータやセンサにつなぐ、ほかの人と一緒に開発する、外部のネットワークに公開する、といった段階になったときに思い出したい道具です。3つあります。

micro-ROS は、ESP32 や一部の Arduino のボードなどのマイコンを、PC と同じ ROS2 の語彙、つまりノード、トピック、パラメータで、システムに参加させます。

SROS2 は、DDS Security による認証、暗号化、アクセス制御を提供します。ロボットを外部のネットワークにつなぐときの安心材料です。

Docker は、環境をまるごと再現できるコンテナです。複数の人や複数の PC で、同じ環境をそろえたいときに使います。

## 6. 基本用語集

原文の6節は、23の用語と、その意味を並べた表です。順に読み上げます。

ノード、Node。処理の実行の単位。基本は1つのプロセスに1つのノードだが、Composition、つまりこの表の下の方のコンポーネントの仕組みで、1つのプロセスに複数のノードをまとめることもできる。

トピック、Topic。名前の付いた、一方向で継続的な通信のチャネル。publish と subscribe の形で使う。

メッセージ、Message。トピックでやり取りするデータの型。.msg のファイルで定義する。

パブリッシャとサブスクライバ。トピックにデータを送る側と、受け取る側。

サービス、Service。1回の要求と応答。同期的な RPC に近い。.srv のファイルで型を定義する。

クライアントとサーバ。サービスを要求する側と、処理して結果を返す側。

アクション、Action。時間のかかる処理に向けた、非同期の通信。goal つまり目標、feedback つまり途中経過、result つまり結果があり、キャンセルもできる。.action のファイルで型を定義する。

パラメータ、Parameter。ノードの実行時の設定の値。YAML のファイルや、ros2 param のコマンドで変えられる。

インターフェース、Interface。msg、srv、action の総称。専用のパッケージとしてビルドされ、複数の言語から共通の型として使える。

パッケージ、Package。ROS2 の配布とビルドの単位。ament_python や ament_cmake などのビルドのタイプがある。

ワークスペース、Workspace。複数のパッケージをまとめてビルドする作業のディレクトリ。中に src、build、install、log のフォルダがある。

launch ファイル。複数のノードをまとめて起動する設定。Python、XML、YAML のいずれかで書ける。

QoS プロファイル。通信の信頼性、持続性、履歴の保持などをまとめた、設定の組。

DDS。ROS2 の標準の通信ミドルウェアの規格。本文の2節の図にあり、詳しくは Tips集の6節。

RMW。ROS2 の API と DDS の実装をつなぐ、抽象の層。これも2節の図にあり、詳しくは Tips集の6節。

Executor。ノードのコールバック、つまりデータを受けたときなどに呼ばれる関数を、いつ、どのスレッドで実行するかを管理する仕組み。

コールバックグループ。複数のコールバックを、同時に実行してよいか、排他にすべきかで束ねる仕組み。Executor と組み合わせて使う。

ライフサイクルノード、Managed Node。unconfigured から inactive、active などへ移る状態を持ち、起動と終了の手順が管理されたノード。

コンポーネント、Composition。複数のノードを1つのプロセスにまとめて実行する仕組み。プロセスの間の通信の負担を避けられる。フェーズ4 とフェーズ5 の間の間章で扱う。

colcon。ROS2 の標準のビルドツール。5節の場面1 に出てきた。

ament。ROS2 のビルドのシステムや Lint などのツール群の総称。これも場面1。

rosdep。パッケージが必要とする依存関係を解決して導入するツール。これも場面1。

ROS_DOMAIN_ID。同じネットワークの上で、複数の ROS2 のシステムを分けるための番号。

## 7. この教材のゴール（完成形の構成）

6節までは、ROS2 そのものの話でした。ここからは、この教材が何を作り、それに向けて何をどの順番で学ぶかを見ていきます。

この教材には、2段階のゴールがあります。

最初のゴールはフェーズ5 です。慣性のある車両を、目標の速度に追従させるシミュレーションを、ROS2 のノードで組み立てます。車両は、Gazebo の中を走ります。Gazebo は、物の動きを物理法則で計算して、画面に表示するシミュレータです。アクセルとブレーキの踏み方は、PI制御で決めます。PI制御は、目標との差と、その差の積み上げから、操作の量を決める、古典的な制御です。

最終ゴールはフェーズ7-5 です。そのPI制御を、強化学習で学習させたニューラルネットワーク、NN に置き換えます。強化学習は、試した結果に点数を付け、点数が上がるように行動の決め方を学ばせる方法です。そして、同じ ROS2 の一式で走らせ、記録から計算した指標で、PI制御と比べます。

ノードやトピックを1つずつ学んでいる間は、それが何の役に立つのかが見えにくいものです。そこで、先に完成形を見ておきます。

原文では、最終ゴールのフェーズ7-5 で動かす一式を、図にしています。これも、SVG と mermaid の2つの版があります。各箱の最後の行には、色の付いた文字で、その部品を作る、または使い方を学ぶフェーズが書かれています。ここでは、SVG の配置に沿って説明します。

図の中ほどには、大きな点線の枠があります。枠の名前は「launch ファイルで一式を起動」で、関わるフェーズとして、フェーズ4、5-3、5-4、7-5 が添えてあります。

枠の中の上の段には、4つの箱が、左から右へ並んでいます。

1つ目の箱は target_generator です。目標の速度を、階段の形に送ります。フェーズ5-3 で作ります。

2つ目の箱は nn_controller です。学習した NN で、ペダルを決めます。フェーズ7-5 で作ります。

3つ目の箱は gz_plant です。ペダルを、車輪のトルクに直します。フェーズ5-1 と5-4 で作ります。

4つ目の箱は「Gazebo とブリッジ」です。車両の物理を計算します。フェーズ5-0 と5-4 で学びます。

これらの箱の間の矢印は、次のとおりです。target_generator から nn_controller へ「目標速度」。nn_controller から gz_plant へ「ペダル」。その逆向きに、gz_plant から nn_controller へ「速度」。gz_plant から Gazebo とブリッジへ「トルク」。その逆向きに、Gazebo とブリッジから gz_plant へ「オドメトリ」。つまり、制御器とプラントの間、プラントと Gazebo の間は、それぞれ行きと帰りの2本の矢印でつながっています。

枠の中の下の段、nn_controller のすぐ下には、もう1つの箱、pi_controller があります。PI制御で、引数で NN と入れ替える、と書かれています。フェーズ5-2 で作ります。この箱には、矢印がつながっていません。箱の説明のとおり、nn_controller と入れ替えて使う部品です。SVG では、nn_controller と pi_controller の2つの箱だけが同じ色で、ほかのノードの箱と色が分けてあります。

点線の枠の上、図の一番上の段には、ROS2 の外のものが2つあります。左の箱は「強化学習で学習」で、Gymnasium と SB3、つまり Stable-Baselines3 を使い、ROS2 の外で行います。フェーズ7-0 から7-4 で学びます。この箱から右へ「学習」という矢印が出て、「学習済みの重み」の箱につながります。重みは .npz のファイルで、numpy だけで読みます。フェーズ7-4 で作ります。そして、この重みの箱から、下の nn_controller へ、点線の矢印が出ています。

点線の枠の下には、記録と評価の2つの箱があります。枠そのものから下へ「記録」という矢印が出て、ros2 bag record の箱につながります。トピックをファイルに記録するもので、フェーズ6-1 で学びます。そこから右へ「再生」という矢印が出て、metrics の箱につながります。指標を計算して、PI と NN を比べるもので、フェーズ6-3 で作ります。

図の説明は、こう続きます。上の段の2つ、強化学習と学習済みの重みと、Gazebo の本体は、ROS2 のノードではありません。Gazebo の本体は、ROS2 とは別の通信の仕組みで動きます。ほかはすべて、ROS2 のノードと、それをまとめて起動する launch ファイルです。

制御のループのノードどうしは、目標速度、ペダル、速度の3つのトピックでつながります。gz_plant と Gazebo の間は、ブリッジを通したトピック、つまり車輪のトルクとオドメトリでつながります。ブリッジは、Gazebo の中の値を、ROS2 のトピックとやり取りするための、中継のノードです。トルクは車輪を回す力、オドメトリは車両の位置と速さを表すデータです。

この構成の要は、部品の境目を、トピックの名前と型で決めておくことです。nn_controller は、PI制御の pi_controller と同じトピックを受けて、同じトピックへ送ります。そのため、ほかのノードのコードを1つも変えずに、launch ファイルの引数で、制御器を入れ替えられます。最初のゴールで作った一式が、最終ゴールの土台になるのは、このためです。

ただし、フェーズ7-5 では、フェーズ5-4 の一式を写して新しい launch ファイルを作り、2つの設定を、NN を学習させたときの条件に合わせます。1つはワールドで、減衰の入ったものにします。もう1つはプラントのパラメータで、ブレーキの遅れです。変えるのは設定だけで、ノードのコードは変えません。同じ考え方で、フェーズ5-4 では、制御器を変えずに、車両の計算を、自作の式から Gazebo の物理に差し替えます。

もう1つの要は、学習する側と、使う側を分けることです。NN の学習には、強化学習のライブラリ、Gymnasium と Stable-Baselines3 を使います。学習が終わったら、NN の重みを、数だけのファイル、.npz に書き出します。ROS2 のノードは、そのファイルを、Python の数値計算のライブラリ numpy で読んで計算するだけなので、学習のライブラリが無くても動きます。

続いて原文は、各部品で使う技術と、それを学ぶフェーズを、表にまとめています。列は、部品、使う技術、学ぶフェーズの3つで、11行あります。順に読み上げます。

ノードとトピック、つまり全体の土台。Python の rclpy でノードを書き、トピックで送受信する。ros2 のコマンドで動きを観察する。学ぶのは、フェーズ1 と3-1。

パッケージとビルド、これも全体。ワークスペースとパッケージを作り、colcon build でビルドする。フェーズ2。

target_generator。パラメータとタイマー。パラメータは、目標の値と切り替える時刻を、YAML のファイルで渡す。YAML は、設定を書くためのテキストの形式。フェーズ3-3 と5-3。

pi_controller。PI制御の式。受けた値を覚え、決まった周期でまとめて計算して送る。フェーズ5-2。

gz_plant。アクセルとブレーキの遅れの式と、シミュレーションの時刻。シミュレーションの時刻とは、Gazebo の時計で動くこと。フェーズ5-1 と5-4。

Gazebo とブリッジ。Gazebo のワールド、つまりシミュレーションする世界を書いたファイルと、ros_gz_bridge。フェーズ5-0 と5-4。学習用のワールドはフェーズ7-3。

launch ファイル。複数のノードの起動、引数、YAML のパラメータ、引数の値で起動するノードを選ぶ条件、そして記録用の launch ファイルから一式を取り込むこと。フェーズ4、5-3、5-4、6-1、7-5。

ros2 bag record。トピックをファイルに記録し、決めた時間で終わらせる。フェーズ6-1。

metrics。記録から、追従の指標を計算する。追従の指標とは、追従の良し悪しを表す数で、行き過ぎ量、整定時間、RMS などがある。RMS は、誤差の二乗の平均の平方根。フェーズ6-3。

強化学習、これは ROS2 の外。Gymnasium で環境を作り、Stable-Baselines3 の SAC で学習させ、重みを書き出す。SAC は、強化学習の手法の1つ。フェーズ7-0 から7-4。

nn_controller。numpy で NN を計算する。学習のときと同じ観測を、トピックの値から作る。そして、学習した範囲の外では NN を使わない。フェーズ7-5。

表に無い必須のフェーズ、例えばフェーズ3-2a や3-2b は、これらの部品を作るときにつまずかないための基礎です。

最初のゴールのフェーズ5 と、それを記録で評価するフェーズ6 までは、ROS2 だけで進められるので、必須の範囲にしています。フェーズ7 は、ROS2 とは別に強化学習のライブラリを入れ、学習に時間もかかるので、最初のゴールの後に進む、最終ゴールまでの道筋にしました。

フェーズ7-4 の学習は、自分で学習させると約1.6時間かかります。任意の、比べるための学習も含めると、約3.2時間です。ただ、作成したときに学習させた重みを配っているので、学習を待たずにフェーズ7-5 へ進めます。

なお、最終ゴールで比べると、NN は PI制御に届きません。これはフェーズ7-5 の5節にあります。この教材の最終ゴールは、NN で PI制御に勝つことではありません。学習させた NN を ROS2 の部品として組み込み、同じ物差しで比べて、それぞれのよい点と弱い点を説明できるようになることです。

## 8. 学習しなければならない概念（この教材の地図）

いきなり全部を学ぶのではなく、段階的に積み上げます。原文は、ROS2 の概念の領域ごとに、この教材のどのフェーズが対応するかを、表にまとめています。列は、概念の領域、具体的な内容、この教材での対応の3つで、15行あります。順に読み上げます。

通信のパターン。トピック、サービス、アクション、パラメータ。フェーズ1 で観察し、フェーズ3 で自作する。サービスとアクションは、概要をつかむ程度でよい。

QoS。reliability、durability、history など。フェーズ3-2b で、合わないと黙ってつながらないことを体験する。

ビルドとパッケージの管理。colcon、ament、package.xml、ワークスペース。package.xml は、パッケージの名前や依存などを書く設定ファイル。フェーズ2。

起動の管理。Python、XML、YAML の launch ファイル、namespace、remap。remap は、起動するときにノード名やトピック名を付け替えること。フェーズ4。

実行のモデル。Executor、コールバックグループ、spin。spin は、コールバックを呼び出しながら、ノードを動かし続ける処理。フェーズ3 で触れる程度で、フェーズ3-5 で複数スレッドの executor に少し触れる。深入りは発展課題。

ノードの組み立て方。コンポーネント、つまり Composition と、Node クラスの内部の構造。間章と、参考資料で扱う。

座標の変換。tf2 の broadcaster と listener、そして座標系。フェーズ8 で扱う。TF の仕組みと、tf2_echo での読み方の基本は、URDF と RViz の任意の間章の4-4節にある。

ロボットの記述。URDF と xacro、そして RViz2 での可視化。任意の間章が2つあり、1つは用意されたロボットの表示、もう1つは Gazebo の物理の間章の4節。発展はフェーズ8。

制御のフレームワーク。ros2_control、つまりハードウェアの抽象化。フェーズ8。

シミュレーション。Gazebo の物理エンジンと、センサの模擬。フェーズ5-0 で導入と基本を学び、これは必須。フェーズ5-1 から5-4 で、車両の表示と、物理での制御。フェーズ7-3 から7-5 で、強化学習の環境と、最終ゴールの一式。そしてフェーズ8 で、URDF などと組み合わせた発展。

強化学習。エージェント、環境、観測、行動、報酬、方策、そして Gymnasium と Stable-Baselines3。これらは ROS2 のパッケージではない。フェーズ7 で、最終ゴールまでの道筋として扱う。中身は、PI のゲインの調整、PI制御のニューラルネットワークへの置き換え、そして ROS2 のノードへの持ち出し。二足歩行への橋渡しのフェーズ7-6 は発展。

ライフサイクルの管理。managed node と、状態の遷移。この教材では扱わず、用語だけ把握する。

ナビゲーションと操作。Nav2 と MoveIt2。この教材の範囲の外で、将来の発展課題。

セキュリティ。SROS2 の認証と暗号化。この教材では扱わず、用語だけ把握する。

組み込み。micro-ROS。任意の読み物の間章で、仕組み、道具、書き方の入門を扱う。実機での実習は、将来の実機との連携のときに検討する。

表の後で、原文は、5節の周辺ツールのうち、どれをこの教材で使うかを整理しています。

必須の範囲で使うのは、次の4つの場面のツールです。場面1 の colcon と ament。ただし rosdep は使いません。場面2 の rqt 系。rqt_graph と rqt_console はフェーズ1、rqt_plot はフェーズ6-1 で使います。場面3 の ros2 bag、これはフェーズ6。場面4 の Gazebo、これはフェーズ5-0 からで、フェーズ7-3 から7-5 でも使います。

任意の間章で体験するものもあります。URDF と xacro、ros2_control は、Gazebo の物理の間章の4節と5節で。URDF と RViz2 での表示の基本は、URDF と RViz の間章で体験します。そこには、TF を配る robot_state_publisher も含まれます。micro-ROS は、その間章で、仕組みを読み物として扱います。

tf2 を使うノードの自作と、RViz2 を使った発展は、保留中のフェーズ8 で扱う予定です。

扱わないのは、PlotJuggler と Foxglove Studio、Nav2 と MoveIt2、そして場面5 の SROS2 と Docker です。導入の時期は、学習計画の「OSS 活用計画」にあります。
