# フェーズ5-3: 目標の速度を自動で変え、launch で一式を起動する（聞くための原稿）

これは、ros2MinimalPhysicalAi という教材の、フェーズ5-3 の手順書の話です。学習計画のフェーズ5 の5-3 にあたります。目標の速度を、階段の形に自動で変えるノードを作り、フェーズ5-1 と5-2 のノードと、フェーズ5-0 の Gazebo のデモを、1つの launch ファイルでまとめて起動します。最後に、目標、速度、ペダルをグラフに重ねて、アクセルとブレーキの違いが、追いつき方にどう表れるかを読み取ります。これで、フェーズ5 の完了の条件のうち2つ、つまり階段の形の目標の速度に追いつくことと、アクセルとブレーキの非対称性の影響をグラフで説明することに届きます。

想定する環境は、WSL2 と Ubuntu 24.04 と ROS2 Jazzy です。前提は、フェーズ5-2 と、フェーズ4 です。フェーズ4 では、learn_bringup のパッケージがあり、launch と config のフォルダをインストールする設定が済んでいることが要ります。所要時間の目安は1から2コマで、言語は Python です。launch も Python の形式で書きます。

原文の進め方の囲みです。2節で目標の速度を送るノードを、3節で launch ファイルとパラメータの YAML を書きます。4節で起動し、ログ、Gazebo、グラフで動きを見ます。5節で、目標0 で止まりきらない現象を、制御の式から読み解きます。サンプルは学習の手がかりとして最小限に書いたもので、公式のチュートリアルの転載ではありません。コードは手順書を作るときに、使い捨ての環境でビルドし、launch を起動して確かめました。Gazebo は画面なしで別に起動したので、画面の見え方と、rqt_plot のグラフとウィンドウの部品の見た目は確かめていません。出力が違うときは、実機の表示を優先します。

期待する結果の出どころの囲みもあります。ビルドの表示と、launch の --show-args と --print の表示は、使い捨ての環境で確かめたものです。4-1節の launch のログ、4-2節のオドメトリの値、4-4節の Ctrl+C の後の表示、3-4節の最後のエラーの表示は、使い捨ての環境で実際に実行した表示で、時刻、pid、パスは実行ごとに違います。ログは抜粋です。4-2節の画面の様子と、4-3節のグラフの見え方は、ログの数値から筆者が想定したものです。

この原稿では、サンプルコードを書き写さず、ブロックの役割と要の行を言葉で説明します。

## 0. 学習目標と完了の条件

学習目標は4つです。

1つ目。起動からの経過時間に応じて、階段の形に目標の速度を変えるノードを書き、配列のパラメータを扱える。

2つ目。自作のノードと、別のパッケージの launch、つまりフェーズ5-0 のデモを1つの launch にまとめ、引数で一部の起動を切り替えられる。

3つ目。複数のノードのパラメータを1つの YAML にまとめて渡し、ファイルを差し替えて条件を変えられる。

4つ目。rqt_plot で、目標、速度、ペダルを重ねて表示し、加速と減速の違い、つまりアクセルとブレーキの非対称性を、グラフで説明できる。

完了の条件です。ros2 launch learn_bringup vehicle_sim.launch.py の1回で一式が起動し、目標が毎秒10メートル、5メートル、0メートルと変わるのに追いつく様子を、Gazebo とグラフで見ます。そして、グラフのペダルの形から、加速のほうが減速より目標に届くまでに時間がかかる理由を、2つの力の大きさ、つまり駆動力の3000ニュートンと制動力の9000ニュートン、そして遅れ、つまり0.5秒と0.2秒から説明できることです。

## 2. 目標の速度を送るノード、target_node.py

### 2-1. 仕様

ノード名と実行ファイル名は target_generator で、パッケージは learn_py です。

送るのは /target_velocity で、型は std_msgs の msg の Float64、0.1秒ごとに送ります。

目標の速度は、起動からの経過時間で、階段の形に変わります。切り替えの時刻と値は、パラメータの step_times と step_values で決めます。どちらも実数の配列です。既定値は、10秒で毎秒10メートル、50秒で5メートル、80秒で0メートルです。最初の切り替えより前は0 です。

配列の長さがそろっていない、時刻が増えていない、などの誤りがあれば、起動のときにエラーで止まります。実行中の変更は受け付けず、変えるときは起動し直します。

ログは、目標の速度が変わったときだけ、経過時間と新しい値を出します。

最初の切り替えを10秒後にしているのは、launch で一緒に起動する Gazebo の準備ができる前に、車両が走り出さないようにするためです。Gazebo の起動に時間がかかる環境では、3-2節の YAML で遅らせます。

主な API、つまりこれまでの手順書で使ったもの以外の表は、2列で、2行あります。

declare_parameter の既定値に、10.0、50.0、80.0 のようなリストを渡すと、配列のパラメータを宣言できます。2-2節の解説で扱います。

launch の conditions の IfCondition に LaunchConfiguration を渡すと、launch の引数の値、true か false で、Node や IncludeLaunchDescription を起動するかどうかを切り替えられます。3-3節で扱います。

経過時間を測る、単調に増える時計、ClockType の STEADY_TIME はフェーズ5-1 の5-2節で、別の launch の取り込み、IncludeLaunchDescription はフェーズ4 の4-6節で使ったものです。

### 2-2. サンプルコードと解説

サンプルは、learn_py の learn_py フォルダの target_node.py です。

target_node.py は、80行ほどのコードで、ブロックは4つです。1つ目は import で、rclpy、SetParametersResult、Clock と ClockType、ExternalShutdownException、Node、Float64 を読み込みます。

2つ目は、クラスの外に置いた check_steps の関数で、要の行は2つの検査です。2つの配列の長さが違うか空なら、同じ長さで空でないこと、という理由を返し、最初の時刻が負か、後の時刻が前の時刻より大きくなっていなければ、0 以上で、前の時刻より必ず大きくなること、という理由を返します。

3つ目は、Node を継承した TargetGenerator のクラスで、__init__、target_at、on_timer、on_params の4つのメソッドを持ちます。要の行は、__init__ の中の3つです。step_times を、10.0、50.0、80.0 のリストで、step_values を、10.0、5.0、0.0 のリストで宣言する2行と、check_steps が理由を返したら ValueError を投げる行です。

4つ目は main で、これまでと同じです。

原文の解説の要点です。

check_steps は、2つの配列が正しいかを調べる関数です。ノードのクラスの外に置いたのは、ROS2 を起動しなくても、import して試せるようにするためです。フェーズ5-1 と5-2 で、モデルを分けたのと同じ考え方です。

配列のパラメータは、declare_parameter の既定値にリストを渡すと宣言できます。要素が小数点付きなので、型は実数の配列、DOUBLE_ARRAY になります。get_parameter の value で読むと、Python のリストのような値が返るので、list で、ふつうのリストにしています。

起動のときの検証です。check_steps が理由を返したら、ValueError を投げて起動を止めます。フェーズ3-3 の変更のコールバックと違い、起動のときの値はコールバックを通らないので、__init__ で自分で調べます。誤った設定のまま動き続けるより、起動の時点で止まって理由を示すほうが、原因に気づきやすい、とあります。

経過時間の時計は、フェーズ5-1 の gz_display と同じく、単調に増える時計で測ります。PC の現在の時刻は時刻合わせで数秒飛ぶことがあり、それで測ると、目標の切り替えが数秒早まることがあるためです。

target_at は、経過時間までに過ぎた切り替えのうち、最後のものの値を返します。

on_timer は、目標の速度を0.1秒ごとに送り続けます。変わったときだけ送る形にしないのは、後から起動したノード、たとえば pi_controller にも、すぐに今の目標が届くようにするためです。ログは、値が変わったときだけ出します。前回の値を覚えておいて、比べています。

on_params は、階段と周期の変更を拒否します。途中で階段を差し替えると、経過時間の何秒から新しい階段にするかを決めなければならず、仕組みが複雑になります。この手順書では、変えたいときは、3-2節の YAML を直して、launch を起動し直します。

## 3. launch とパラメータの YAML

### 3-1. 依存と実行ファイルの登録

learn_py の setup.py の entry_points に、target_generator を learn_py の target_node の main に結び付ける行を、1行足します。今ある行は残し、フェーズ5-2 の5-3節の一覧の最後に続けます。

learn_bringup の package.xml には、フェーズ5-0 のデモのパッケージ、ros_gz_sim_demos への、実行時の依存を1行足します。フェーズ4 の3-2節で足した exec_depend の並びに加えます。learn_py、launch、launch_ros は、フェーズ4 で足してあります。learn_bringup は、デモのパッケージを、launch ファイルから起動するときにだけ使い、ビルドには使わないので、depend でなく、実行時の依存の exec_depend で書きます。フェーズ4 の3-2節の、depend でなく exec_depend にする理由、のとおりです。

CMakeLists.txt は変えなくてかまいません。フェーズ4 の3-3節の、launch と config の install の指定で、足したファイルもインストールされます。ただし、新しいファイルなので、ビルドは要ります。

### 3-2. パラメータの YAML、config の vehicle_sim.yaml

ファイルは、learn_bringup の config の vehicle_sim.yaml です。

この YAML は、20行ほどで、先頭に概要のコメントが1行あり、4つのノードのまとまりが並びます。どのまとまりも、最上位がノード名で、その下が ros__parameters、その下にパラメータを書く形です。vehicle_plant には、tau_accel を0.5、tau_brake を0.2。pi_controller には、kp を0.5、ki を0.1。target_generator には、step_times を、角かっこで囲んだ10.0、50.0、80.0、step_values を、10.0、5.0、0.0。gz_display には、scale を0.025 と書きます。

原文の説明は3つです。

1つ目。1つのファイルに、4つのノードのパラメータを並べています。最上位のキー、つまり vehicle_plant などがノード名で、launch の Node の name と一致したノードにだけ、その下の値が渡されます。フェーズ4 の4-4節のとおりです。どのノードにも同じファイルを渡し、自分の名前の部分だけが使われます。

2つ目。書いていないパラメータ、たとえば vehicle_plant の mass などは、コードの既定値のままです。ここには、よく変えて試すものだけを書きました。既定値と同じ値でも書いておくと、どの値で動かしたかが、ファイルを見れば分かります。

3つ目。配列は、角かっこで囲んで書きます。小数点を付けます。10、50、80 のように整数で書くと、整数の配列になり、2-2節の型、つまり実数の配列と合わずに、起動が失敗します。7節の表と、3-4節の最後の、型のエラーを確かめる手順で扱います。

### 3-3. launch ファイル、launch の vehicle_sim.launch.py

ファイルは、learn_bringup の launch の vehicle_sim.launch.py です。

vehicle_sim.launch.py は、50行ほどのコードで、ブロックは、import と、generate_launch_description の関数の2つです。import では、LaunchDescription、DeclareLaunchArgument、IncludeLaunchDescription、IfCondition、PythonLaunchDescriptionSource、LaunchConfiguration、PathJoinSubstitution、Node、FindPackageShare を読み込みます。

関数は、パスなどを変数に用意してから、LaunchDescription に、引数の宣言2つ、デモの取り込み1つ、Node 4つの、7つの要素を並べて返します。要の行は、condition に IfCondition の gazebo を付けた2か所、つまりデモの IncludeLaunchDescription と、gz_display の Node です。

原文の解説の要点です。役割は、目標、PI 制御、プラントの3つのノードを必ず起動し、引数 gazebo が true なら、Gazebo のデモと表示用のノードも起動することです。

解説の表は、2列で、6行あります。

gazebo の DeclareLaunchArgument は、Gazebo の部分を起動するかどうかの引数です。既定は、起動します。

params_file の DeclareLaunchArgument は、パラメータの YAML のパスの引数です。既定は、このパッケージの config の vehicle_sim.yaml で、フェーズ4 の4-4節と同じく、FindPackageShare で探します。別のファイルを試したいときは、params_file:= のあとにパスを書いて差し替えます。4-5節で扱います。

FindPackageShare の ros_gz_sim_demos は、自分のパッケージではなく、フェーズ5-0 のデモのパッケージのインストール先を探します。FindPackageShare は、どのパッケージにも使えます。

IncludeLaunchDescription は、フェーズ5-0 のデモの launch、diff_drive.launch.py を取り込みます。launch_arguments の rviz を false にする指定は、フェーズ5-0 で rviz:=false と打っていた引数を、ここで渡しています。

condition に IfCondition の gazebo を付けた項目は、gazebo が true のときだけ実行されます。IncludeLaunchDescription にも Node にも付けられます。

Node の parameters に params_file を渡すのは、4つのノードに同じ YAML を渡すためです。3-2節の1つ目の説明のとおりです。

補足が2つあります。1つ目。gazebo の値は文字列で、IfCondition は、true、false、1、0 を判定します。大文字の True なども使えます。gazebo:=no のような値は、起動のときに、条件の式が正しくない、という趣旨のエラーになります。2つ目。フェーズ5-0 のデモの launch は、Gazebo を起動するときの引数、gz_args を中で固定しているので、取り込む側から、Gazebo を画面なしにする、といった変更はできません。取り込んだ launch に引数として用意されているもの、たとえば rviz だけを変えられます。

### 3-4. ビルドして、引数と中身を確かめる

ros2_ws に移り、colcon build に --symlink-install と、--packages-select に learn_py と learn_bringup の2つを付けてビルドし、source install/setup.bash をしてから、ros2 launch learn_bringup vehicle_sim.launch.py に --show-args を付けて実行します。

期待する結果です。ビルドは、2つのパッケージについて、終わった、という行が出て、2つのパッケージが終わった、という要約で終われば成功です。--show-args の抜粋では、最初の2つが、この launch で宣言した gazebo と params_file で、説明文も表示されます。gazebo の既定値は true、params_file の既定値は、learn_bringup の share を探して config と vehicle_sim.yaml をつなぐ、という置換の式のままで表示されます。その後に、gz_args や rviz など、取り込んだフェーズ5-0 のデモと、その中で取り込まれている gz_sim.launch.py の引数も並びます。--show-args は、取り込んだ launch の引数も一覧に含めます。rviz の既定値は true と表示されますが、この launch が取り込むときに false を渡すので、RViz2 は開きません。gz_args も表示されますが、デモの launch の中で固定されているので、起動するときに指定しても効きません。

続いて、同じ ros2 launch に --print を付けて実行します。

期待する結果です。木の中に、DeclareLaunchArgument が2つ、IncludeLaunchDescription が1つ、そして learn_py の vehicle_plant、pi_controller、target_generator、gz_display を起動する ExecuteProcess が4つ、書いた順に並びます。アドレスは実行ごとに変わります。IncludeLaunchDescription は1行の Action として表示され、中身、つまり Gazebo とブリッジまでは展開されません。gz_display の行は、gazebo:=false を付けて --print しても表示されます。フェーズ5-0 の3-1節と同じく、--print は起動の条件を評価せずに一覧を出すためで、実際に起動したときは条件どおりになります。

step_times を整数で書いたときと、2つの配列の長さがそろっていないときのエラーは、ビルドが済んだここで確かめられます。3-2節の、小数点を付ける、と、2-2節の check_steps の確かめです。1つ目のコマンドは、ros2 run learn_py target_generator に --ros-args を付け、-p で step_times を、整数の10 と50 の配列に、step_values を、10.0 と0.0 の配列にしたものです。2つ目のコマンドは、step_times を10.0 と50.0 に、step_values を10.0 の1つだけにしたものです。

期待する結果、最後の数行の抜粋です。1つ目は、step_times に、型が INTEGER_ARRAY の値を設定しようとしたが、DOUBLE_ARRAY の型が期待されている、という InvalidParameterTypeException が出て、プロセスが失敗で終わった、と出ます。2つ目は、step_times と step_values は同じ長さで空でないこと、という ValueError が出て、同じく失敗で終わります。

1つ目は、宣言した型、つまり実数の配列と違う型、つまり整数の配列が渡されたので、declare_parameter の時点で rclpy が止めています。2つ目は、型は合っていますが、2-2節の check_steps が長さの食い違いを見つけて止めています。どちらも、その前に Traceback から始まる数行が出ます。

横軸は、rqt_plot を開いてからの秒数です。このあとの表の区間の時刻は、launch を起動してからの秒数なので、グラフの目盛りとは、launch を起動してから rqt_plot を開くまでの時間の分だけずれます。

線が出ないトピックがあるとき、の注記です。rqt_plot は、開いたときに1度だけ、引数のトピックが ROS2 のネットワークにあるか、つまり送り手か受け手がいるかを調べて、型を知ります。そのときに見つからなかったトピックは、描く対象に加えず、後でそのトピックが流れ始めても、加え直しません。これは rqt_plot のソースの plot_widget.py で確かめた、とあります。launch より先に開いたときや、launch を起動してすぐ、ノードが起動しきる前に開いたときは、こうなります。手順書を作るときに、送り手を起動して1秒後に開いたら、線が出ないことがあった、とあります。上で、target_generator のログが出てから開くのは、このためです。

グラフの読み方の表があります。4-1節のログの数値から想定した形で、時刻は launch を起動してからの秒数です。4列で、4行あります。列は、区間、目標、速度の線、ペダルの線です。

1行目は、10秒から約16秒で、目標は10 です。速度の線は、ほぼまっすぐに上がります。ペダルの線は、プラス1、つまり全開に張り付いた平らな線です。

2行目は、約16秒から30秒で、目標は10 です。速度の線は、10 に向かって曲がりながら近づきます。ペダルの線は、プラス1 から下がり、0.54 で平らになります。

3行目は、50秒のあたりで、目標は5 です。速度の線は、約1秒で5 の近くまで急に下がります。ペダルの線は、マイナス1、つまりブレーキ全開へ一瞬下がり、すぐプラス0.3 のあたりに戻ります。

4行目は、80秒のあたりで、目標は0 です。速度の線は、1秒から2秒で0 の近くまで下がり、その後わずかに浮きます。ペダルの線は、マイナス1 へ一瞬下がり、プラス0.1 のあたりに戻ります。

加速、つまり約6秒の全開の後、さらに10秒ほどかけて毎秒10メートルに近づくのと、減速、つまり毎秒5メートルに下げるのに約1秒かかるのとの違いが、ペダルの線の、張り付いている長さに表れます。これが、アクセルとブレーキの非対称性の影響です。理由は3つです。

1つ目。アクセル全開の駆動力は3000ニュートンで、ブレーキ全開の制動力9000ニュートンの3分の1しかありません。さらに、速度に比例する抵抗は、加速のときは邪魔をし、つまり速くなるほど加速が鈍り、減速のときは助けます。そのため、加速では、全開のまま長く踏み続けないと届きません。

2つ目。アクセルの遅れ、0.5秒は、ブレーキの0.2秒より長いです。全開から0.54 へ戻す途中でも、駆動力はすぐには減りません。

3つ目。フェーズ5-2 の2-4節で見たとおり、ブレーキの側では、ループが約3倍強く効きます。減速が速いのはそのためで、ゲインを上げると、減速のほうから先に、行き過ぎや振動が出始めます。

グラフの詳しい使い方、つまり軸の範囲の固定、画像の保存、記録した値の再生などは、フェーズ6-1 の3節で扱います。

### 4-4. 止める、Ctrl+C

launch を起動したターミナルで Ctrl+C を押すと、起動したノードがまとめて止まります。フェーズ4 の4-5節の観察のポイントと、フェーズ4 の4-1節の Ctrl+C の期待する結果のとおりです。

期待する結果、Gazebo なしで起動した場合の抜粋です。まず launch が、ユーザーが ctrl-c、SIGINT で中断した、という警告を出し、target_generator、pi_controller、vehicle_plant に、それぞれ SIGINT を送っている、という行が出ます。そのあと、vehicle_plant-1 から Traceback が出て、途中に node.destroy_node の行があり、KeyboardInterrupt で終わります。最後に、vehicle_plant-1 のプロセスが終了コード マイナス2 で死んだ、という ERROR の行が、起動したコマンドの行付きで出ます。pid とパスは実行ごとに変わります。

読み方が4つあります。

1つ目。Traceback や、プロセスが死んだという ERROR の行が出ますが、ノードは止まっていて、異常ではありません。3つの Python のノードのそれぞれに、同じような数行が出ます。

2つ目。理由は、フェーズ4 の4-1節の、Ctrl+C の期待する結果の後の説明と同じです。端末と launch から割り込みが2回届き、2回目で後片付けが中断されます。終了コード マイナス2 は、割り込みの信号で終わった、という意味です。この教材の Python のノードは、どれも同じ main の書き方なので、launch から起動すると、同じ表示になります。

3つ目。もう一度 ctrl-c で中断されたが無視する、という行が続けて出ることもあります。launch 自身が割り込みを2回受け取った場合で、これも問題ありません。

4つ目。手順書を作るときの確かめは、端末の Ctrl+C をまねて、プロセスのグループ全体に割り込みを送る方法で行った、とあります。

### 4-5. YAML を差し替えて条件を変える

パラメータを変えて試すときは、インストールされた YAML を直接書き換えるのではなく、コピーを作って、params_file で渡します。元のファイルは、既定の条件として残しておけます。

cp で、ソースの側の、ros2_ws の src の learn_bringup の config の vehicle_sim.yaml を、ros2_ws の config に、slow_brake.yaml という名前でコピーします。コピーした slow_brake.yaml の、vehicle_plant の tau_brake を0.2 から1.0 に書き換えて、渡します。ros2_ws の config は、フェーズ3-3 で作ったフォルダです。フェーズ4 の3-1節で空になって消した場合は、mkdir -p で作り直します。

コマンドは、ros2 launch learn_bringup vehicle_sim.launch.py に、params_file:= のあとに、ドル記号の HOME から始まる、slow_brake.yaml のパスを付けたものです。

期待する結果です。フェーズ5-2 の6-5節と同じく、50秒ごろに目標が毎秒5メートルへ下がったとき、ブレーキの効きが遅れて、4メートル前後まで下がりすぎ、アクセルを踏み直して5メートルへ戻ります。rqt_plot では、ペダルの線が、マイナス1 とプラス1 の間を、一度大きく振れます。

注意が2つあります。1つ目。params_file:= の後ろは、絶対パスで書きます。チルダで始めると、チルダはこの位置ではシェルに展開されず、そのままの文字で渡ります。ドル記号の HOME は展開されるので、HOME から書きます。2つ目。YAML はテキストのファイルなので、条件ごとにファイルを分けておけば、どの条件で何が起きたかを、後から比べやすくなります。フェーズ3-3 の5-4節の、用途ごとに設定を切り替えられる、の話です。

課題が2つあります。

課題1。slow_brake.yaml の pi_controller のゲインを変えて、tau_brake が1.0 のままでも、下がりすぎが小さくなる組み合わせを探します。フェーズ5-2 の4節の closed_loop_sim.py の cases に、同じ条件を足して、先に計算で当たりを付けてから試すと早い、とあります。筆者の計算では、kp だけを0.3 に下げると、かえって毎秒3.39メートルまで下がりすぎました。kp を0.3、ki を0.05 のように、積分ゲインも下げると、4.08 までに収まります。その代わり、目標に落ち着くまでは遅くなります。積分の項が、ブレーキの遅れの間に育ちすぎないようにするのが効く、とあります。

課題2。target_generator の階段を、step_times を10.0、30.0、50.0、70.0、step_values を5.0、10.0、15.0、0.0 のように変えて、目標が上がる階段と下がる階段で、追いつき方の違いを比べます。毎秒15メートルは、アクセル全開の定常速度、約19.85メートルに近いので、加速はさらに時間がかかります。

## 5. 目標0 で止まりきらない理由

4-1節のログでは、目標を0 にした後、速度がいったん毎秒0.12メートルまで下がってから、0.18 に少し上がりました。フェーズ5-2 の4節の closed_loop_sim.py と同じ計算で、目標を10、5、0 と変えた場合を筆者が計算すると、その後の様子は次のようになります。時刻は、目標を0 にした時刻からの秒数です。

4列の表で、7行あります。列は、経過、速度、ペダル、積分の項です。

0秒では、速度が5.00、ペダルがマイナス1.00、積分の項が0.307 です。

1秒では、速度が0.62、ペダルがマイナス0.07、積分の項が0.242 です。

1.5秒では、速度が0.12、ペダルがプラス0.17、積分の項が0.229 です。

4秒では、速度が0.25、ペダルがプラス0.06、積分の項が0.181 です。

10秒では、速度が0.06、ペダルがプラス0.07、積分の項が0.101 です。

20秒では、速度が0.01、ペダルがプラス0.07、積分の項が0.076 です。

30秒より後では、速度が0.00、ペダルがプラス0.07、積分の項が0.074 です。

1.5秒ごろに毎秒0.12メートルまで下がった後、ペダルがアクセルの側に戻って、4秒ごろに0.25 まで浮き、その後20秒ほどかけて、ゆっくり0 へ近づきます。4-1節のログの、0.12 から0.18 は、この浮き上がりの途中を見ています。

原因は、フェーズ5-2 の2-2節の積分の項と、フェーズ5-1 の2-1節の、後ろへは進まない、の組み合わせにあります。目標が毎秒5メートルのとき、積分の項は、5メートルを保つのに必要な0.31 まで育っていました。目標が0 になっても、積分の項はすぐには0 に戻りません。偏差、つまり目標から速度を引いたものは、速度が0 以上なので、0 以下にしかならず、速度が小さくなるほど偏差も小さくなるので、積分の項が減る速さ、つまり K の i かける偏差も、遅くなります。速度が0 に近づくと、比例の項も0 に近づくので、ペダルは、残った積分の項、つまりプラスのアクセルに近づき、車両がわずかに押し出されます。最後は、ペダルが0.074、つまりフェーズ5-1 の2-3節の、動き出さない境目まで下がったところで、駆動力と転がり抵抗がつり合って止まります。表のそれぞれの段階の動きの理由を詳しく追う説明は、フェーズ5 の後の任意の間章、古典制御の間章の4-1節で扱います。

PI 制御は、偏差を0 にするための仕組みで、止まる、後ろへは進まない、といった、式の外の決まりを知りません。そのため、ちょうど境目で止まるのは苦手です。実物の車両の制御では、目標が0 のときは積分の項を0 に戻してブレーキを踏ませる、といった、状況に応じた切り替えを、制御器の外側に足すことが多い、とあります。

課題3。pi_node.py の on_timer に、目標が0 で、速度も十分小さい、たとえば毎秒0.5メートル未満のときは、積分の項を0 に戻し、ペダルをマイナス0.3、つまり弱いブレーキにする、という処理を足し、4-1節と同じ条件で、目標0 の後に速度が浮かないことを確かめます。書き換えるのは pi_node.py だけで、式のクラスの pi_control.py は変えません。状況による切り替えは、式の外側に置く、という分担になります。

## 6. このフェーズのまとめ

まとめは7つです。

1つ目。目標のように実行中に変わる入力は、専用のノードで作ってトピックで送ると、launch で一式を起動するだけで、同じ実験を繰り返せます。

2つ目。配列のパラメータは、既定値にリストを渡して宣言します。YAML では、小数点を付けて書きます。整数だと型が合いません。

3つ目。別のパッケージの launch も、FindPackageShare と IncludeLaunchDescription で、そのまま取り込めます。取り込んだ側から変えられるのは、取り込まれる側が引数として用意したものだけです。

4つ目。IfCondition を付けると、引数で一部の起動を切り替えられます。重い部分、つまり Gazebo を外して、軽く試せます。

5つ目。複数のノードのパラメータを1つの YAML にまとめ、ファイルを差し替えて条件を変えられます。

6つ目。launch から起動した Python のノードを Ctrl+C で止めると、Traceback と、プロセスが死んだという表示が出ることがありますが、異常ではありません。

7つ目。学習計画のフェーズ5 の完了の条件のうち、階段の形の目標の速度に追いつく、は4-1節のログで、アクセルとブレーキの非対称性の影響をグラフで説明する、は4-3節のグラフの読み方で確かめました。残りの、同じゲインで、自作のプラントと Gazebo の物理の追いつき方の違いを説明する、はフェーズ5-4 で扱います。フェーズ5 全体のまとめは、フェーズ5-4 の9節に載せます。

## 7. つまずきやすい点

2列の表で、10行あります。列は、症状と、確かめることです。

1行目。パッケージ learn_bringup が見つからない、と出る場合。フェーズ4 の3節の準備が済んでいるか、colcon build で learn_bringup もビルドし、source install/setup.bash をしたかを確かめます。

2行目。vehicle_sim.launch.py というファイルが見つからない、と出る場合。新しいファイルを足した後に、learn_bringup をビルドし直したかを確かめます。フェーズ4 の3-3節のとおりで、既にあるファイルの編集なら要りません。

3行目。パッケージ ros_gz_sim_demos が見つからない、と出る場合。フェーズ5-0 の1-2節で導入したかを確かめます。

4行目。target_generator が、INTEGER_ARRAY のエラーで止まる場合。YAML や -p の配列を、小数点を付けて書いたかを確かめます。3-2節のとおりです。

5行目。パラメータが効いていない場合。YAML の最上位のノード名が、launch の Node の name と一致しているかを確かめます。ros2 param get で確かめます。フェーズ4 の4-4節のとおりです。

6行目。params_file:= のあとをチルダで始めて、ファイルが見つからない場合。チルダは展開されません。ドル記号の HOME から書くか、絶対パスで書きます。4-5節のとおりです。

7行目。Gazebo が開く前に、車両が走り出す場合。step_times の最初の値を大きくして、目標の切り替えを遅らせます。2-1節のとおりです。

8行目。Ctrl+C で、Traceback と、プロセスが死んだという表示が出る場合。異常ではありません。4-4節のとおりです。

9行目。rqt_plot に、線が出ないトピックがある場合。トピックの指定が、スラッシュ、トピック名、スラッシュ data、になっているかを確かめます。rqt_plot を開いたときに、そのトピックが見つからなかった場合は、ウィンドウの Topic の欄から足すか、開き直します。4-3節の注記のとおりです。

10行目。目標0 の後、車両がしばらく動く場合。積分の項が残るためです。5節で説明しています。5節の最後の課題3で、対策できます。
