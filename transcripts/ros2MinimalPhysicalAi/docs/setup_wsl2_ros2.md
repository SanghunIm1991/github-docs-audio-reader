# 環境構築: WSL2 と Ubuntu 24.04 と ROS2 Jazzy（聞くための原稿）

これは、ros2MinimalPhysicalAi という教材の、環境構築の手順書の話です。教材の中では、ステップ0 にあたります。

Windows の PC に、WSL2 で Ubuntu 24.04 を入れ、その中に ROS2 Jazzy を導入します。WSL2 は、Windows の上で Linux を動かす仕組みです。フェーズ0 の読み物の後、フェーズ1 で実際に手を動かす前に行う、この教材の最初の作業です。

想定する環境は、Windows 11 です。WSL2 が使える Windows 10 でもかまいません。CPU の仮想化支援の機能が有効であることが条件で、これは1節で確かめます。

所要時間の目安は2時間程度です。ダウンロードの時間と Windows の再起動を含み、回線の速さで前後します。任意の2b節と7節は含みません。

必須の範囲は、1節から5節と、6節のワークスペースの場所です。任意の範囲は、2b節の、仮想ディスクを別のドライブへ移す手順と、7節の、GitHub の認証と Claude Code の環境です。

原文は、この手順書の位置づけをこう書いています。必須の範囲だけで、フェーズ1 以降の手順書をすべて進められます。任意の2つの節は、必要な人だけが行えばよいものです。2b節は、C ドライブの空きが少ない PC で、Ubuntu の保存先を別のドライブへ移す手順です。7節は、非公開の GitHub のリポジトリを扱う場合や、AI のコーディング支援ツールの Claude Code を WSL の中で使う場合の準備で、この教材の作者の運用に合わせたものです。

期待する結果の出どころについても、断りがあります。Windows の側、つまり PowerShell の表示は、各ツールの仕様から想定したものです。Ubuntu の側の表示は、筆者の環境で確かめたものと、仕様から想定したものが混ざっています。版の数字や、表示の言語が日本語か英語かは、環境によって違います。

## 目的とゴール

WSL2 の上に、Ubuntu 24.04 と、apt のバイナリパッケージの ROS2 Jazzy を導入し、ROS2 が動くことを確かめます。

完了の判定の基準は5つで、すべて満たしたら完了です。

1つ目。wsl -l -v で、Ubuntu-24.04 が VERSION 2 として表示される。これは2節です。

2つ目。Ubuntu の中で lsb_release -a が 24.04 を示す。3節です。

3つ目。printenv ROS_DISTRO が jazzy を返す。5節です。

4つ目。ros2 run demo_nodes_cpp talker と、ros2 run demo_nodes_py listener を別々のターミナルで動かし、メッセージが届く。これも5節です。

5つ目。ワークスペースを作るホームディレクトリが、WSL の Linux のファイルシステム、つまり /home の下の自分のユーザー名のフォルダにあり、/mnt/c や /mnt/d の下ではない。6節です。

2b節を行った場合は、あわせて、WSL の仮想ディスク、ext4.vhdx が移動先のドライブにあることも確かめます。

## 注意

原文は、4つの注意を挙げています。

1つ目。導入の作業は、自分の手で行います。コマンドの意味が分からないまま、貼り付けて実行しないでください。

2つ目。パスワード、つまり Linux のユーザーと sudo のパスワードは、チャット、ファイル、ログに残さないでください。

3つ目。ROS2 の導入は、apt のリポジトリと GPG キーの追加を伴います。公式のページに載っている手順と取得元だけを使い、ブログなどに載っている別の取得元は使わないでください。

4つ目。この手順では、Windows の側のセキュリティの設定、例えば Defender やファイアウォールは変えません。変える必要があるように見える場面では、止まって確かめます。

## 1. 事前の確認（Windows の側）

確かめることは3つです。

1つ目は、仮想化支援です。BIOS または UEFI で、CPU の仮想化支援、つまり Intel VT-x か AMD-V が有効かを確かめます。タスクマネージャーのパフォーマンスの、CPU の欄の「仮想化: 有効」で確かめられます。

2つ目は、空き容量です。目安は20GB 以上で、Ubuntu と ROS2 の desktop の分です。WSL の仮想ディスクは、既定で C ドライブに作られます。C ドライブの空きが少なく、D ドライブなど別のドライブに余裕がある場合は、2節の後に、任意の2b節で移します。

3つ目は、メモリです。WSL2 の既定の設定、つまり物理メモリの約半分を WSL2 に割り当てる設定のまま、始めてかまいません。この教材のフェーズ2 から4 のビルドは、既定の設定で足りることを確かめています。足りないと感じた場合は、上限の調整、つまり .wslconfig のファイルを、別に検討します。

## 2. WSL2 と Ubuntu 24.04 の導入（Windows の側）

手順は4つです。

1つ目。管理者の権限の PowerShell で、wsl --install -d Ubuntu-24.04 を実行します。案内は、Microsoft の公式の短縮 URL にあります。

2つ目。再起動を求められたら、再起動します。

3つ目。Ubuntu の初回の起動で、Linux のユーザー名とパスワードを設定します。これは Windows のアカウントとは別のものです。

4つ目。確認として、PowerShell で wsl -l -v を実行して VERSION が2 であることを確かめ、wsl --version も実行します。VERSION が1 の場合は、wsl --set-version Ubuntu-24.04 2 で変換します。

期待する結果は、こうです。wsl -l -v では、NAME、STATE、VERSION の3列の表が出て、Ubuntu-24.04 の行の STATE が Running、VERSION が2 になります。行の先頭には、アスタリスクの印が付きます。wsl --version では、WSL のバージョン、カーネルのバージョン、WSLg のバージョンなどの行が並びます。版の数字は更新によって変わり、表示の言語は Windows の設定によります。

読み方は2つです。wsl -l -v のアスタリスクは、既定のディストリビューション、つまり wsl とだけ打ったときに起動するものの印です。VERSION が2 であることが大事で、1 のままだと、ROS2 の GUI の表示、つまり WSLg などが使えません。また、wsl --version に WSLg のバージョンの行があれば、フェーズ1 で使う GUI の表示の仕組み、WSLg が入っています。

## 2b. 任意: Ubuntu の保存先を別のドライブへ移す（Windows の側。ROS2 を入れる前に行う）

この節が必要なのは、C ドライブの空きが少ない場合、目安として20GB を大きく下回る場合だけです。空きに余裕があれば、飛ばして3節へ進みます。原文は、移動先を D ドライブの WSL というフォルダの下とした例で書いています。

目的は、WSL2 の仮想ディスク ext4.vhdx を、ROS2 を導入する前の、中身がほぼ空の状態で、別のドライブへ移すことです。必ず4節の ROS2 の導入より前に行います。導入した後に行うと、エクスポートのファイルが大きくなり、失敗したときの影響も大きくなるからです。

影響も書かれています。移動先のドライブにフォルダを作り、WSL のディスクイメージを置きます。外部との通信や、Windows のセキュリティの設定の変更はありません。ただし、wsl --unregister は、対象のディストリビューションのデータを完全に消すので、エクスポートしたファイルがあることとその大きさを確かめてから実行します。この時点の Ubuntu は導入した直後なので、失うものはほぼありません。

方法は2つあります。

### 方法A: エクスポートとインポート

どの版の WSL でも使える、標準の手順です。11の手順があります。

1つ目。2節の初回の起動で、ユーザー名とパスワードを設定してあること、そして Ubuntu の中に自分で作ったデータやファイルが無いこと、つまり導入した直後の状態であることを確かめます。データがある場合は、先に必要なものを退避します。

2つ目。Ubuntu の中で、既定のユーザーを固定します。インポートした後は、既定のユーザーが root に戻ってしまうので、その対策です。まず cat /etc/wsl.conf で、今の内容を確かめます。Ubuntu 24.04 では、systemd の設定などのために、boot の節がすでにあることがあります。その場合は、今の内容を消さず、user の節だけを書き足します。ファイルが無い場合は、新しく作ります。編集は sudo nano /etc/wsl.conf で行い、user という節を作って、その下に default イコール自分のユーザー名、という1行を書いて保存します。保存した後に、もう一度 cat /etc/wsl.conf を実行し、user の節が入っていることと、前からあった節が残っていることを確かめます。boot の節が元からあった場合の期待する結果は、boot の節の systemd イコール true の行の後に、空行を挟んで、user の節の default の行が続く形です。

3つ目。PowerShell で、作業のフォルダを作ります。New-Item のコマンドで、D ドライブの WSL の下に、backup と Ubuntu-24.04 の2つのフォルダを作ります。

4つ目。wsl --shutdown で、Ubuntu を止めます。これは、ほかの WSL のディストリビューションも含めて、WSL 全体を止めます。ほかに動いているものがあれば、先に作業を保存しておきます。

5つ目。wsl --export で、Ubuntu-24.04 を、backup のフォルダの ubuntu-24.04-fresh.tar というファイルにエクスポートします。

6つ目。確認として、Get-Item でそのファイルがあることと、大きさを確かめます。Length の列が大きさで、単位はバイトです。数百MB 以上あればよく、極端に小さい、または0 の場合は、エクスポートに失敗しているので、5つ目の手順をやり直します。

7つ目。C ドライブの側の登録を解除します。実行する前に、wsl -l -v で、対象が Ubuntu-24.04 であることをもう一度確かめます。確かめてから、wsl --unregister Ubuntu-24.04 を実行します。ほかの名前のディストリビューションを指定しないように、とあります。

8つ目。wsl --import で、移動先の Ubuntu-24.04 のフォルダへ、さきほどの tar のファイルを、バージョン2 としてインポートします。

9つ目。確認として、wsl -l -v で Ubuntu-24.04 が VERSION 2 であることを確かめ、wsl -d Ubuntu-24.04 で中に入って、whoami が2節のユーザー名になっていることを確かめます。root と表示されたら、2つ目の手順の /etc/wsl.conf を見直します。なお、インポートした後は、Windows Terminal のプロファイルや、スタートメニューの登録が変わることがあります。wsl -d Ubuntu-24.04 で入れれば、問題ありません。

10個目。仮想ディスクの場所を確かめます。Test-Path で、移動先のフォルダに ext4.vhdx があるかを調べ、True と表示されればよいです。

11個目。バックアップの tar のファイルは、環境が安定して動くことを確かめられるまで残します。その後は消してかまいません。

### 方法B: wsl --manage --move

新しい版の WSL だけで使える、任意の方法です。登録済みのディストリビューションを移すコマンドがあります。wsl --manage --help に --move が表示される場合に限り、wsl --manage Ubuntu-24.04 --move に移動先のフォルダを付けて実行すれば、移せます。移動先のフォルダは、方法Aの3つ目の手順のコマンドで、先に作っておきます。表示されない場合は、方法Aを使います。なお、方法Aの2つ目の手順、つまり既定のユーザーの固定は、方法B では要りません。

## 3. Ubuntu の更新（Ubuntu の中）

手順は4つです。

1つ目。sudo apt update と sudo apt upgrade を、続けて実行します。

2つ目。確認として、lsb_release -a が 24.04 を示すことを確かめます。期待する結果は、ディストリビューションの名前が Ubuntu、説明が Ubuntu 24.04 のいくつかの LTS、Release が 24.04、Codename が noble、という行が並ぶ形です。Release が 24.04、Codename が noble であればよく、説明の末尾の小さな版数は、更新によって変わります。

3つ目。作業の場所は、ホームディレクトリの下にします。pwd が、/home の下の自分のユーザー名のフォルダの下であることを確かめます。

4つ目。pwd が /mnt/c や /mnt/d の下になる場合の話です。これは、wsl が、Windows の側の今のフォルダ、例えば D ドライブの一番上を、そのまま引き継ぐ仕様のためで、異常ではありません。ホームで始めるには、起動するときに wsl --cd ~ -d Ubuntu-24.04、または wsl ~ -d Ubuntu-24.04 と指定します。毎回指定したくない場合は、Windows Terminal の設定で、Ubuntu-24.04 のプロファイルの開始ディレクトリを、wsl.localhost の下の、Ubuntu-24.04 の自分のホームのフォルダにします。古い形式では、wsl$ で始まる形になります。ただし、これは Windows Terminal を使っていて、Ubuntu-24.04 のプロファイルがある場合だけです。2b節の wsl --import で作った環境では、プロファイルが自動で作られないことがあります。また、~/.bashrc に cd ~ を書く方法は、wsl --cd で意図して別の場所から始めたときも上書きされてしまうので、勧めない、とあります。

## 4. ROS2 Jazzy の導入（Ubuntu の中。公式の手順）

公式の Installation のページの、Jazzy の版の、Ubuntu の deb パッケージの手順に、上から従います。

原文には、この節のコマンドについての断りがあります。コマンドは、公式のページ、そのソースである ros2/ros2_documentation リポジトリの jazzy ブランチから抜粋し、コメントと注意書きを加えたもので、改変があります。ROS 2 のドキュメントは、CC BY 4.0 で公開されています。取得は要約を経由したため、一語ずつの書き写しではありません。内容は2026年9月20日の時点のもので、版によって変わりえます。実行する前に公式のページと照らし合わせ、食い違いがあれば、公式のページを正とします。公式のページは、上部のボット対策、Anubis のために自動で取得できなかったので、GitHub の上のソースから取得した、とあります。

この原稿では、この節のコマンドは書き写さず、何をするものかを言葉で説明します。手順は5つです。

1つ目は、ロケール、つまり UTF-8 の設定です。locale のコマンドで、すでに UTF-8 になっていれば要りません。そうでなければ、apt で locales のパッケージを入れ、英語の UTF-8 のロケールを作って、システムの既定と、今のターミナルの言語の設定を、英語の UTF-8 にします。最後に locale で確かめます。期待する結果は、LANG の行が UTF-8 で終わっていることです。WSL の Ubuntu では、最初から C.UTF-8 になっていることが多いそうです。

2つ目は、universe のリポジトリと、ROS2 の apt の取得元の追加です。software-properties-common のパッケージを入れ、universe のリポジトリを有効にし、curl を入れます。続いて、GitHub の API で、ros-infrastructure の ros-apt-source というリポジトリの、最新のリリースの版の番号を調べて、環境変数に入れます。そして、その版の、Ubuntu の名前に合った ros2-apt-source の .deb のファイルを、tmp のフォルダにダウンロードします。

原文は、ここで一度止まり、注記を確かめてから次へ進むように言っています。次は、dpkg -I で、ダウンロードした .deb のファイルの中身を確かめます。これは確認のためで、インストールはしません。そのうえで、sudo dpkg -i でインストールします。

注記は3つです。1つ目。この手順は、GitHub から取得した .deb を管理者の権限でインストールし、以後の apt の取得元に、ROS2 のリポジトリを足すものです。取得元は公式の ros-infrastructure/ros-apt-source ですが、外部から取得したパッケージを導入する操作なので、URL が手順のとおりであることを確かめてから実行します。2つ目。sudo dpkg -i の前に、dpkg -I の出力で、パッケージの名前、版、依存関係を目で確かめます。これは内容の確認で、改ざんを見つける整合性の検証ではありません。3つ目。版の番号を入れた環境変数が空になる場合は、GitHub の API の、認証しないアクセスの回数の制限に当たっているかもしれません。echo で中身を確かめ、しばらく待ってからやり直します。

dpkg -I の期待する結果は、Package の行が ros2-apt-source、Version の行が 1 の何々の noble、Architecture の行が all で、Description の行に、ROS 2 の apt の取得元を設定するパッケージだということが書かれていることです。そうであれば、意図したファイルです。版の数字は、取得した時期によって変わります。

3つ目は、開発のツールの導入です。apt で、ros-dev-tools というパッケージを入れます。これは colcon を含みます。期待する結果は、導入するパッケージの一覧が表示され、続けるかどうかを Y か n で聞かれるので、Y で進めることです。最後に、E とコロンで始まるエラーの行が出ずにプロンプトへ戻れば、成功です。colcon --help で使い方が表示されれば、colcon が使えます。補足として、ros-dev-tools は、colcon のほかに、C++ のコンパイラの g++、make、cmake も、依存として一緒に入れます。ros-build-essential から build-essential を経由するためです。C++ のコンパイラを別に入れる必要はありません。詳しくは、フェーズ2 の1-3節の補足にあります。

4つ目は、ROS2 本体の導入です。学習用には、rqt や turtlesim などを含む Desktop Install を選びます。apt の update と upgrade をしてから、ros-jazzy-desktop のパッケージを入れます。期待する結果は、導入するパッケージの一覧と容量が表示され、Y で進めることです。数百のパッケージが入るので、回線によっては数十分かかります。最後にエラーの行が出ずにプロンプトへ戻れば成功で、ls /opt/ros を実行すると jazzy と表示されます。

5つ目は、環境の読み込みです。opt の ros の jazzy の下の setup.bash を、source のコマンドで読み込みます。期待する結果は、何も表示されないことです。source は、成功しても何も表示しません。

この読み込みの行は、~/.bashrc に書き足します。新しいターミナルを開くたびに手で source が要ると、フェーズ1 以降の手順書が前提とする「ROS2 は読み込み済み」という前提が崩れ、ターミナルごとに動きが食い違う原因になるからです。書き足す内容は、自分で確かめたうえで行います。

原文は、~/.bashrc に書き足す行を、累積の一覧として管理しています。今の時点では1行だけで、この手順で足した、ROS2 本体の読み込みの行です。いつも必要で、消さない行です。以後のフェーズの手順書で足す必要が出たら、その手順書の中に、この行を含めた累積の一覧を載せる、とあります。

## 5. 動作の確認（Ubuntu の中）

手順は4つです。

1つ目。printenv ROS_DISTRO が jazzy を返すことを確かめます。

ここで、次の2つの手順の ros2 run の説明があります。ros2 run は、ros2 run の後にパッケージの名前と実行ファイルの名前を続ける形で、パッケージに入っているプログラムを起動するコマンドです。ここでは、ROS2 に付属するデモ、つまり C++ 版の送信側の talker と、Python 版の受信側の listener を起動します。

2つ目。1つ目のターミナル、T1 で、ros2 run demo_nodes_cpp talker を実行します。

3つ目。2つ目のターミナル、T2 で、ros2 run demo_nodes_py listener を実行します。

4つ目。T2 にメッセージが表示されることを確かめ、T1 と T2 のどちらも Ctrl+C で止めます。

期待する結果は、こうです。T1 の C++ の talker は、INFO の印と時刻と talker という名前の後に、「Publishing」と、Hello World と番号の文を表示します。番号は1、2と増えていきます。T2 の Python の listener は、listener という名前の後に、「I heard」と、受け取った Hello World と番号の文を表示します。時刻の数字は、実行するごとに変わります。

T1 は1秒ごとに番号を増やしながら送り、T2 は同じ番号の文を受け取ります。C++ で書かれた送信側と、Python で書かれた受信側がつながっていて、ROS2 の通信が言語をまたいで動くことの、最初の確認になります。

なお、rqt や turtlesim のような GUI のアプリの表示、つまり WSLg は、フェーズ1 の1-2節で確かめます。この手順書の完了の条件には含めません。

## 6. 練習用のワークスペースの場所を確かめる（Ubuntu の中）

フェーズ2 以降の手順書は、練習用のワークスペース、つまり自分で書くコードをまとめてビルドするフォルダを、ホームディレクトリの下の ~/ros2_ws に作る前提で書いています。フォルダそのものは、フェーズ2 の2-1節で作ります。ここでは、ホームディレクトリの場所だけを確かめます。

コマンドは2つで、cd ~ でホームへ移り、pwd で今の場所を表示します。期待する結果は、pwd が、/home の下の自分のユーザー名と表示されることです。cd は、成功しても何も表示しません。

注意が2つあります。1つ目。/mnt/c や /mnt/d の下、つまり Windows の側のドライブに、ワークスペースを作らないでください。Windows と Linux のファイルシステムをまたぐので、ビルドがとても遅くなります。2つ目。この教材は GitHub で読む前提で、リポジトリを clone する必要はありません。手元に置きたい場合は clone してもかまいませんが、ワークスペースは教材のフォルダの中ではなく、上のとおり ~/ros2_ws に作ります。練習のコードと教材のファイルが混ざらないようにするためです。

## 7. 任意: GitHub の認証と Claude Code の環境（Ubuntu の中）

この節が必要なのは、非公開の GitHub のリポジトリを WSL の中で clone や push する場合と、Claude Code を WSL の中で使う場合だけです。フェーズ1 以降の学習には要りません。この節は、この教材の作者の運用、つまり Claude Code に手順書の作成やレビューを手伝わせる運用に合わせて書いています。6つの手順があります。

### 7-1. GitHub の認証

非公開のリポジトリは、認証していない WSL では git clone が失敗し、Repository not found や Authentication failed となります。WSL の git は、Windows の側の設定や認証を引き継がないので、WSL の中で、次の A か B のどちらかを設定します。推奨は A の SSH の鍵で、追加のツールの導入が要らないからです。

A の SSH の鍵の手順は、5つです。

1つ目。WSL の中で、鍵を新しく作ります。コマンドは ssh-keygen で、鍵の種類に ed25519、コメントに wsl-ubuntu、保存先に ~/.ssh の id_ed25519 を指定します。パスフレーズの設定は必須です。この鍵はアカウントの下のすべてのリポジトリにアクセスできるので、パスフレーズなしにしてはいけません。期待する結果は、パスフレーズを2回聞かれ、入力した文字は表示されず、最後に鍵の指紋と、記号で描いた図、randomart が表示されることです。そうなれば、秘密鍵の id_ed25519 と、公開鍵の id_ed25519.pub ができています。

2つ目。公開鍵、つまり .pub のファイルだけを、cat で表示してコピーします。秘密鍵、つまり拡張子の無いファイルは、絶対に表示したり共有したりしません。期待する結果は、ssh-ed25519 で始まり、長い文字列が続き、wsl-ubuntu で終わる1行です。この1行を丸ごとコピーします。

3つ目。ブラウザで GitHub にログインし、Settings の SSH and GPG keys の New SSH key に貼り付けて登録します。Title は、WSL Ubuntu などにします。

4つ目。ssh -T git@github.com で、接続を確かめます。初回は、接続先のフィンガープリントの確認が出ます。GitHub の公式のドキュメントの「GitHub's SSH key fingerprints」に載っているものと一致する場合だけ yes と答え、一致しなければ yes とせずに中断します。期待する結果は、Hi と GitHub のユーザー名の後に、認証に成功した旨の英語の文が出ることです。

5つ目。clone には、SSH の形式の URL を使います。

A についての補足が2つあります。パスフレーズは、clone や push のたびに入力を求められます。学習の用途なら、毎回入力して問題ありません。手間なら、ssh-agent に鍵を読み込ませて、セッションの間の入力を省けます。ssh-agent を起動してから ssh-add で鍵を読み込む方法で、ssh-agent はシェルを閉じると終わります。もう1つ、鍵の権限の範囲について、対象のリポジトリだけに効く Deploy key という登録の方法もあります。同じアカウントで push も行うなら、アカウント全体に効く鍵として扱います。

B は、GitHub CLI、つまり gh のブラウザでの認証です。gh は、Ubuntu 24.04 に標準では入っていない場合があり、導入するときは公式の手順に従います。gh auth login を実行し、GitHub.com、HTTPS、ブラウザでの認証を選び、表示されたワンタイムのコードをブラウザで入力して承認します。終わったら、gh auth status で確かめられます。clone は HTTPS の形式の URL で行います。トークンの保管には注意が要ります。WSL にはキーリングが無いことが多く、その場合、トークンは ~/.config/gh の hosts.yml に、平文で保存されることがあります。既定のスコープも広めです。要らなくなったら gh auth logout を実行し、GitHub の Settings のアプリやトークンの一覧からも失効させます。

原文は、A と B の後に、注意を3つ挙げています。

1つ目。アカウントは、対象のリポジトリにアクセスできるものを使います。登録の前に、ブラウザでログインしているアカウントを確かめます。別のアカウントだと Repository not found になります。認証の情報、つまり鍵やトークンは、WSL 専用の別のもので、Windows の側とは共有されません。

2つ目。パスワードや PAT、つまり Personal Access Token を、コマンドの履歴やファイルに残しません。Windows の側の .ssh や資格情報は流用しません。

3つ目。鍵を登録するのは、この WSL 専用です。要らなくなったら、GitHub の SSH keys の画面から消せます。

### 7-2. リポジトリの clone

ホームに移ってから、git clone でリポジトリを取得し、できたフォルダに移ります。A の SSH の場合は、git@github.com から始まる SSH の形式の URL を、B の gh の場合は、https から始まる形式の URL を使います。どちらも、自分の GitHub のユーザー名の下の ros2MinimalPhysicalAi.git を指定します。期待する結果は、Cloning into と、リポジトリの名前が表示され、ホームディレクトリの下に同じ名前のフォルダができることです。A の SSH の場合は、途中で鍵のパスフレーズを聞かれます。

補足があります。Claude Code にコミットさせる場合は、Claude が関わったコミットを区別する規約、例えばメッセージの接頭辞などを、リポジトリの CLAUDE.md に書いておきます。この教材のリポジトリの例は、CLAUDE.md の「Git運用」にあります。また、コミットに記録されるメールアドレスには、実際のアドレスではなく、GitHub が用意する noreply のアドレスを使います。author と committer のどちらにも user.email が使われるので、リポジトリの単位の git config user.email で設定します。実際のメールアドレスは、一度コミットに入ると、履歴から消すのが難しいからです。

### 7-3. Claude Code の導入

Anthropic の公式の Claude Code のドキュメントで、最新のインストールの手順を確かめ、その手順で導入します。リンク先は変わりえるので、公式のサイトから探します。出どころの分からないスクリプトは使いません。

### 7-4. Claude Code の設定を、別の PC から引き継ぐ場合

Claude Code の設定のディレクトリ ~/.claude は、Windows の側から引き継がれません。自分の設定、例えばグローバルのルールなどを GitHub のリポジトリで管理している場合は、ここへ clone します。

これは、Claude Code を初めて起動する前に行います。起動すると ~/.claude が作られ、clone する先が空でなくなるからです。すでにある場合は、中身を確かめてから、例えば名前を変えて退避します。clone のコマンドは、設定のリポジトリの URL と、~/.claude を指定する形です。期待する結果は、Cloning into と、ホームの下の .claude が表示され、そこに設定のファイルが入ることです。

clone した後の確認が2つあります。内容に、Windows に固有の記述、例えば settings.json の permissions のパスや、PowerShell を前提にしたルールなどが残っていないかを確かめ、必要なら WSL 用に直します。また、認証の情報やブラウザのプロファイルのような機微なファイルが含まれていないかも確かめます。あわせて、projects のフォルダ、つまりメモリやセッションの履歴など、Windows の側の作業の履歴が含まれていないかも確かめます。

### 7-5. 起動

clone したプロジェクトのディレクトリで、claude を起動します。

### 7-6. 導入の作業のレビューを頼む場合

実施した内容を Claude Code などにレビューしてもらうときは、次の3つを貼り付けます。実行したコマンド、例えば history のその部分。各確認のコマンドの出力。そして、~/.bashrc に書き足した場合は、書き足した行です。貼り付ける前に、認証の情報やパスワードが含まれていないことを確かめてください、とあります。

## つまずきやすい点

原文は、7つのつまずきやすい点と、その対処を挙げています。

1つ目。仮想化が無効だと、wsl --install が失敗します。1節の BIOS や UEFI の設定を確かめます。

2つ目。/mnt/c や /mnt/d の下で作業すると、ビルドが遅くなります。ホームの下で作業します。6節です。

3つ目。wsl を起動した直後の pwd が、/mnt/c や /mnt/d などになります。Windows の側の今のフォルダを引き継いでいるだけです。wsl --cd ~ -d Ubuntu-24.04 で起動します。3節の4つ目の項目です。

4つ目。ターミナルを開き直すと、ros2 が見つかりません。ROS2 の setup.bash を読み込む行が、~/.bashrc に書き足されていません。4節の5つ目の手順です。

5つ目は、2b節を行った場合です。インポートした後に、root でログインされます。/etc/wsl.conf の user の節の default が設定されていません。2b節の方法Aの2つ目の手順です。

6つ目は、7節を行う場合です。非公開のリポジトリの git clone が、Repository not found や Authentication failed の認証のエラーになります。WSL の git は、Windows の側の認証を引き継ぎません。7節の1つ目の手順で、SSH の鍵か gh の認証を設定します。ssh -T git@github.com で、認証の状態を切り分けられます。

7つ目も、7節を行う場合です。~/.claude への clone が、「already exists and is not an empty directory」、つまりすでにあって空ではない、というエラーで失敗します。Claude Code を先に起動して、作られてしまっています。中身を確かめて退避してから clone します。7節の4つ目の手順です。
