# フェーズ5-4: プラントを Gazebo の物理に差し替える（聞くための原稿）

これは、ros2MinimalPhysicalAi という教材の、フェーズ5-4 の手順書の話です。学習計画のフェーズ5 の5-4 にあたります。フェーズ5-1 で自作した疑似プラント、vehicle_plant の代わりに、Gazebo の物理エンジンが計算する車両を、プラントにします。PI 制御のノード、つまりフェーズ5-2 の pi_controller は、一行も変えずにつなぎ替え、同じゲインで、追いつき方がどう変わるかを比べます。プラントを差し替えても、制御のノードはそのまま使える、という、トピックで部品をつなぐ ROS2 の利点を確かめるのが、この手順書の目的です。

想定する環境は、WSL2 と Ubuntu 24.04 と ROS2 Jazzy です。前提は、フェーズ5-3 を終え、learn_bringup に vehicle_sim.launch.py があり、target_generator が動くことです。所要時間の目安は2から3コマで、言語は Python です。launch も Python の形式で書きます。

原文の進め方の囲みです。2節で、Gazebo の車両を力で動かせるワールドを用意し、3節で、実車の単位と Gazebo の縮尺の関係を式にします。4節で、ペダルを車輪のトルクに変えるノードを書き、5節で、シミュレーションの時刻の扱いを押さえます。6節の launch で一式を起動し、7節で、フェーズ5-3 の結果と比べます。サンプルは学習の手がかりとして最小限に書いたもので、公式のチュートリアルの転載ではありません。コードは手順書を作るときに、使い捨ての環境でビルドし、Gazebo を画面なしで起動して、一連の動きを確かめました。画面の見え方と、rqt_plot のグラフは確かめていません。出力が違うときは、実機の表示を優先します。

期待する結果の出どころの囲みもあります。gz sdf の -k、ビルド、launch の --show-args と --print の表示と、6-3節の launch のログ、7節の比べの数値は、使い捨ての環境で、Gazebo を画面なしで実際に実行した表示で、時刻と pid は実行ごとに違います。ログは抜粋です。3-2節の加速度の値は、筆者が実験で測った値です。6-3節の画面の様子と、6-4節のグラフの見え方は、ログの数値から筆者が想定したものです。

## 0. 学習目標と完了の条件

学習目標は4つです。

1つ目。既にあるワールドファイルを写して、車両を、速度ではなく、力、つまりトルクで動かせるように改造できる。改造したファイルの出典と変更点を残せる。

2つ目。実車の単位と Gazebo の縮尺、つまり速度と力の関係を式にし、車輪の回転の慣性を含めた、有効質量を計算できる。

3つ目。シミュレーションの時刻、つまり /clock と use_sim_time で動くノードを組める。

4つ目。PI 制御のノードを変えずにプラントを差し替え、同じゲインで追いつき方が変わる理由を、プラントの違いから説明できる。

完了の条件です。ros2 launch learn_bringup gazebo_plant.launch.py で一式が起動し、Gazebo の緑の車両が、実車の単位で、目標の毎秒10メートル、5メートル、0メートルに追いついて走ります。そして、フェーズ5-3 の自作のプラントと比べて、行き過ぎ、落ち着いたときのペダル、目標0 での止まり方が違う理由を、7節の表を使って説明できることです。

## 2. Gazebo の車両を力で動かすワールド

### 2-1. なぜ改造が要るか

フェーズ5-0 で使った緑の車両には、DiffDrive プラグインが付いています。DiffDrive は、速度の指令を受け取ると、車輪の回転の速さを、毎ステップ直接決めます。外から車輪に力をかけても、次のステップで DiffDrive が速さを上書きするので、力の効き目が出ません。車両を力で動かすには、DiffDrive を外して、次の2つのプラグインに付け替えます。

表は3列で、2行あります。列は、プラグイン、役割、トピックです。

ApplyJointForce は、関節、ここでは車輪の軸に、トルクをかけます。車輪1つに1つ付けます。トピックは、model の vehicle_green の joint の、関節名の cmd_force で、型は gz.msgs.Double です。最後に受け取った値を、かけ続けます。

OdometryPublisher は、車両の位置の変化から、速度を計算して送ります。トピックは、model の vehicle_green の odometry で、型は gz.msgs.Odometry です。速度は、車両の向きを基準にした前後と左右の成分で、直近の10回分の平均です。

どちらも Gazebo Sim 8 に付属しているので、追加の導入は要りません。トピック名と振る舞いは、公式の API リファレンスと、gz-sim8 のソースで確かめた、とあります。

### 2-2. ワールドファイルを写して改造する

フェーズ5-0 で使ったワールドファイル、つまり Gazebo に付属の diff_drive.sdf を、learn_bringup の中へ写します。mkdir -p で、learn_bringup の中に worlds のフォルダを作り、cp で、Gazebo のインストール先の worlds にある diff_drive.sdf を、その worlds のフォルダに、vehicle_force.sdf という名前で写します。

ワールドファイルは、SDF、つまり Simulation Description Format という、Gazebo のためのデータの書き方で書かれた XML のファイルです。要素は入れ子になっていて、原文は、書き換えるときと、3-2節の計算のときに探す要素だけを挙げています。

world は、ワールド全体です。中に、地面や車両の model が並びます。

model は、1台の車両など、ひとまとまりの物体です。緑の車両は、name が vehicle_green の model です。中に、次の3種類の要素を持ちます。

1つ目の link は、形と質量を持つ部品です。緑の車両では、車体、左右の車輪、補助輪の4つです。質量と慣性モーメント、つまり回転のしにくさは、その中の inertial に、車輪の半径は、形の記述の中の radius に書かれています。どちらも3-2節で使います。

2つ目の joint は、部品どうしのつなぎ目、つまり関節です。車体と車輪をつなぐ left_wheel_joint と right_wheel_joint が、車輪の軸にあたります。

3つ目の plugin は、物体に機能を足す部品です。DiffDrive も、これで付いています。

写した vehicle_force.sdf を、エディタで、次の3か所だけ書き換えます。青の車両は、残しておいてかまいません。指令を送らなければ、止まったままです。

1か所目は、ファイルの先頭のコメントです。デモの使い方が書かれているコメントを、出典と変更点を書いたコメントに置き換えます。原文が載せている新しいコメントは5行ほどで、フェーズ5-4 用のワールドで緑の車両を車輪のトルクで動かすこと、出典が Gazebo Sim 8 に付属する worlds の diff_drive.sdf で Apache License 2.0 であること、そして変更点として、ワールド名を vehicle_force にし、緑の車両の DiffDrive プラグインを、左右の車輪の ApplyJointForce と、OdometryPublisher に差し替えたこと、が書いてあります。

2か所目は、ワールドの名前です。world の行の name を、diff_drive から vehicle_force に変えます。ワールドの名前は、Gazebo のトピック名の一部、つまり world の vehicle_force の下になるので、フェーズ5-0 のデモと区別できるようにします。

3か所目は、緑の車両のプラグインです。ファイルの後半の、name が vehicle_green の model の中の、最後にある、gz-sim-diff-drive-system のプラグインの始まりから終わりまでを、3つのプラグインに置き換えます。青の車両の中にも同じ DiffDrive がありますが、そちらは変えません。

置き換える3つのプラグインの記述は、15行ほどです。要の行は、1つ目と2つ目の、filename が gz-sim-apply-joint-force-system、name が gz の sim の systems の ApplyJointForce のプラグインで、joint_name に、それぞれ left_wheel_joint と right_wheel_joint を書く行です。3つ目は、filename が gz-sim-odometry-publisher-system、name が OdometryPublisher のプラグインで、odom_publish_frequency に50 を書きます。

書き換えたら、gz sdf に -k を付けて、vehicle_force.sdf の書き方に誤りがないかを確かめます。

期待する結果は、Valid、つまり正しい、という1語です。これが出れば、SDF として正しく読めます。タグの閉じ忘れなどがあると、どこが誤りかを示すエラーが出ます。

ワールドファイルの出典についての囲みがあります。diff_drive.sdf は、Gazebo Sim、つまり Open Source Robotics Foundation に付属するファイルで、Apache License 2.0 で配布されています。Apache License 2.0 では、改変したファイルを使ったり配ったりしてかまいませんが、改変したことを分かるようにしておく必要があります。1か所目のコメントで出典と変更点を残しているのは、そのためです。この教材のリポジトリには、このファイルそのものは含めておらず、読者が各自で写して改造する、とあります。

## 3. 縮尺と有効質量

### 3-1. 速度と力の縮尺

pi_controller は、フェーズ5-2 で、実車の単位、たとえば毎秒10メートルで、ゲインを決めました。Gazebo の車両の速度とは、フェーズ5-1 の gz_display と同じく、40分の1の縮尺で対応させます。DiffDrive を外したので、フェーズ5-1 で縮尺を決めた理由、つまり最高の速度の毎秒0.5メートルの上限は、もうありません。それでも縮尺をそろえておくと、フェーズ5-1 から5-3 で表示器として見た車両と同じ速さで、画面の車両が走り、見比べやすくなります。一方、Gazebo の車両の質量は約6キログラムで、実車の1500キログラムとは比率が違うので、力の縮尺は、速度とは別に決めます。

縮尺は3つです。

速度は、Gazebo の速度が、実車の速度かける s です。s は0.025 です。gz_plant は、Gazebo のオドメトリの速度を s で割って、実車の単位に戻してから、/plant/velocity へ送ります。

加速度は、時間の縮尺がそのまま、つまり1秒は1秒なので、同じ比率の s になります。実車で毎秒毎秒2メートルの加速は、Gazebo では毎秒毎秒0.05メートルです。

力は、加速度が、力を質量で割ったものなので、Gazebo で同じ比率の加速度を出す力は、次の式になります。Gazebo の力、F の gz は、実車の力、F の real に、m の gz かける s を、m の real で割ったものを掛けたもの、です。m の real は、フェーズ5-1 の車両の質量、1500キログラム、m の gz は、Gazebo の車両の有効質量で、3-2節で求めます。右辺の分数、つまり、m の gz かける s 割る m の real を、力の縮尺と呼び、パラメータの force_scale にします。

### 3-2. 有効質量、つまり車輪の回転も質量として効く

Gazebo の緑の車両の各部の質量は、ワールドファイルに書かれています。車体が1.14キログラム、左右の車輪が2キログラムずつ、補助輪が1キログラムで、合計6.14キログラムです。ところが、車輪を回して車両を加速させるときは、車両を前へ動かすだけでなく、車輪と補助輪を回転させるためにも、力が要ります。回転の慣性、つまり慣性モーメント I を持つ、半径 r の輪が転がるとき、その分は、質量が、I 割る r の2乗だけ増えたのと同じ効き方をします。

慣性モーメントは、回転の速さの変えにくさで、まっすぐな運動の質量にあたります。トルクは、慣性モーメントかける角加速度です。車両が加速度 a で進むと、滑らずに転がる輪は、角加速度 a 割る r で回転を速めます。そのために要るトルクは、I かける a 割る r で、これを輪の縁で出す力に直すと、さらに半径 r で割って、I 割る r の2乗、かける a になります。つまり、質量が I 割る r の2乗の物体を加速させるのと同じだけの力が、余分に要ります。

表は5列で、4行あります。列は、部品、質量、回転の軸のまわりの慣性モーメント I、半径 r、そして I 割る r の2乗です。

車体は、質量が1.14キログラムで、ほかの欄はありません。

左の車輪は、質量が2キログラム、慣性モーメントが0.125キログラム平方メートル、半径が0.3メートルで、I 割る r の2乗は1.39キログラムです。

右の車輪も、左と同じで、1.39キログラムです。

補助輪は、質量が1キログラム、慣性モーメントが0.1、半径が0.2メートルで、I 割る r の2乗は2.5キログラムです。

これらを合わせて、有効質量の m の gz は、6.14 に、1.39 の2倍と、2.5 を足して、約11.4キログラムになります。

慣性モーメントと半径も、ワールドファイルの値です。2-2節のとおり、それぞれの部品の link の中の inertial と radius に書かれています。筆者が実験で確かめたところ、左右の車輪に0.05ニュートンメートルずつのトルクをかけると、加速度は毎秒毎秒0.0292メートルでした。このトルクは、車両を押す力にすると、2 かける0.05 割る0.3 で、約0.333ニュートンです。0.333 割る0.0292 で約11.4キログラムとなり、計算と合います。

これで、力の縮尺は、11.4 かける0.025 割る1500 で、約1.9 かける10 のマイナス4乗になります。実車のアクセル全開の3000ニュートンは、Gazebo では約0.57ニュートン、車輪1つあたりのトルクにすると、0.57 かける0.3 割る2 で、約0.0855ニュートンメートルです。

課題1。補助輪の慣性モーメントを使わずに、つまり車体と車輪の質量の合計6.14キログラムだけで力の縮尺を決めると、Gazebo の車両の加速は、実車の縮尺に比べて、速くなるか遅くなるか、何倍か、を考えます。有効質量の比、11.4 割る6.14、約1.86倍の違いが出る、とあります。

## 4. ペダルを車輪のトルクに変えるノード

### 4-1. 仕様

learn_py にファイルを2つ、learn_bringup にファイルを3つ足します。learn_bringup の分は、2節と6節で作ります。表は2列で、5行あります。

learn_py の actuator_model.py は、アクセルとブレーキの遅れだけを計算するクラス ActuatorModel と、パラメータをまとめる ActuatorParams です。ROS2 を使いません。

on_odom です。Gazebo のオドメトリ、つまりブリッジが nav_msgs の Odometry に変換したものの、前後の速さ、つまり Gazebo の単位の twist の twist の linear の x を、s で割って実車の単位に戻し、/plant/velocity へ送ります。オドメトリは50ヘルツで届くので、/plant/velocity も50ヘルツになります。フェーズ5-1 の vehicle_plant は100ヘルツでした。

ブレーキの向きです。ブレーキは、動いている向きと逆に働く力です。フェーズ5-1 では、後ろへは進まない、として速度を0 で止めましたが、ここでは Gazebo が速度を計算するので、その手は使えません。そこで、制動力に、速度を brake_speed_band で割って、マイナス1 から1 に収めたものを掛けて、向きを決めます。速く動いているときは、全部の制動力が逆向きにかかり、止まる直前、つまり毎秒0.1メートル未満では弱まって、止まったときは0 になります。止まった車両を、ブレーキが後ろへ押し出さないようにするための工夫です。

ログは、フェーズ5-1 の vehicle_plant と同じ形に、送ったトルクを足しました。

## 5. シミュレーションの時刻

Gazebo の中の時間、つまりシミュレーションの時刻は、PC の負荷によって、現実の時間より遅く進むことがあります。フェーズ5-0 の2-1節の RTF の話です。この手順書では、Gazebo の物理と、gz_plant と pi_controller の計算が、同じ時計で進んでほしいのです。そうでないと、たとえば Gazebo が遅れている間も、pi_controller は現実の時間で積分を進めてしまい、制御がずれます。

そのため、次の2つを行います。仕組みは、Tips集の1節で説明した、とあります。

1つ目。ブリッジで、Gazebo の /clock を、ROS2 の /clock、つまり rosgraph_msgs の msg の Clock の型へ中継します。

2つ目。gz_plant と pi_controller に、パラメータの use_sim_time を true にして渡します。すると、ノードの時計、たとえばタイマーの周期が、/clock に従うようになります。コードは変えなくてかまいません。

target_generator には、use_sim_time を渡しません。フェーズ5-3 の2-2節のとおり、target_generator は、単調に増える時計、つまり PC の経過時間で目標を切り替えるので、切り替えの時刻は現実の時間で決まります。目標は、人が決めて送るもの、と考え、ここではそのままにした、とあります。シミュレーションの時刻で切り替えたい場合は、この節の最後の課題3です。

課題3。target_generator を、シミュレーションの時刻で目標を切り替えるように改造します。steady_clock の代わりにノードの時計、つまり get_clock を使い、launch で use_sim_time を true にして渡します。ただし、フェーズ5-1 の5-2節のとおり、ノードの時計は、PC の時刻合わせの影響を受けうる、とあります。シミュレーションの時刻を使う場合は、受けません。

目標5 での最低の速度は、フェーズ5-3 では5.00 で、下回りません。フェーズ5-4 では4.52 で、約10パーセント下回ります。

目標0 の後は、フェーズ5-3 では、毎秒0.25メートルほどまで浮き、約20秒かけて止まります。フェーズ5-4 では、約1秒で止まり、動きません。

理由は、プラントの車体の性質の違いにあります。主なものは、Gazebo の車両が、転がっても、ほとんど抵抗を生まないことです。3-2節の実験では、一定のトルクで、加速度がほぼ一定のまま、速くなっても加速が鈍りませんでした。自作のプラントには、転がり抵抗の約220ニュートンと、速度に比例する抵抗、毎秒10メートルで1400ニュートンがありました。理由は3つに分けて説明されています。

1つ目。抵抗が無いと、一定の速さを保つのに力が要らないので、落ち着いたペダルも積分の項も、0 に近づきます。目標0 の後に残る積分の項も無いので、フェーズ5-3 の5節のように浮かずに止まります。

2つ目。抵抗が自然なブレーキの役をしなくなるので、ペダルを戻しても勢いのまま進み、行き過ぎや下回りが出ます。オドメトリの速度が、直近の10回分、つまり0.2秒分の平均で、少し遅れて届くこと、つまり2-1節の表の話も、行き過ぎやすくします。

3つ目。フェーズ5-2 の既定のゲインは、プラントを一次遅れ、つまりフェーズ5-1 の2-3節の、速度の時定数 T、m 割る c で近づく形に近づけて、目安を立てたものです。抵抗が無いと c が0 に近づき、T が際限なく長くなるので、目安の前提が崩れ、同じゲインが最適ではなくなります。

それぞれの理由を詳しく追う説明は、フェーズ5 の後の任意の間章、古典制御の間章の4-2節で扱います。

モデルと物理の違いは、フィジカル AI の中心的な課題だ、とあります。自作の式で調整した制御が、より現実に近いシミュレーション、ここでは Gazebo では、少し違う振る舞いをします。同じことが、シミュレーションで調整したものを実物に移すときにも起きます。これが、シミュレーションと現実の差です。対処の方向は2つあります。

1つ目は、モデルを現実、ここでは Gazebo に近づけることです。たとえば、自作のプラントの抵抗の係数を、Gazebo で測った値に合わせます。この節の最後の課題4です。

2つ目は、どちらのプラントでもそこそこ動くゲインを探すか、プラントに合わせてゲインを調整し直すことです。調整し直す方向の例として、任意のフェーズ7-2 では、自作の式のプラントのブレーキを遅くしたもの、つまりフェーズ5-2 の6-5節の tau_brake が1.0 のもので、強化学習にゲインを調整させます。Gazebo の物理に合わせたゲインの調整は、フェーズ7 でもしていません。この節の最後の課題5で、手で試せます。

フェーズ7-3 から7-5 では、もう1つの方向として、自作の式を使わず、このページの Gazebo の物理、つまり車輪の関節に抵抗を足したものの上で、直接、NN の制御を学習させます。

課題が2つあります。

課題4。フェーズ5-2 の4節の closed_loop_sim.py で、rolling_coeff を0.0、drag_coeff を0.001 にした VehicleParams、つまり抵抗をほぼ0 にしたプラントを使って、同じ比べ方をします。7節の表の Gazebo の列に近い振る舞い、つまり行き過ぎて、ペダルが0 に近づくかを確かめます。筆者の計算では、最高の速度が10.29、目標5 での最低の速度が4.61 と、Gazebo の10.31 と4.52 に近い値になりました。抵抗が無いことが、違いの主な理由だと分かります。速度に比例する抵抗の係数を0 にすると、フェーズ5-1 の2-3節の時定数の式で0 で割ることになるので、ごく小さな値にしておきます。

課題5。gazebo_plant.yaml の pi_controller のゲインを変えて、Gazebo の物理のプラントで、目標10 への行き過ぎと、目標5 での下回りを小さくする組み合わせを探します。見つかったゲインを、フェーズ5-3 の vehicle_sim.yaml に入れると、自作のプラントではどうなるかも試します。

## 8. このフェーズのまとめ

まとめは5つです。

1つ目。DiffDrive は車輪の速さを直接決めるので、車両を力で動かすには、ApplyJointForce、つまり車輪のトルクと、OdometryPublisher、つまり速度に付け替えます。既にあるワールドを写して改造するときは、出典と変更点を残します。

2つ目。実車の単位と Gazebo の縮尺は、速度と加速度が s 倍、力が、m の gz かける s 割る m の real 倍です。m の gz は、車輪や補助輪の回転の慣性、つまり I 割る r の2乗を含めた有効質量で、部品の質量の合計より大きくなります。

3つ目。Gazebo の物理をプラントにするときは、/clock を中継し、計算するノードに use_sim_time を true にして渡して、同じ時計で動かします。

4つ目。pi_controller は変えずに、プラントを、自作の式から Gazebo の物理に差し替えられました。トピックの名前、型、単位を合わせておけば、部品を入れ替えられます。

5つ目。同じゲインでも、プラントの性質、つまり抵抗の有無や、速度の計り方の遅れが違えば、追いつき方は変わります。モデルと物理、つまりシミュレーションと現実の差をどう埋めるかは、フィジカル AI の中心的な課題です。

## 9. フェーズ5 のまとめ

フェーズ5-0 から5-4 で、次のものを作り、つなぎました。表は3列で、5行あります。列は、ページ、作ったもの、役割です。

5-0 では gz_drive を作りました。Gazebo の車両を、ROS2 から動かす入り口です。

5-1 では、VehicleModel、vehicle_plant、gz_display を作りました。車両の数理モデルと、その速度を Gazebo で見せる表示器です。

5-2 では、PIController、closed_loop_sim.py、pi_controller を作りました。PI 制御の式と、ROS2 なしの閉ループの計算と、それをつないだノードです。

5-3 では、target_generator、vehicle_sim.launch.py、vehicle_sim.yaml を作りました。目標の自動化と、一式の起動と、設定の切り替えです。

学習計画のフェーズ5 の完了の条件のうち、階段の形の目標の速度に追いつく、はフェーズ5-3 の4-1節のログで、アクセルとブレーキの非対称性の影響をグラフで説明する、は同じく4-3節のグラフの読み方で、同じゲインで自作のプラントと Gazebo の物理の追いつき方の違いを説明する、はこの手順書の7節で確かめました。

ページをまたいで通っている考え方は、次の3つです。

1つ目は、式を ROS2 から分けることです。車両のモデル、つまりフェーズ5-1、PI 制御、つまりフェーズ5-2、アクチュエータ、つまりフェーズ5-4 は、どれも ROS2 を使わないクラスにして、ノードはそれを包むだけにしました。式は ROS2 なしで確かめられ、閉ループの計算、closed_loop_sim.py にも、そのまま使えます。

2つ目は、トピックの名前、型、単位で部品をつなぐことです。マイナス1 から1 の /plant/pedal と、実車の毎秒メートルの /plant/velocity をそろえたので、プラントを vehicle_plant から、gz_plant と Gazebo に差し替えても、pi_controller は変えずに済みました。

3つ目は、Gazebo の車両の使い方を、段階的に変えることです。フェーズ5-0 でデモの車両を速度で動かし、フェーズ5-1 から5-3 では計算の結果を見せる表示器にし、フェーズ5-4 では力で動かす形に改造して、プラントそのものにしました。
