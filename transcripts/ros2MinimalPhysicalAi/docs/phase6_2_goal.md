# フェーズ6-2: 条件で記録を終わらせる、ゴールの見張り（聞くための原稿）

想定する環境は、WSL2 と Ubuntu 24.04 と ROS2 Jazzy です。前提はフェーズ6-1 で、record.launch.py と記録用の YAML があり、target_generator に end_time を足してあることです。所要時間の目安は1コマで、言語は Python です。launch も Python の形式です。

この手順書の位置づけの囲みです。このページは、任意の寄り道です。フェーズ6-3 以降、フェーズ7 の最終ゴールまでは、このページを読んでいなくても進められます。フェーズ6-3 とフェーズ7 で使う記録は、どれもフェーズ6-1 の、決めた時間で終わる形です。このページでは、もう1つの終わり方、つまり条件を満たしたら終わる形と、走った距離の2つの求め方を、見張りのノードを書いて試します。

進め方の囲みです。2節で、走った距離を求める2つの方法を比べます。3節で見張りのノードを書き、4節で、フェーズ6-1 の記録用の launch を取り込んだ launch を作ります。5節でフェーズ5-3 の一式を案A で、6節でフェーズ5-4 の一式を案B で記録します。7節で、2つの方法の違いが小さかった理由と、それでも案B を選ぶ理由を考えます。サンプルは、学習の手がかりとして最小限に書いたもので、公式チュートリアルの転載ではありません。コードは、手順書を作るときに、使い捨ての環境でビルドし、記録を実行して確かめました。Gazebo は画面なしで起動したので、画面の見え方は確かめていません。出力が違う場合は、実際の表示を優先します。

## 0. 学習目標と完了の条件

学習目標は3つです。

1つ目。ゴールに着いたことを判定する見張りのノードを書き、条件をきっかけに、記録、つまり launch 全体を終わらせられる。

2つ目。走った距離を、速度を時間で積み上げて求める方法、つまり案A と、位置から求める方法、つまり案B の違いと、それぞれの誤差の出どころを説明できる。

3つ目。時間切れ、つまりフェーズ6-1 の end_time と、ゴールの、早いほうで終わる形を組める。

完了の条件です。フェーズ5-3 の一式を案A で、フェーズ5-4 の一式を案B で記録し、どちらも、走った距離が450メートルに達したところで記録が止まること。フェーズ5-4 の記録で、案A と案B の距離がほぼ一致した理由と、それでも強化学習では案B を本命にする理由を説明できることです。

## 1. 全体像

フェーズ6-1 では、記録を100秒で終わらせました。時間でそろえると、ゲインや時定数といった条件が違っても、同じ長さの記録が取れます。ただし、車両が走った距離は、条件ごとに違ってしまいます。追従の遅いゲインの車両は、100秒たっても、速いゲインの車両ほど遠くへは進んでいません。

決めた地点まで、どれだけ上手に走れたかを比べたいときは、時間ではなく、ゴールの地点に着いたことをきっかけに終わらせるほうが自然です。これは、強化学習のエピソードの終わり方の、1つの形でもあります。ただし、最終ゴールに向かうフェーズ7 の強化学習では、ゴールではなく、決めた時間で終わらせました。7節の末尾で触れます。強化学習では、1回の試行をエピソードと呼び、エピソードは、ゴールに着いた、時間切れになった、ぶつかったなどで失敗した、のどれかが起きたところで終わります。この手順書では、ゴールと時間切れの2つを組み合わせます。

ゴールは、見張りのノード goal_monitor の役目です。走った距離を見張り、ゴールの距離、450メートルに達したら、自分で終わります。フェーズ6-1 の target_generator と同じく、launch の on_exit=Shutdown() で、全体が止まります。

時間切れは、フェーズ6-1 で target_generator に持たせた end_time、つまり100秒と105秒が、そのまま残ります。ゴールに着く前に100秒たてば、フェーズ6-1 と同じく、時間で終わります。

どちらのノードにも on_exit=Shutdown() が付いているので、早く起きたほうで、全体が止まります。

ここに図が1枚あります。SVG と mermaid の版がありますが、内容は同じです。全体を、青みがかった灰色の破線の大きな枠が囲み、見出しは record_goal.launch.py です。その中の左に、薄い緑の破線の縦長の枠があり、見出しは、6-1 の record.launch.py、include、つまり取り込み、です。

緑の枠の中には、薄い青の箱が上下に2つあります。上の箱は、5-3 または5-4 の一式、target_generator は end_time で終わる、時間切れ、と書いてあります。下の箱は、ros2 bag record です。上の箱から下の箱へ、実線の矢印が下りています。

大きな枠の中の右上、緑の枠の外に、薄いオレンジ色の箱が1つあり、goal_monitor、走った距離が goal_distance に達したら終わる、ゴール、と書いてあります。

上の一式の箱から、右の goal_monitor の箱へ、実線の矢印が2本、平行に伸びています。上の矢印のラベルは、/plant/velocity、案A、速度かける時間を積み上げる、です。下の矢印のラベルは、/model/vehicle_green/odometry、案B、5-4 だけ、位置から求める、です。

goal_monitor の箱の下からは、破線の矢印が下りてから左へ折れ、緑の枠の中の ros2 bag record の箱に入ります。ラベルは2行で、終わると Shutdown で全体が止まる、target_generator が先なら、そちらで止まる、です。

まとめると、フェーズ6-1 の記録用の launch を取り込み、その外に goal_monitor を足す。goal_monitor は、速度か位置から走った距離を求め、ゴールに達すると終わって、記録を含めた全体を止める。target_generator の end_time は、時間切れの役を担う、という流れです。

## 2. 走った距離の求め方

距離を求める方法は2つあります。

### 2-1. 案A: 速度を時間で積み上げる

/plant/velocity が届くたびに、前に届いてから今回までの時間、デルタ t と、今回の速度 v を掛けたものを、足していきます。

式は、d に、v かける デルタ t を足したものを、新しい d にする、というものです。d は走った距離です。原文では、左向きの矢印の記号で書いていて、これは、右辺を計算して、左辺の d に入れ直す、という意味です。フェーズ5-1 の2-4節の、x の k プラス1 が、x の k に何かを足したもの、という式と同じことを、1つの変数を上書きしていく形で書いたものです。

フェーズ5-1 の2-4節のオイラー法で、速度から位置を計算するのと同じ考え方です。フェーズ5-3 の自作のプラントは位置を持たないので、フェーズ5-3 では案A しか使えません。一方、この方法の誤差について、次の3つのことがあります。

1つ目は、時間の測り方です。デルタ t は、見張りのノードにメッセージが届いた時刻の差で測ります。届くまでの遅れのばらつきが、そのままデルタ t に入ります。記録を再生して聞かせると、再生の速さでもデルタ t が変わります。この手順書の7節の末尾の課題2 です。PC の時計が飛ぶ環境では、フェーズ6-1 の2-2節の注記のとおり、その分も入ります。そのため、このノードでは、デルタ t を単調増加する時計で測り、フェーズ5-4 ではシミュレーション時刻で測ります。3-2節の解説で扱います。

2つ目は、取りこぼしです。途中のメッセージが届かなければ、その間のデルタ t は、次のメッセージの速度で埋められます。

3つ目は、積み重なり方です。いつも同じ向きにずれる誤差、たとえば時計の取り違え、再生の速さ、速度の推定の偏りは、足し込むたびに積み重なり、あとから打ち消されることはありません。一方、届くまでの遅れのばらつきは、今回のデルタ t が長くなった分だけ、次のデルタ t が短くなるので、速度がほぼ一定の間は、大部分が打ち消し合います。取りこぼしも、その間に速度がほとんど変わらなければ、誤差はわずかですが、加速や減速の途中で起きると、その分の誤差が残ります。

### 2-2. 案B: 位置から求める

フェーズ5-4 の Gazebo の車両は、オドメトリ、つまり /model/vehicle_green/odometry で位置を送っています。走り始めた地点の位置を覚えておき、今の位置との距離を求めれば、積み上げなくても、走った距離が分かります。

フェーズ5-4 のオドメトリは、Gazebo の物理エンジンが計算している車両の位置そのもの、つまりシミュレーションの中の真の値を送っています。フェーズ5-4 の2-1節の OdometryPublisher の話です。そのため、案A のような、時間の測り方や取りこぼしの誤差が乗らず、何度試しても、同じ基準で判定できます。

実物のロボットのオドメトリは推定値だ、という注記があります。実物のロボットのオドメトリは、車輪の回転を積み上げて求めた推定値で、車輪が滑ると、実際の位置とずれていきます。フェーズ5-0 の3-4節の注記の話です。つまり、実物では、オドメトリも、案A と同じ種類の誤差を持ちます。実物で位置の真の値に近いものを得るには、GPS やカメラなど、車輪とは別の手段で位置を測ります。案B の、誤差が乗らない、という点は、シミュレーションだからこそ使える利点です。

## 3. 見張りのノード、goal_monitor_node.py

### 3-1. 仕様

仕様は5つです。

1つ目。ノードの名前と実行ファイルの名前は、goal_monitor で、パッケージは learn_py です。

2つ目。受けるのは、/plant/velocity と、use_odometry が true のときだけ、/model/vehicle_green/odometry です。/plant/velocity の型は std_msgs の msg の Float64 で、実車の単位の、毎秒何メートルで、案A に使います。オドメトリの型は nav_msgs の msg の Odometry で、Gazebo の単位で、案B に使います。

3つ目は、パラメータです。goal_distance は、ゴールまでの距離で、実車の単位のメートル、既定は450.0 です。use_odometry は、true なら案B で判定するもので、既定は false です。scale は、Gazebo の長さを実車の長さで割ったもので、既定は0.025 です。フェーズ5-4 の3-1節の、速度の縮尺と同じ値です。どれも、起動のときにだけ読みます。

4つ目。判定に使う距離が goal_distance に達したら、ログを1行出して終わります。

5つ目はログです。5秒に1回、案A と案B の距離を出します。案B を使わないときは、ハイフンを出します。

### 3-2. サンプルコードと解説

ファイルは、ros2_ws の src の learn_py の learn_py の goal_monitor_node.py です。

90行ほどのコードで、ブロックは7つです。import、Node を継承した GoalMonitor のクラスの __init__、on_velocity、on_odom、summary、check、そして main です。クラスの前のコメントには、車両が走った距離を見張り、ゴールの距離に達したら ROS2 を終わらせるノードで、案A は速度を時間で積み上げた距離、案B は Gazebo のオドメトリの位置から求めた距離、とあります。summary は、2つの距離を、distance A、velocity と、B、odometry の値を並べた1行の文字列にする関数です。

要の行は2か所です。1つ目は、__init__ の中で、goal_distance か scale が0 以下なら、ValueError で止める行です。2つ目は、on_velocity の最後で、use_odometry が false のときだけ、案A の距離で check を呼ぶ行です。案B を使うときは、判定は on_odom の側だけで行います。

goal_monitor_node.py の解説は、4つです。

1つ目は、時計の選び方で、__init__ の中です。案A のデルタ t を測る時計を、use_sim_time の値で選びます。use_sim_time が true のとき、これはフェーズ5-4 の一式ですが、ノードの時計の self.get_clock() を使います。ノードの時計は、フェーズ5-4 の5節のとおりシミュレーション時刻に従うので、Gazebo の物理と同じ時計で積み上げられます。そうでないとき、これはフェーズ5-3 の一式ですが、単調増加する時計を使います。ノードの時計は PC の現在時刻で、時計が飛ぶと、その分だけ距離が多く足されてしまいます。毎秒10メートルで走っているときに数秒飛べば、数十メートルで、たとえば3秒なら30メートルです。use_sim_time は、自分で宣言しなくても、すべてのノードが持っているパラメータなので、get_parameter でそのまま読めます。Tips集の1節の話です。

2つ目は、案A の on_velocity です。最初の1回は、時刻を覚えるだけにします。前回が無いので、デルタ t を求められないためです。2回目からは、2-1節の式のとおり、msg.data かける dt を足します。ログは、throttle_duration_sec を5.0 にして、5秒に1回に間引きます。フェーズ5-1 の vehicle_plant のログと同じ仕組みです。間引く間隔は、use_sim_time に関係なく、PC の現在時刻で数えます。rclpy のソースで、間引きに使う時計の既定が、PC の現在時刻の Clock になっているためです。

3つ目は、案B の on_odom です。最初に届いた位置を、走り始めた地点として start_position に覚え、今の位置との距離を求めて、scale で割って、実車の単位に直します。距離は、x の差の2乗と y の差の2乗を足したものの平方根で、math.hypot で求めます。走り始めた地点を覚えるのは、OdometryPublisher の位置が、ワールドの原点を基準にした位置だからです。フェーズ5-0 の5-5節で見た DiffDrive のオドメトリは、走り始めた地点が原点でした。同じ車両でも、プラグインによって、位置の基準が違います。緑の車両は、フェーズ5-0 の2節の表のとおり、y がマイナス2メートルの所から走り始めます。そのため、今の位置の原点からの距離をそのまま使うと、止まっているのに、2 を0.025 で割った80メートル、走ったことになってしまいます。これは、手順書を作るときに、最初に書いたコードで実際に起きた、とあります。

4つ目は check です。判定に使う距離がゴールに達したら、ログを出して、rclpy.shutdown を呼びます。フェーズ6-1 の target_generator と同じく、main の spin が戻ってきて、プロセスが終わります。self.done で、1回だけに限っています。rclpy.shutdown を呼んだ後も、すでに届いていたメッセージのコールバックが呼ばれることがあり、2回目の rclpy.shutdown はエラーになるためです。

### 3-3. 実行ファイルとして登録し、ビルドする

ros2_ws の src の learn_py の setup.py の entry_points に、1行足します。既存の行は残し、フェーズ5-4 の6-3節で足した gz_plant の行の後に続けます。足すのは、goal_monitor を、learn_py の goal_monitor_node の main に結びつける行です。

ビルドは、4節の launch と YAML を足してから、まとめて行います。4-3節です。

## 4. launch と YAML

### 4-1. ゴール用の YAML

フェーズ6-1 の記録用の YAML を写して、goal_monitor の部分を足します。

cd で、ホームの ros2_ws の src の learn_bringup の config に移り、cp で、vehicle_sim_record.yaml を vehicle_sim_goal.yaml に、gazebo_plant_record.yaml を gazebo_plant_goal.yaml に写します。

写したファイルの最後に、それぞれ goal_monitor の部分を足します。

vehicle_sim_goal.yaml、つまりフェーズ5-3 の一式で案A のほうには、goal_monitor の ros__parameters に、goal_distance の450.0 だけを書きます。

gazebo_plant_goal.yaml、つまりフェーズ5-4 の一式で案B のほうには、goal_distance の450.0 に加えて、use_odometry を true、scale を0.025、use_sim_time を true と書きます。

説明は4つです。

## 7. 案A と案B の差が小さかった理由

6節では、案A と案B の距離の差が、ここに挙げた行では、ログの表示で最大0.1メートルしかなく、表示に現れるほど広がることもありませんでした。450メートルに対して約0.02パーセント、実際の違いの上限の0.2メートル未満でも、約0.04パーセントです。2-1節で挙げた誤差の出どころが、この組み合わせでは小さかったためで、理由は3つです。

1つ目は、時間の測り方です。フェーズ5-4 の一式では、goal_monitor が、シミュレーション時刻でデルタ t を測っています。PC の時計の飛びも、Gazebo が現実より遅れること、つまり RTF も、デルタ t に入りません。

2つ目は、速度の出どころです。フェーズ5-4 の /plant/velocity は、同じオドメトリの速度を、実車の単位に直したものです。フェーズ5-4 の4-3節の on_odom の話です。その速度は、OdometryPublisher が、位置の変化から計算したもので、直近の10回分の平均です。フェーズ5-4 の2-1節の表のとおりです。そのため、積み上げると、位置の変化にほぼ戻ります。

3つ目は、取りこぼしです。同じ PC の中の通信で、周期も1秒に50回と速くないので、取りこぼしは起きにくいです。

それでも、強化学習で、ゴールに着いたことをきっかけに試行を終わらせるなら、判定には案B を本命にします。理由は3つです。

1つ目。強化学習では、同じ条件の試行を何千回も繰り返し、試行ごとの結果を比べます。判定の基準が試行ごとに少しずつずれると、その分だけ、ゲインが良かったのか、判定がずれただけなのか、の区別がつきにくくなります。案B は、積み上げの誤差が、試行ごとにばらつくことがありません。

2つ目。案A の誤差は、条件によっては小さくありません。PC の負荷が高くて取りこぼしが増えたとき、届く間隔が実際の時間とずれたとき、これはこの節の末尾の課題2 の話です。また、時計の選び方を誤ったときや、速度の推定に偏りがあるとき、たとえば実物の車輪の滑りでも、足し込むたびに誤差が積み重なります。

3つ目。一方、案B は、2-2節の注記のとおり、シミュレーションだからこそ真の値を使えます。実物へ移すときは、真の値の代わりに、別の手段、たとえば GPS やカメラで測った位置を使うことになります。

なお、最終ゴールに向かうフェーズ7 の強化学習では、試行、つまりエピソードを、ゴールではなく、決めた時間、90秒で終わらせました。目標速度が10秒ごとに変わる90秒のシナリオを、最後まで走り切ることを、1回の試行にしたためです。フェーズ7-1 の2-6節の話で、フェーズ6-3 の8節の、エピソードの終わり方、も参照するように、とあります。そのため、フェーズ7 では、このページの goal_monitor は使いません。

課題1 です。vehicle_sim_goal.yaml の goal_distance を200.0 にすると、ゴールは、目標が毎秒10メートルの区間、つまり起動から約35秒で達し、記録はそこで終わります。記録してから ros2 bag info の Duration を確かめ、フェーズ6-1 の記録と比べて短いことを確かめます。

課題2 は、時間の測り方の誤差を見る課題です。5節で取った記録 sim_goal を、2倍の速さで再生し、goal_monitor だけに聞かせます。一式は起動しません。T1 で、ros2 run learn_py goal_monitor を実行します。T2 では、ホームの ros2_ws の bags に移り、ros2 bag play に、sim_goal と -r 2 を付けて実行します。

期待する結果、T1 の分の最後の3行です。時刻と距離の細部は、実行ごとに変わります。案A の距離が、194.9メートル、208.8メートル、234.3メートルと出て、案B はハイフンです。

最後の行の距離が、5節の450メートルの約半分で止まり、goal reached の行は出ません。再生が終わっても goal_monitor は終わらないので、T1 は Ctrl+C で止めます。記録の中の速度は、5節で450メートルに達したときと、まったく同じ値です。それでも、2倍の速さで届くと、デルタ t が半分に測られるので、案A の距離は、約半分にしかなりません。案A は、値が届いた間隔を時間とみなしているので、届き方が変わると、同じ走りでも距離が変わります。案B の位置は、届く間隔に関係なく、同じ値になります。フェーズ6-3 の3節で、記録から時間を数えるときにも、同じ問題を扱います。

課題3 です。gazebo_plant_goal.yaml の use_odometry を false にして、フェーズ5-4 の一式を案A で判定させます。6節と同じくらいの時刻にゴールに着くことを確かめます。B、odometry は、ハイフンになります。

## 8. 本フェーズのまとめ

4つあります。

1つ目。見張りのノードが条件を判定して自分で終わり、launch の on_exit=Shutdown() で全体を止めれば、条件をきっかけに記録を終わらせられます。時間切れのノードにも同じ指定を付けておくと、早く起きたほうで終わります。強化学習のエピソードの終わり方と、同じ形です。

2つ目。走った距離は、速度を時間で積み上げる案A か、位置から求める案B で求められます。案A は、位置を持たないプラントでも使えますが、時間の測り方、取りこぼし、速度の偏りの誤差が積み重なります。案B は、シミュレーションでは真の値を使えるので、判定の基準がぶれません。

3つ目。積み上げに使う時間は、シミュレーション時刻で動く一式なら、ノードの時計、つまり use_sim_time に従う時計で、そうでなければ、単調増加する時計で測ります。

4つ目。フェーズ5-4 のワールドの OdometryPublisher の位置は、ワールドの原点を基準にしています。フェーズ5-0 の DiffDrive のオドメトリとは、基準が違います。走った距離は、最初の位置との差で求めます。

## 9. つまずきやすい点

表は2列で、7行あります。列は、症状と、確認することです。

1行目。止まっているのに、案B の距離が0 ではない、たとえば80メートルの場合です。最初の位置を覚えて、差をとっているかを確かめます。3-2節の解説の on_odom の話です。OdometryPublisher の位置は、ワールドの原点を基準にしていて、フェーズ5-0 の DiffDrive のオドメトリとは違います。

2行目。案B の距離がハイフンのままの場合です。use_odometry を true と、YAML に書いたかを確かめます。フェーズ5-3 の一式にはオドメトリが無いので、案B は、フェーズ5-4 の一式でだけ使えます。

3行目。ゴールに着いても記録が止まらない場合です。record_goal.launch.py の goal_monitor に、on_exit=Shutdown() を付けたかを確かめます。

4行目。goal reached が出ないまま、時間切れ、つまり100秒か105秒で止まる場合です。goal_distance が大きすぎないか。案B なら、use_odometry の true と、scale の値を確かめます。4-1節の話です。目標の階段で、100秒までに走れる距離より遠いと、ゴールの前に、target_generator の end_time で終わります。

5行目。フェーズ5-4 の一式で、案A の距離が、案B よりはっきり大きい、または小さい場合です。gazebo_plant_goal.yaml の goal_monitor に、use_sim_time を true と書いたかを確かめます。書かないと、現実の時間で積み上げるので、RTF が100パーセントを下回る環境では、ずれます。

6行目。goal_monitor が、No executable found、つまり実行ファイルが見つからない、で起動しない場合です。setup.py の entry_points に足したかを確かめます。3-3節の話です。また、ビルドし直して、source install/setup.bash をしたかを確かめます。

7行目。記録の後も Gazebo が残る場合です。フェーズ6-1 の8節の表と同じで、pgrep -af の gz sim で確かめ、残っていれば止めます。

## 10. 次へ

フェーズ6-3、記録から指標を計算して比べる、で、フェーズ6-1 で取った、時間で終わる記録を再生しながら、行き過ぎ量や整定時間などの指標を計算する解析のノードを書き、条件ごとに比べます。この手順書の、ゴールで終わる記録を比べに使わない理由は、フェーズ6-3 の8節にあります。作成の状況は、学習計画の、手順書一覧で確かめられます。
