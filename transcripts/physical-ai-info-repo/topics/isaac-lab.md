## 環境の設計

環境、英語で task は、観測を返し、行動を受け取り、シミュレーションを進める部分です。Isaac Lab には、2つの書き方があります。マネージャー型、manager-based と、直接型、direct です。

原文では、この2つを表で比べています。比べている観点は、基底のクラス、書き方、向いている場面、実機への展開の道具、の4つです。

基底のクラスは、マネージャー型が ManagerBasedRLEnv で、設定は ManagerBasedRLEnvCfg です。直接型は DirectRLEnv で、複数のエージェントの場合は DirectMARLEnv です。

書き方は、マネージャー型では、観測、行動、報酬などを、役割ごとの「マネージャー」に、設定のクラスで項、英語で term として登録します。直接型では、観測、行動、報酬、リセットを、1つのクラスのメソッドとして書きます。

向いている場面は、マネージャー型では、部品の差し替えや比較、チームでの分担、同じ課題を別のロボットやセンサーで試す場合です。直接型では、部品に分けにくい複雑な処理や、PyTorch の JIT や Warp での高速化をしたい場合です。直接型は、IsaacGymEnvs から移る人にもなじみやすい、としています。

実機への展開の道具は、マネージャー型では、後で説明する IO 記述子と LEAPP の対象になります。直接型では、3.0 で、注記を足せば、RSL-RL で学習したものだけが LEAPP の対象になります。

次に、マネージャー型で使う主なマネージャーです。原文は、7つのマネージャーを、役割と設計の要点の2つの観点で表にしています。

1つ目は、行動、Action のマネージャーです。役割は、方策の出力を、関節の目標値などの指令に変えることです。設計の要点は、項ごとに、対象の関節と倍率、scale を決めることです。倍率は、1歩で動ける量を決めます。歯車の挿入の手引きでは、倍率を少し上げると、静止摩擦を越えて動けるようになりました。

2つ目は、観測、Observation のマネージャーです。役割は、方策に渡す値を計算することです。設計の要点は、項をグループにまとめることです。policy という名前のグループは、Isaac Lab の各種のラッパーが前提にするので、必須です。項ごとに、ノイズ、切り詰め、倍率を付けられ、グループごとに、ノイズを有効にするかを選びます。

3つ目は、イベント、Event のマネージャーです。役割は、決まった時点で処理をすることで、ドメインランダム化の中心になります。ドメインランダム化とは、物理や見た目の条件をばらつかせることです。時点は3つあります。起動の時の startup は、質量などの重い変更を1回だけ行います。リセットの時の reset は、初期の姿勢など、毎回変えるものに使います。そして、一定の歩数ごとの interval です。

4つ目は、報酬、Reward のマネージャーです。役割は、項ごとの関数と重みの和で、報酬を計算することです。設計の要点は、項ごとの寄与が記録されるので、どの項が学習を引っ張っているかを確かめられることです。

5つ目は、終了、Termination のマネージャーです。役割は、エピソードを終える条件を決めることです。設計の要点は、時間切れの項に time_out イコール True を付けて、失敗による終了と区別することです。これは、Gymnasium の打ち切り、truncation の扱いにあたります。

6つ目は、指令、Command のマネージャーです。役割は、歩く速さや手先の目標の姿勢などの目標を作り、更新することです。設計の要点は、指令を観測にも入れて、方策が目標に応じて動けるようにすることです。

7つ目は、カリキュラム、Curriculum のマネージャーです。役割は、学習の進み具合に応じて、難しさを上げることです。歩行の地形や、操作の課題で使われています。

表のほかに、要点が2つあります。

1つ目は、時間の刻みです。物理の計算の刻みである sim.dt と、何刻みごとに方策を1回動かすかを決める decimation で、制御の周期が決まります。例えば、5ミリ秒、つまり200ヘルツの刻みで、decimation を4にすると、方策は50ヘルツで動きます。実機の制御の周期と合わせることが、実機に移すときの前提になります。

2つ目は、自分の課題の作り方です。雛形を生成する機能を使って、Isaac Lab のリポジトリの外に、独立したプロジェクトとして作るのが推奨されています。生成のコマンドは、2.3 系では isaaclab.sh にハイフン2つの new、3.0 では uv run isaaclab にハイフン2つの new を付けます。生成のときに、書き方、つまりマネージャー型か直接型かと、強化学習のライブラリを選びます。

## アクチュエータのモデル

実機に移すときに最も効く設定の1つが、関節の駆動の模擬、つまりアクチュエータのモデルです。2種類あります。

1つ目は、暗黙のモデル、implicit です。PD 制御を物理エンジンに任せるもので、クラスは ImplicitActuator です。計算は安定しやすいです。

2つ目は、明示のモデル、explicit です。指令からトルクを自分で計算し、モーターの限界で切り詰めてから与えます。用意されているのは次のものです。理想的な PD の IdealPDActuator。速度に応じてトルクの上限が下がる DC モーターの DCMotor。指令の遅れを模擬する DelayedPDActuator。角度に応じた上限の RemotizedPDActuator。そして、実機のデータから学習したモデルの、ActuatorNetMLP と ActuatorNetLSTM です。

注意点が3つあります。暗黙のモデルで学習した方策は、同じロボットを明示のモデルにすると、うまく動かないことがあります。明示のモデルは数値的に不安定になりやすく、関節の armature を大きくすると落ち着くことがあります。そして、同じ駆動の関節はまとめて、1つのモデルを割り当てます。例えば、四脚の全関節が同じ駆動、という場合です。

## 強化学習

Isaac Lab は、強化学習のライブラリにつなぐラッパーを用意しています。原文には、2.3 系の文書の比較の表があります。表の列は、ライブラリ、主なアルゴリズム、計算の枠組み、複数の GPU、複数のエージェント、の5つで、4つのライブラリが並んでいます。

1つ目は RSL-RL です。主なアルゴリズムは、PPO と、教師と生徒の蒸留です。計算の枠組みは PyTorch。複数の GPU に対応し、複数のエージェントは PPO で扱えます。

2つ目は RL-Games です。主なアルゴリズムは、PPO、SAC、A2C です。計算の枠組みは PyTorch。複数の GPU に対応し、複数のエージェントは PPO で扱えます。

3つ目は skrl です。アルゴリズムは多数あります。計算の枠組みは PyTorch と JAX で、skrl 自体は Warp でも実装されています。複数の GPU に対応し、複数のエージェントは、PPO と、複数のエージェント向けのアルゴリズムで扱えます。

4つ目は Stable-Baselines3 です。アルゴリズムは多数あります。計算の枠組みは PyTorch です。複数の GPU には対応しておらず、並列の環境にも対応していません。複数のエージェントの欄は空欄です。

3.0 の文書の比較は、表の形が変わり、「何のために選ぶか」で整理しています。主な違いは3つです。RSL-RL が既定で入り、対称性を使ったデータの水増しや、探索を促す手法の RND なども挙げられています。複数のエージェントの学習、つまり MAPPO や IPPO は、skrl でだけ説明されています。そして、VLA、つまり Isaac GR00T や OpenVLA を、強化学習で追加学習するための RLinf と、PyTorch の部品で独自のアルゴリズムを組むための TorchRL が加わりました。

ここからは、強化学習の実務の要点が5つあります。

1つ目は速さです。開発元の文書によれば、人型の課題である Isaac-Humanoid-v0 を、RTX 4090 の1枚で、描画なし、4,096の並列の環境で、6,550万歩だけ学習させました。かかった時間は、RSL-RL、RL-Games、skrl がほぼ同じで約200秒、Stable-Baselines3 は約290秒でした。ですから、速さよりも、使いたいアルゴリズム、文書、既存の例の多さで選ぶことになります。

2つ目は、並列の環境の数です。多いほど1回の更新のデータが増えますが、ある所から先は伸びが鈍り、1歩の計算が遅くなる分が上回ります。上限を決めるのは、ふつう GPU のメモリです。カメラの画像の観測、柔らかい物体、細かい衝突の形状が、メモリを使います。環境の数が少ないときは、バッチの大きさや、1回の試行の長さを増やして補います。これは、学習の手引きによります。

3つ目は、観測が NaN、つまり数でない値になる場合です。原因はたいてい学習のアルゴリズムではなく、シミュレーションの不安定さにあります。例えば、大きすぎる行動や、不正なリセットです。関節、速度、力の上限、ゲイン、物理の刻み、ソルバーの反復の回数を見直します。これも同じ手引きによります。

4つ目は、複数の GPU と計算機での学習です。PyTorch の torchrun、つまり DistributedDataParallel を使い、GPU ごとに1つのプロセスを立てます。それぞれが自分の並列の環境と方策の写しを持ち、勾配の更新のときだけ通信します。Linux でだけ使え、対応するのは RL-Games、RSL-RL、skrl です。計算機をまたぐ場合は、通信の遅れで、1台より遅くなることもあります。

5つ目は、複数の方策を競わせる学習、Population Based Training です。複数の方策を並行して学習させ、成績の悪いものを良いものの写しに置き換えながら、ハイパーパラメータを変えていきます。対応は RL-Games だけで、開発元は、6つ以上の方策で使うことを勧めています。

## 模倣学習

人の操作の記録から方策を学ばせる流れは、5つの段階です。なお、3.0 の文書の目次では、模倣学習の機能は、「試験的な機能」、Experimental Features の欄に置かれています。

1つ目の段階は、記録です。キーボード、SpaceMouse、または CloudXR による XR の手の追跡で、シミュレーションの中のロボットを操作し、成功した操作を HDF5 の形式で記録します。目安は10回程度です。短く、まっすぐ、止まらずに動かすのがよい、としています。

2つ目の段階は、区切りの注記です。記録を、つかむ、運ぶ、置くといった、物体ごとの小さな作業に区切ります。手作業か、課題が用意した判定で自動で行います。区切りが少ないほど、つなぎ合わせが滑らかになります。

3つ目の段階は、生成です。Isaac Lab Mimic で、区切りを新しい物体の配置に合わせて変換してつなぎ、成功したものだけを残して、例えば1,000回分に増やします。

4つ目の段階は、学習です。robomimic の行動の模倣、BC-RNN で、方策を学習させます。

5つ目の段階は、評価です。最後のチェックポイントが最良とは限らないので、複数の時点のチェックポイントを試します。

照明、背景、質感といった、見た目の変化への強さが要る場合は、生成した動画を Cosmos Transfer で別の見た目に変えてから学習させる方法も用意されています。開発元の文書の例、つまり立方体を積む課題では、照明や背景を変えた評価で、成功率が大きく上がりました。一方で、条件を変えない評価では、増やさずに学習させたものより、少し下がりました。

## 実機への展開

開発元の歯車の挿入の手引きは、シミュレーションと実機の差を小さくするための、具体的な教訓をまとめています。教訓は6つです。

1つ目。観測には、実機で手に入る値だけを使い、カメラによる推定の値には、実際の誤差に合わせたノイズを加える。

2つ目。関節の摩擦、つまり静止摩擦を模擬する。模擬しないと、方策は、指令した位置にぴったり届く前提で動いてしまう。

3つ目。駆動のゲインと物体の位置をばらつかせる。ただし、ばらつかせすぎると学習が難しくなる。

4つ目。実機の制御は、インピーダンス制御など、シミュレーションとずれる設定の少ないものを選ぶ。

5つ目。本格的に学習させる前に、摩擦や接触のソルバーの設定を、実機と見比べて合わせる。

6つ目。うまく動かないときは、実機の最初の観測をシミュレーションで再現し、応答を比べる。

方策を実機の側に渡す道具は、次の3つです。

1つ目は、2.3 系の IO 記述子、IO descriptors です。マネージャー型の環境で学習させた方策について、行動と観測の項の並び、関節の名前、単位、時間の刻みを、YAML に書き出します。実機の側で、観測の作り方を手で写し直さずに済みます。

2つ目は、3.0 の LEAPP と Isaac ROS Deploy です。方策を、観測と行動の処理ごと、ONNX などに書き出し、ROS 2 の上で動かします。LEAPP には、次の制約があります。マネージャー型の環境では、RSL-RL、RL-Games、skrl、Stable-Baselines3 で学習させた方策に対応します。直接型の環境では、注記を足した RSL-RL の方策だけに対応します。また、テンソルの値によって分岐や繰り返しが変わる処理と、Warp の処理は書き出せません。外部のライブラリの呼び出しも、たどれないことがあります。そして、書き出すときは、学習のときと同じ物理の計算の部分と設定を使います。

3つ目は、計算の部分をまたいだ確かめです。3.0 の文書は、PhysX と Newton の間で方策を移して確かめること、つまり sim-to-sim を勧めています。2.3 系の文書によれば、Newton で学習させた歩行の方策を、実機の Unitree G1 で動かしました。

## OSS: skrl

部品に分けた作りと、アルゴリズムの実装の読みやすさを重視した、強化学習のライブラリです。PyTorch、JAX、NVIDIA Warp で実装されています。Isaac Lab、MuJoCo Playground、Gymnasium、PettingZoo などの環境を読み込めます。複数のエージェントを1回の学習で同時に学ばせる仕組みを持ちます。Isaac Lab で JAX を使って複数の GPU で学習させる場合は、skrl を使います。

## OSS: Isaac Lab Mimic と SkillGen

少数の人の操作の記録から、多数の操作の記録を自動で作る、Isaac Lab の模倣学習の機能です。

Isaac Lab Mimic は、記録を物体ごとの小さな作業に区切り、新しい物体の配置に合わせて変換してつなぎ、成功したものだけを残します。開発元の文書によれば、生成の成功率は、立方体を積む課題で約50パーセント、人型ロボットの GR-1 でつかんで置く課題で、65から80パーセントでした。それで学習させた方策の成功率は、課題によって40から86パーセントでした。

SkillGen は、区切りの間の移動を、GPU で動く、衝突を避ける動作の計画、cuRobo でつなぎます。これにより、狭い箱の中のような、障害物のある場面にも対応します。

使える条件として、Mimic は Linux でだけ使えます。SkillGen は、開発元によれば、1から2の環境で、24 GB 以上の GPU のメモリが要ります。

ライセンスは、isaaclab_mimic が Apache-2.0 です。SkillGen が使う cuRobo は、独自の利用許諾です。これは Isaac Lab の README と文書の表記によります。

状態は実用です。正式な版の Isaac Lab 2.3 に含まれていて、SkillGen は 2.3.0 で追加されました。ただし、SkillGen は独自の利用許諾の cuRobo に頼るので、その条件に注意が要ります。また、3.0 の文書では、模倣学習の機能は「試験的な機能」の欄に置かれています。

一次情報は、遠隔操作と Mimic の公式の文書と、SkillGen の公式の文書です。

## OSS: Isaac Lab-Arena

Isaac Lab の上で、ロボットの方策を大規模に評価するための枠組みです。

場面、ロボット、課題の3つを別々に定義して組み合わせ、Isaac Lab の環境を作ります。場面は配置と物体、ロボットは機体、センサー、制御、課題は何をさせるか、です。物体は、「上に」「隣に」のような関係で配置できます。GPU で並列の数千の環境で評価を回し、小さな作業ごとの成否の判定や、条件の変化への敏感さの分析で、方策がどこで失敗するかを調べます。評価する方策として、Isaac GR00T や π0.5 などを、クライアントとサーバーの形でつなぐ例があります。

ライセンスは Apache-2.0 です。ただし、動かすには、別の条件の部品を含む Isaac Sim が要ります。

状態は研究段階です。README で、試作の段階である Alpha で、API が安定しておらず、本番での利用は勧めない、としているためです。確認した時点の版は 0.3.1 で、Isaac Lab 3.0.0-EA と組み合わせます。

## OSS: LEAPP と Isaac ROS Deploy

Isaac Lab で学習させた方策を、実機で動かすための、2つの道具です。Isaac Lab 3.0 の世代のものです。

LEAPP は、Lightweight Export Annotations for Policy Pipelines の略です。方策のネットワークだけでなく、観測の作り方、行動の変換、再帰の状態の扱いまでを、まとめて書き出します。出力は3つです。モデルで、既定は ONNX。実行の周期などの情報。そして、再帰の状態や前回の行動の初期値で、形式は safetensors です。対応する学習の仕方と制約は、さきほどの実機への展開で説明しました。

Isaac ROS Deploy は、LEAPP で書き出した方策を、ROS 2 の上で、NVIDIA Triton で推論して動かす、パッケージの集まりです。方策の入出力を、ROS のトピックや ros2_control につなぎ、出力を安全のための制御器で制限することもできます。VLA の方策にも対応する、としています。

ライセンスは、Isaac ROS Deploy が Apache-2.0 です。LEAPP のパッケージ自体のライセンスは、読んだ文書には書かれておらず、未確認です。

状態は研究段階です。LEAPP は、正式な版の前の Isaac Lab 3.0 の機能です。Isaac ROS Deploy は版の番号を示しておらず、最新の更新は2026年9月21日です。また、Isaac ROS Deploy で、Isaac Sim の中のロボットに方策を動かす機能は、確認した時点の最新の公開には含まれていません。

一次情報は、LEAPP での書き出しの公式の文書と、Isaac ROS Deploy の公式リポジトリです。

## OSS: HOVER

人型ロボットの全身の制御の方策を、Isaac Lab で学習させるための拡張です。

人の動きのデータを手本に、まず教師の方策を学習させ、それを使って、生徒の方策を蒸留で学ばせます。論文によれば、狙いは、用途ごとに違う指令の与え方を、1つの方策にまとめ、切り替えて使えるようにすることです。例えば、移動では胴体の速度、机の上の作業では上半身の関節の角度、というように指令の与え方が違いますが、用途ごとに別の方策を作らずに済むようにします。論文は ICRA 2025 のものです。

MuJoCo の上での確かめ、つまり sim-to-sim と、実機の Unitree H1 への展開の手順を含みます。開発元は、Isaac Lab の公式の文書で、学習と展開の手引きとして紹介しています。

ライセンスは Apache-2.0 です。

状態は研究段階です。論文の実装で、正式な版の公開がないためです。動作を確かめた版は Isaac Lab 2.0.0 と Isaac Sim 4.5.0 で、確認した時点の最新より古いです。また、実機への展開は H1 だけに対応します。

## 解説: 歯車の挿入の方策の学習と ROS での展開

Isaac Lab の公式の文書にある、強化学習で学習させた方策を、実機の腕で動かすまでの手引きです。腕は UR10e で、グリッパーが付いています。

歯車をつかんだ状態から、カメラで推定した軸の位置を手がかりに、関節の位置を少しずつ動かして差し込みます。1つの方策で、3つの大きさの歯車に対応します。

学習は RSL-RL で行います。カメラの推定の誤差に合わせた観測のノイズと、駆動のゲインと関節の摩擦のばらつきを入れます。

実機の側は、Isaac ROS の物体の位置と姿勢の推定の FoundationPose と、動作の計画の cuMotion、そして方策を動かす ROS のノードを組み合わせます。シミュレーションと実機の差を小さくするための教訓は、さきほどの実機への展開でまとめた6つです。

## まとめ

Isaac Lab は、GPU で並列にロボットの学習を行う、NVIDIA の枠組みです。確認した時点では、安定の 2.3 系と、計算の部分を選べるようになる先行の 3.0 があり、長く使うコードは 3.0 への移行を見込んで書くのが無難です。

環境は、部品を組み合わせるマネージャー型か、1つのクラスに書く直接型で作ります。マネージャー型では、行動、観測、イベント、報酬、終了、指令、カリキュラムの7つのマネージャーを使います。実機に移すときは、アクチュエータのモデル、制御の周期、摩擦やノイズの模擬が効きます。

強化学習のライブラリは、RSL-RL、RL-Games、skrl の3つがほぼ同じ速さで、Stable-Baselines3 は少し遅いので、速さよりも、アルゴリズムや文書で選びます。模倣学習は、少数の記録を Isaac Lab Mimic で増やして学ばせます。実機へは、IO 記述子や、3.0 の LEAPP と Isaac ROS Deploy で方策を渡します。
